# ADR-046: Flight change push: an anonymous server subscription

- **Status:** Accepted
- **Date:** 2026-11-09
- **Related:** ADR-011, ADR-029, ADR-045; tracker #143 (Phase 2), #106 (WebSocket relay, decoupled)
- **Plan:** `~/projects/beanies-ops/docs/plans/2026-11-09-travel-live-flight-checks-phase-2-push.md`
- **Implementation:** `infrastructure/lambda/flight-status/` (`alerts.mjs`, `alertsStore.mjs`, `webhook.mjs`, `cleanup.mjs`, `credits.mjs`, `alertToken.mjs`, `schedule.mjs`, `copy.mjs`, `push/`), `infrastructure/lambda/registry/alertToken.mjs`, `src/services/native/pushRegistration.ts`, `src/utils/flightStatus/alerts.ts`, `src/stores/flightStatusStore.ts`; shipped in app 1.2.0

## Context

ADR-045 made flights self-checking on the device: the app asks an anonymous proxy for a flight's schedule when it is open. A family asleep the night before an early departure learns nothing until they open the app. Closing that gap needs the one thing ADR-045 deliberately avoided: server-held, per-device state, because a closed iOS or Android app can only be woken by APNs or FCM. This is the first remote push in beanies and the first per-device record a beanies server keeps, so the zero-knowledge posture (ADR-011, ADR-029) has to be kept by construction, not by promise.

## Decision

1. **The server holds an anonymous subscription, and nothing else.** A DynamoDB table (`beanies-family-flight-alerts-<env>`, one partition per flight number) holds, per watching device: the push token (and its hash as the sort key), platform (`ios` or `android`), a two-letter language, the provider's departure and arrival airport codes, the last revision the device knows (`sent_rev`) and an expiry. It never holds a family id, a member, a trip, a segment id, a name, an IP or a device model. The expiry is the flight date plus 72 hours, so a record is gone shortly after the flight has landed (DynamoDB TTL is lazy, so it may linger a further day; it is never read after expiry). The Settings sentence says exactly this.
2. **Entitlement proof without identity.** The registry GET already knows a family's entitlement, so it mints `flightAlertToken` inside the `entitlement` object when the family is eligible (not enforced, trial, beta, or active on the full plan). The token is `v1.<exp>.<sig>`: `exp` is the next whole hour plus 7 days and `sig` is an HMAC-SHA256 over `alert:v1:<exp>` with a secret shared by the registry and flight-status Lambdas. It carries no family id, hash or nonce, and every family polling in the same hour gets the identical token, so a registration cannot be linked to a family or a mint time. The flight-status Lambda verifies signature and expiry on subscribe only; unsubscribe needs no token (knowing the push token is the proof, since the sort key is its hash), so a lapsed family can still leave on sign-out. The signer and verifier are two zero-dependency restatements pinned by one golden vector in both test suites (the `email-unsubscribe/token.mjs` precedent; no cross-Lambda shared directory).
3. **The token is a shared bearer, on purpose.** One leaked token lets anyone subscribe for up to 7 days. That is bounded by the soft `x-api-key`, the per-IP hourly bucket, the per-flight device cap (12), the daily provider-call cap and the credit refill cap, and it is the same class of residual as ADR-045's bundle key. It also sits in the device's entitlement cache for up to 7 days, like the soft key. It is not "fixed" by binding the token to anything, because any binding would be an identity.
4. **APNs and FCM, not #106's relay.** #106 is a WebSocket relay between devices that are open and online; a WebSocket cannot wake a closed iOS app. Phase 2 needs APNs and FCM, which #106 does not use, so the two share nothing. The Lambda sends through two zero-dependency senders (APNs over HTTP/2 with an ES256 JWT; FCM HTTP v1 with a service-account OAuth token). The Lambda speaks to the production APNs host only, so an iOS debug build (sandbox token) is refused as `BadDeviceToken`; device testing uses TestFlight, and the sender logs `apns_reason` so a mismatch is readable. Web Push for the PWA is out of scope: it needs VAPID keys, a service-worker handler and a third sender, and is its own follow-up.
5. **Change feed: AeroDataBox Flight Alert webhooks, per flight number.** The provider subscribes per flight number (no date, no event filter), never expires, is free to create, and bills one credit per flight item per notification for every instance of that number in a window from 6 hours ago to 72 hours ahead. It signs nothing. So: (a) the webhook route is authenticated by a secret path segment (`/flight-status/webhook/{secret}`, compared in constant time, never logged); (b) there is no event-class filter, only a per-device revision comparison; (c) a provider subscription is created once per number on the first subscribing device and must be cancelled when no device needs it.
6. **The sweep is the only canceller.** A scheduled `cleanup` task (EventBridge `rate(6 hours)` into the same Lambda) is the one two-way reconcile between the table and the provider's own subscription list. It matches on each listed subscription's callback URL: exactly ours is ours, our base URL with another secret is stale (cancelled, which is how a secret rotation heals), anything else is foreign and never touched. It subscribes numbers that have live devices and no subscription, adopts orphans, and cancels subscriptions with no live device. The request path never cancels and never counts devices (an earlier design had an atomic counter; it was redundant exactness with its own race). A leak is therefore bounded at 6 hours, which is a handful of credits. The cost is that nothing cancels within seconds of the last device leaving, which nothing needs. The new exposure is a sweep that stops running, so it has a heartbeat alarm that fires on silence.
7. **Credits are kept above a floor automatically.** At zero credits every subscription pauses silently. `ensureCredits` runs on every webhook (each notification carries `balance.creditsRemaining`) and on every sweep (the balance endpoint is free); below `ALERT_CREDIT_FLOOR` (100) it refills `ALERT_CREDIT_REFILL` (200) credits from the unit quota, under a global daily cap of 2 refills tracked in the alerts table. An absent balance counts as zero, so the first sweep seeds it. A counter fault fails closed (no refill, alarmed), because an unbounded refill is the failure the counter exists to stop. The alerts store itself fails closed for subscriptions (`503 alerts_unavailable`, the device retries): a lost registration is a lost notice, unlike the Phase 1 cache, where a lost item only costs units.
8. **The revision contract is restated and pinned, not shared.** `sent_rev` and the device's `liveRevision` must be byte-identical or the first webhook pushes a revision the device already knows. Each Lambda is its own zero-dependency zip and the client's matcher pulls airport data that must never ship in a Lambda, so `schedule.mjs` restates `revisionOf`, `cancelRevisionOf` and the code-only leg selection, and a client parity test runs shared fixtures through both implementations. The device registers the provider's own airport codes for the leg it already matched, so the server never runs name matching. One selection rule is server-only: a webhook payload is per flight NUMBER and carries only the items that changed, so the server takes the leg departing `dep` NEAREST the departure the device knows (its `sent_rev`) within 12 hours, whatever its date, and falls back to the registered date only when no departure is known. Daily instances of a number are 24 hours apart, so 12 hours is the largest bound that never mistakes the adjacent instance for a move (the on-date rule did, for a device already pushed to an off-date departure). The accepted asymmetry with the client, which fetches the booked date ±1 day: a retime of 12 hours or more is not pushed, and the device's on-open check still finds and applies it. A late notice is preferred to a false one.
9. **Idempotency by claiming before sending.** For each planned push the handler first advances the device's `sent_rev` with a conditional update, and sends only when the claim succeeded, so a duplicate or concurrent delivery never sends twice. The claim is kept even when the send fails: there is no retry path, by design. The failure is in the log and the change is in the app on the next open. The replay guard (`e#<notificationId>`, 24 hour TTL) is written only after the fan-out, so a store fault answered 500 never swallows the provider's retry.
10. **The push is the notice; the open-app path still writes.** The push is composed server-side from a two-language table (`copy.mjs`, pinned to the client strings by a drift test) with no names: flight, date, time, terminal, and the airline name from the provider. The pod write stays on the device through the ADR-045 path on the next open (no `content-available`, no silent push, no background mode). The device seeds `sent_rev` with the revision its plan already holds, and suppresses its own local notice when its registration shows the push was the notice (`pushCovered`), judged once, when the local notice is first stamped, so the outcome does not depend on the order of a debounced rebuild and a network call. Because a recorded registration mutes the local notice, subscribe answers 200 only while a provider subscription for the number exists or is being made: `ready`, or `pending` for exactly two cases (another request holds the claim and is filling it; or the provider call succeeded and only recording its id failed, which the sweep adopts), both keeping the device record. Any other failure after the device record is written (daily budget, an upstream error, an unset webhook secret, a store fault) deletes that record again and answers the original error, so the device records nothing and keeps its Phase 1 local notice. The server log names the outcome `ready`, `pending` or `failed`. The client counts a registration as evidence only once the server answered `ready`: a `pending` (or unreadable) subscribe answer is recorded but unconfirmed, re-asked each run, and never mutes the local notice.
11. **Accepted gap: no fallback banner.** A device registered before it first saw a revision gets no local OS notice for it even if the push never arrived (send failed, token invalid, an airport outside the provider's live coverage). This is deliberate: one rule, no guessing about Notification Center state. The in-app change block and bell still show the change, and the server log shows no `sent` for the number.
12. **Declarations.** The iOS privacy manifest adds `NSPrivacyCollectedDataTypeDeviceID` (not linked, not tracking, app functionality); Play Data Safety adds "Device or other IDs" (app functionality, not shared); the runbook's data-collection table gains the flight-number-and-date proxy call (omitted in Phase 1) and the alerts table; the privacy page gains a live flight checks section and lists AeroDataBox. "No device identifiers" becomes "no advertising identifiers; the only device identifier is the push address held while a flight is watched". The Help article and the Settings privacy sentence say the same.

## Consequences

- The server now holds a push address with a flight number and date. It cannot say whose phone that is, and it forgets it within about a day of landing, but it is no longer true that the server holds nothing per device; the privacy copy, the store declarations and this ADR are the record of that.
- Provider cost scales with the number of distinct watched flight numbers, not families or devices, and is bounded by the credit refill cap and the daily provider-call cap, both shared with Phase 1 checks on the 5,000-unit monthly quota. The Phase 1 units-low warning covers refills.
- There is one flight-status environment, and it is prod. Anything needing a forced fault is a unit test, never a prod experiment.
- A secret rotation (`aerodatabox_webhook_secret`) briefly answers `webhook_rejected` (alarmed, expected) until the next sweep re-subscribes under the new URL.
- Alerts fire only for airports with live provider coverage; elsewhere the on-open check remains the only signal.
- The new Terraform (table, route, EventBridge rule and the two secrets) lives in the private ops repo; the APNs key and FCM service-account fields are Terraform variables, and `google-services.json` is a GitHub secret written at Android build time.

## Revisit when

- Web Push for the PWA is planned (VAPID, service worker, a third sender).
- The provider adds a signed webhook (the secret path could then become defence in depth) or per-date subscriptions (cost would drop).
- One flight number's device count or the daily refill cap is hit in practice.
- A server-driven pod write becomes desirable, which would need a different trust model than "the write stays on the device".

## Alternatives considered

- **Polling the provider on a schedule.** Rejected: it would spend the 5,000-unit quota on flights nobody changed. Kept as the documented fallback had the Flight Alert API not been reachable on the held channel.
- **A family id or member id on the subscription.** Rejected: it would break the privacy sentence and the zero-knowledge posture for a convenience the design does not need.
- **A device counter on the provider item with cancel-at-zero in the request path.** Rejected for a 6-hourly sweep: the counter had its own race and added a provider call to the invalid-token path.
- **Silent pushes (`content-available`) that write the pod.** Rejected: unreliable on iOS, need a background mode, and tempt a server-driven write.
- **Reusing the #106 relay.** Rejected: a WebSocket cannot wake a closed app.
