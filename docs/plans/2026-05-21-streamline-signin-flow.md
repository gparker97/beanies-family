# Plan: Streamline returning-member sign-in (kill the duplicate provider + file selection)

> Date: 2026-05-21
> Related issues: None — direct implementation
> Plan file: `docs/plans/2026-05-21-streamline-signin-flow.md`
>
> **No GitHub issue created.** This plan was approved for direct implementation. Full prompt history is in the `## Prompt Log` section.

## User Story

As a family member signing back in to my pod, I want to pick my family once and go straight to unlocking it, so that I'm not asked to choose "Google Drive vs local" and then re-pick the exact same `.beanpod` file I already identified.

## Context

A returning user who signs out (or opens a tab/PWA whose token is gone) and signs back in is asked to identify their pod **up to three times**:

1. **Pick the family** ("which beanies") — `FamilyPickerView`, shown when `familyContextStore.allFamilies.length > 0` (auto-selected when only one). **Essential.**
2. **Pick the provider** ("Google Drive or local file?") — generic `LoadPodView` storage cards. **Redundant** — the picked family's stored config already says which provider.
3. **Pick the file** — `GoogleDriveFilePicker` lists every `.beanpod` on the account. **Redundant** — we already know the exact `driveFileId`.

Then password/biometric decrypt — the correct cryptographic boundary, unchanged.

**Root-cause finding (the reframe):** `LoginPage.handleFamilySelected` (src/pages/LoginPage.vue:323-397) _already does the right thing_ — on family-select it re-inits the provider for that family (`switchFamily` → `syncStore.resetState()` → `syncStore.initialize()`, which reads the per-family `PersistedProviderConfig` from `fileHandleStore` and sets `isConfigured`) and **attempts a silent auto-load** (`syncStore.loadFromFile()`). When that succeeds, the user goes straight to decrypt with no provider/file prompts.

The duplicate selection is the **fallback** that fires when the auto-load _fails_. After an explicit sign-out it fails for exactly one reason: `authStore.signOut` (src/stores/authStore.ts:896-901) deliberately deletes + revokes the Google **refresh token** (via `clearGoogleSessionState`, googleAuth.ts:1140) to stop a later sign-in with a _different_ account silently reusing the old grant. So `provider.read()` → `getValidTokenSilent()` → no refresh token → throws `TokenExpiredError` (googleAuth.ts:1093 default-constructor variant; or the 401-then-failed-refresh variant at googleDriveProvider.ts:215), even though the family's `providerConfig` already holds `{ type: 'google_drive', driveFileId, driveFileName, driveAccountEmail }`.

**Verified failure-propagation chain (corrects the original plan).** `TokenExpiredError` does **not** propagate up to `handleFamilySelected`. The chain is:

- `googleDriveProvider.read()` throws `TokenExpiredError`: in the literal post-sign-out case it is the default-constructor variant thrown by `getValidTokenSilent()` _before any API call_ (read() calls `getValidTokenSilent()` at googleDriveProvider.ts:194 → googleAuth.ts:1093); in the access-token-rejected case it is the explicit-message variant (googleDriveProvider.ts:215). **Both message shapes contain the substring "silent refresh failed"** — verified, so a single matcher classifies both.
- `syncService.load()`'s generic `catch` (syncService.ts:783) does **not** rethrow it — it stores `e.message` in `lastError` and returns `null`.
- `syncStore.loadFromFile()` sees `text === null`; the message isn't a `DriveApiError:404:` so it falls through and returns `{ success: false }` (syncStore.ts:597) — **no throw, no needsPassword**.
- In `handleFamilySelected`, `loadResult` is `{ success: false }` → it hits the **`else` arm (LoginPage.vue:364)**, never the `catch` (line 374).

So the original plan's "catch `TokenExpiredError` in `handleFamilySelected`'s `catch`" is incorrect. The branch must be driven by a **typed `reason`** returned from `loadFromFile`, classified in the store from `syncService.getState().lastError` — reusing the existing `/silent refresh failed/i` matcher (`isAuthTransientSyncError`, syncStore.ts:354).

Everything needed to skip the duplicates survives sign-out and is already in hand:

- `allFamilies` (the picker list) — survives sign-out.
- per-family `PersistedProviderConfig` (`{ type, driveFileId, driveFileName, driveAccountEmail }`, fileHandleStore.ts:11-16) — survives sign-out; **already passed in the `handleFamilySelected` payload** (`payload.providerConfig`).
- a direct-load-by-id path already exists and is used by the recovery flow: `syncStore.loadFromGoogleDrive(fileId, fileName)` (syncStore.ts:2117) → `GoogleDriveProvider.fromExisting(fileId, fileName, accountEmail?)` (googleDriveProvider.ts:393) → `provider.read()` (no picker). Used by `attemptResumeFromRegistry()` (syncStore.ts:2251) / `ResumePodSetup.vue`.

**Decision (greg):** keep sign-out fully clearing/revoking the token (privacy + wrong-account safety). Do **not** add a "Lock vs Sign out" split or preserve tokens. The fix is purely making the _failure fallback_ token-aware and config-driven so the duplicate provider/file selection disappears and re-sign-in becomes "pick family → one consent → decrypt" (or "pick family → decrypt" when a refresh token is still present).

## Requirements

1. When `handleFamilySelected`'s silent auto-load fails **because the Google token is gone/expired** (`reason === 'auth'`) **and** the family's `providerConfig` is `google_drive` with a `driveFileId`: do **not** show the generic provider cards or the Drive file picker. Instead show a **focused reconnect** ("Reconnect to load \<family\>"), and after a single Google consent, load **that exact `driveFileId`** via `loadFromGoogleDrive(driveFileId, driveFileName)` → decrypt.
2. The "refresh-token-present, access-token-expired" case must remain **fully silent** (auto-load succeeds → straight to decrypt). Do not regress this ADR-028 behavior — only the _failure_ path changes.
3. If the known `driveFileId` no longer resolves (deleted / moved / `404`), fall back **gracefully** to the existing Drive file picker (`listGoogleDriveFiles` → `GoogleDriveFilePicker`) as a last resort — never a dead end, with a clear message.
4. Local-provider families keep their existing focused behavior: `isConfigured && needsPermission` → permission-grant UI (no file picker); Firefox/Safari (no File System Access API) keep the existing `unsupported-browser` messaging.
5. Preserve the explicit escape hatch: "Load a different file" (`handleLoadDifferentFile`, `forceNewGoogleAccount`) still lets the user deliberately pick a different account/file.
6. iOS / installed-PWA redirect auth must work end-to-end. The reconnect consent uses the existing redirect path **via `useGoogleReconnect()`**, which already returns to the current URL (`/welcome`) on completion. After the redirect, `LoginPage.onMounted` re-runs auto-select / family-picker, and because a token is now in hand `loadFromFile()` succeeds silently → straight to decrypt. **No resume-setup wiring and no new redirect-return state are added** (the resume-setup path requires an authenticated-but-no-pod session; a signed-out returning member is unauthenticated, so App.vue routes them to plain `/welcome`, App.vue:716-728 — not `?resume=setup`).
7. Multi-family: each picker entry loads its own `driveFileId` (no cross-talk).
8. No silent failures: every new branch surfaces an informative message (toast or inline) + a `console.warn`/`reportError` breadcrumb with a `[surface]` prefix per the project's no-silent-failures rule.

## Important Notes & Caveats

- **Do not weaken sign-out.** Token deletion + revocation stays. The wrong-account-reuse comment at authStore.ts:896-901 / googleAuth.ts:1122-1139 is the reason; respect it.
- **Reuse, don't reinvent (verified inventory):**
  - **Interactive-auth-with-iOS-redirect already exists** as `useGoogleReconnect()` (composables/useGoogleReconnect.ts) — desktop popup via `requestAccessToken({ forceConsent: true })`, iOS/PWA via `shouldUseRedirectAuth()` → `startRedirectAuth(currentPath, loginHint)`. The reconnect action **composes this**; it does **not** re-implement the popup/redirect split. (This is already the composable behind `GoogleReconnectToast`.)
  - **Why auth must come before the load:** `loadFromGoogleDrive` acquires its token via `requestAccessToken()` (syncStore.ts:2148), which opens a **popup** even on iOS — wrong for the redirect path. Acquiring the token first via `useGoogleReconnect()` means `loadFromGoogleDrive`'s `requestAccessToken()` finds a valid cached token (`isTokenValid()` short-circuit, googleAuth.ts:1050) and is a no-op auth-wise (it just reads).
  - **The known-file load + decrypt/biometric handoff already exists** as `LoadPodView.handleDriveFileSelected({ fileId, fileName })` (LoadPodView.vue:551) — note the single-object parameter shape — the reconnect handler calls straight into it; no new Drive-load/decrypt code.
  - **The 404 picker fallback already exists** as `handleLoadFromGoogleDrive()` (LoadPodView.vue:462) → `GoogleDriveFilePicker`.
  - **Reconnect strings already exist:** `googleDrive.reconnect` (uiStrings.ts:4683), `googleDrive.sessionExpired` (4684), `googleDrive.reconnectFailed` (4820) and `fastLogin.loadErrorDrive` (3315). Reuse these. Only **one** new string is genuinely new: a family-scoped reconnect headline.
- **The picker stays** as the last-resort fallback (req. 3) and the deliberate-switch path (req. 5) — we're removing it from the _default_ happy path, not deleting it.
- **Don't show the reconnect screen for non-token failures.** A genuine "file not found" or "corrupt" should not masquerade as "reconnect" — branch precisely on `reason`.
- **`showGoogleReconnect` (the toast banner) does not double-surface with the focused panel.** Worth pinning so a future reader doesn't worry about it: in the _literal post-sign-out_ case the auth layer never fires `onTokenPermanentlyExpired` (no refresh token → `performSilentRefresh` returns `null` at googleAuth.ts:869-878 **without** incrementing the failure counter or escalating), so `showGoogleReconnect` stays `false`. In the _invalid_grant escalation_ sub-case (Google revoked the refresh token, or ≥`SILENT_REFRESH_FAILURE_ESCALATION_THRESHOLD` consecutive silent-refresh failures) the failed `loadFromFile()` _does_ fire `firePermanentFailureCallbacks()` → `setupTokenExpiryHandler`'s subscriber sets `showGoogleReconnect = true` (syncStore.ts:2477-2481). That is **harmless on the login page**: `GoogleReconnectToast` is gated by `!authStore.needsAuth` (App.vue:1305) and an unauthenticated returning member has `needsAuth === true`, so the toast is suppressed; and it self-heals — `loadFromGoogleDrive` clears it defensively at its start (syncStore.ts:2126) and the `onTokenAcquired` path clears it the moment our reconnect acquires a token (syncStore.ts:2489). So both the post-sign-out and the escalation cases land on the focused panel with no competing banner; no extra cleanup code is required.

## Assumptions

> **Review before implementation.** (Each verified at planning time against the cited code.)

1. `PersistedProviderConfig` and `familyContextStore.allFamilies` both survive `authStore.signOut` — verified: `signOut` clears tokens + the per-family encrypted cache, not the provider config or families list. (fileHandleStore.ts:11-16, googleAuth.ts:1140.)
2. `loadFromGoogleDrive(fileId, fileName)` calls `requestAccessToken()` (silent if a cached/refresh token exists; popup otherwise — **so on iOS the interactive token must be obtained first via `useGoogleReconnect()`**) and returns `{ success, needsPassword }` with the envelope staged; on any throw it sets `error.value = (e as Error).message` and returns `{ success: false }` (syncStore.ts:2187-2189). **NOTE — the 404 message contract (corrected this round):** that `error.value` holds the _raw_ Drive error message (e.g. Google's "File not found" body), **not** a `DriveApiError:404:`-prefixed string — the `DriveApiError:404:` prefix is applied only by `syncService.load()` (syncService.ts:780), a code path `loadFromGoogleDrive` bypasses (it calls `provider.read()` directly, syncStore.ts:2152). Therefore the original "inspect `syncStore.error` for the `DriveApiError:404:` shape" plan would have matched an unstable, prefix-less Google string. The fix (Layer 2 §4) classifies the 404 **structurally inside `loadFromGoogleDrive`** (`e instanceof DriveApiError && e.status === 404`, or the `DriveFileNotFoundError` subclass — both already importable; `DriveApiError` is already imported at syncStore.ts:54 and used this exact way at syncStore.ts:1851), returning a typed signal the view branches on — never a message substring. Verified at planning time.
3. ADR-028 (refresh-token persistence) is live in prod — the "access token expired, refresh token present" case already auto-loads silently. (Deployed 2026-05-21.)
4. **`loadFromFile()` does NOT surface `TokenExpiredError`** — it returns `{ success: false }` for both auth failures and transient/other failures (syncStore.ts:597; root cause syncService.ts:783). Therefore extending its return with a typed `reason` is **in scope and required**, not optional. The classification reads `syncService.getState().lastError` and matches the `TokenExpiredError` message shape recognised at syncStore.ts:354. **Both** `TokenExpiredError` variants — the explicit-message 401 one (googleDriveProvider.ts:215) and the default-constructor one thrown on a missing/unrefreshable token (googleAuth.ts:1093, the literal post-sign-out case) — contain "silent refresh failed", so the single `/silent refresh failed/i` matcher classifies both. Verified at planning time.
5. The iOS redirect return lands on plain `/welcome` (not `?resume=setup`) for a signed-out member, where `LoginPage.onMounted` re-runs and `loadFromFile()` now succeeds with the freshly-acquired token. No new return-state plumbing is needed. (App.vue:716-728, 740-765.)

## Approach

**One behavioral change, expressed in two layers, reusing existing primitives end-to-end.**

### Layer 1 — `syncStore.loadFromFile()` returns a typed `reason`, and `LoginPage.handleFamilySelected` branches on it

**Store (single source of truth for classification):** Extend `loadFromFile()`'s return type to `{ success: boolean; needsPassword?: boolean; reason?: 'auth' | 'not-found' | 'error' }`. Set it on the failure paths inside `loadFromFile` (syncStore.ts:575-597 — the `if (!text)` block, which is the only path that reads `lastError`; the version-mismatch path at 603 and any other non-text failure naturally take the `'error'` default, which is correct):

- `lastError` starts with `DriveApiError:404:` → `reason: 'not-found'`.
- `lastError` matches the `TokenExpiredError` shape → `reason: 'auth'`. **Reuse the existing `isAuthTransientSyncError(msg)` matcher already defined in this store (syncStore.ts:354).** Do not introduce a second, parallel matcher — there must be exactly one regex that encodes the "silent refresh failed" message contract, so the consumers (background-sync classification at syncStore.ts:1766/1777 and the new `loadFromFile` classification) can never drift. If a clearer name is wanted for the login-path call site, rename the existing function (and update its two current callers) rather than adding a sibling.
- otherwise → `reason: 'error'`.

This keeps the `instanceof`/string-matching inside the store; the view never inspects `lastError`. No other caller of `loadFromFile` is forced to change — `reason` is optional and additive (existing `{ success, needsPassword }` consumers at LoginPage.vue:233/347, LoadPodView.vue:182, App.vue:409, and syncStore.ts:403/1720/1813 keep working — verified the full caller set by grep).

**Message-contract guard (reliability).** The classification depends on a substring of an error _message_, which is inherently fragile — a future refactor of `TokenExpiredError`'s message would silently reclassify auth failures as `'error'` and quietly bring back the duplicate prompts. Mitigate without over-engineering: (a) add a one-line comment at both the `TokenExpiredError` constructor (googleAuth.ts:1030) and the matcher (syncStore.ts:354) noting they are coupled by the "silent refresh failed" phrase; (b) the store unit test (Testing Plan §1) asserts `reason: 'auth'` for **both** `TokenExpiredError` message variants, so a message change that breaks the contract fails CI rather than shipping silently.

**View (`handleFamilySelected`, LoginPage.vue:343-396):** In the auto-load branch, after `loadFromFile()`:

- Keep the `success` and `needsPassword` arms unchanged (no regression to the silent path).
- Replace the single `else` (line 364) with a `reason` switch:
  - `reason === 'auth'` **and** `payload.providerConfig?.type === 'google_drive'` **and** `payload.providerConfig.driveFileId` → set a new intent `reconnectDriveFile.value = { fileId, fileName }` (derive `fileName` from `providerConfig.driveFileName ?? '<family>.beanpod'`) and route to `LoadPodView` with that prop set; do **not** set the generic `loadError`/`needsPermissionGrant` state.
  - any other case (`'not-found'`, `'error'`, local provider, no `driveFileId`) → existing generic fallback (`loadError` + `providerHint`), unchanged.
- The `catch` arm (line 374) stays as the defensive net for unexpected throws and keeps the existing generic fallback — but it is no longer the token-expiry path.

`reconnectDriveFile` is reset to `undefined` at the top of `handleFamilySelected` (alongside the existing `loadError` reset, line 337) and in `handleLoadDifferentFile` / `handleNavigate`, so it never leaks across navigations (done via the shared `resetLoadPodState()` helper — see Sustainability §2).

### Layer 2 — `LoadPodView` gains a "reconnect to known Drive file" mode that composes existing pieces

Add prop `reconnectDriveFile?: { fileId: string; fileName: string }`. It feeds the `'reconnect'` variant of the new `viewState` union (Sustainability §1): when `viewState === 'reconnect'`, render a **single focused panel** styled like the existing `needsPermissionGrant` block (LoadPodView.vue:768-796) — same amber-icon card, a short headline, and one button — in place of the storage cards. (`viewState`'s documented precedence guarantees exclusivity, so there is no separate "which panel wins?" question.) The handler:

1. Import and use `useGoogleReconnect()`. On click call `reconnect(syncStore.providerAccountEmail ?? providerConfig.driveAccountEmail)` (login hint nudges the right Google account). This composable:
   - **desktop** → popup consent (`requestAccessToken({ forceConsent: true })`);
   - **iOS/PWA** → full-page redirect (`startRedirectAuth(currentPath, loginHint)`), returning `true` as it navigates away — the page reloads at `/welcome`, `LoginPage.onMounted` re-runs, and `loadFromFile()` then succeeds silently (req. 6). Nothing further runs in this handler on the redirect path.
2. On desktop success (`reconnect()` resolves `true` without navigating): call `handleDriveFileSelected({ fileId, fileName })` (LoadPodView.vue:551) directly — note the single-object argument — this already does `loadFromGoogleDrive` → auto-decrypt → biometric-or-decrypt-modal. **No new load/decrypt code.**
3. On `reconnect()` returning `false`: surface `useGoogleReconnect`'s `reconnectError` (or the existing `googleDrive.reconnectFailed` string) inline via `formError`, and `console.warn('[LoadPodView] reconnect failed: ...')` — never a dead end.
4. **`404` / file-not-found (detection corrected this round — classify in the store, not the view).** Keep the 404→picker _decision_ in the reconnect handler, but drive it off a **structured** signal, not a message substring:
   - **Store change:** in `loadFromGoogleDrive`'s `catch` (syncStore.ts:2187), classify the not-found case explicitly — `if (e instanceof DriveApiError && e.status === 404)` (this also covers the `DriveFileNotFoundError` subclass, since it `extends DriveApiError` with `status` 404; driveService.ts:611-631) — and surface it as a typed signal: extend the return to `{ success: boolean; needsPassword?: boolean; reason?: 'auth' | 'not-found' | 'error' }` (same shape as `loadFromFile`, for symmetry) returning `reason: 'not-found'` on the 404, `reason: 'error'` otherwise. Keep setting `error.value = (e as Error).message` for the breadcrumb. This mirrors the established 404-handling idiom already in this store (the `reloadIfFileChanged` catch at syncStore.ts:1851 does exactly `e instanceof DriveApiError && e.status === 404`). **Do not** rely on the `DriveApiError:404:` _string prefix_ here — that prefix is only produced by `syncService.load()` (syncService.ts:780), which this path does not traverse, so the prefix is never present on `loadFromGoogleDrive`'s `error.value`. This was the latent bug in the earlier draft of §4.
   - **View change:** `handleDriveFileSelected` already returns `loadFromGoogleDrive`'s result; the reconnect handler inspects **`result.reason === 'not-found'`** (not `syncStore.error`'s text) and, if matched, clears `reconnectDriveFile` and calls the existing `handleLoadFromGoogleDrive()` (LoadPodView.vue:462) to drop into the Drive file picker — with a clear "we couldn't find that file, pick it from your Drive" message. To avoid coupling the _shared_ `handleDriveFileSelected` to the reconnect caller (Sustainability §4), have it **return** the `loadFromGoogleDrive` result (it currently returns `void`) so the reconnect handler can branch on `reason` at the call site; the picker caller simply ignores the return, exactly as today. Reuses the existing picker entirely; `handleDriveFileSelected` stays a pure "load this fileId, here's what happened" method shared cleanly between the picker and reconnect callers, with **no `reconnectDriveFile` reference inside it**.

The only genuinely new code is: the focused reconnect panel (reusing the permission-grant card styling) + a thin reconnect handler that composes `useGoogleReconnect()` + `handleDriveFileSelected()` + the existing 404→picker fallback, plus the small structured-404 classification added to `loadFromGoogleDrive`.

### Sustainability & Maintainability

This change is small in behavior but lands on two structures the codebase has **already flagged as fragile**. Address that head-on so we don't pay it down later as tech debt:

1. **`LoadPodView`'s implicit state machine — refactor to `viewState` NOW (greg's decision).** Lines 52-56 of `LoadPodView.vue` carry an in-code `TODO(state-machine-refactor)` noting that the independent booleans (`isLoadingFile` / `needsPermissionGrant` / `showDecryptModal` / `showDriveEmptyState` / `lastDriveCheckEmpty` / `selectedSource`) "with implicit exclusivity rules are workable today but heading toward unmaintainable." Rather than add `reconnectDriveFile` as a seventh independent mode, **this change resolves the TODO**: introduce the discriminated-union `viewState` the TODO describes and land `reconnect` as one of its variants.
   - **Scope:** this is now a committed part of the change, not optional. It expands the `LoadPodView` diff beyond the friction fix (it touches every existing mode), so the regression bar is higher — see Acceptance Criteria + Testing Plan, which require every pre-existing mode to behave identically after the refactor.
   - **Variant set — verified complete against the real template.** The template today is a two-level structure (verified LoadPodView.vue:612-1131): an **outer** `v-if="showDecryptModal"` / `v-else`, and inside the `v-else` an ordered inner chain `v-if="isLoadingFile"` → `v-else-if="needsPermissionGrant"` → `v-else-if="showDriveEmptyState"` → `v-else` (storage cards). So the **only** top-level render branches are: decrypt, auto-loading, permission-grant, empty, cards — five today, plus the new `reconnect`, giving the six-variant union `'auto-loading' | 'cards' | 'permission-grant' | 'reconnect' | 'decrypt' | 'empty'`. No current branch is dropped. Mapping (1:1 with today's flags):
     - **`showDecryptModal` (the `ref`) → `'decrypt'`.** Key the variant off `showDecryptModal` **alone**, exactly as the template does today (line 612). **Do NOT derive `decrypt` from `hasPendingEncryptedFile`** — that store getter is used inside the handlers (lines 166, 215) only as control flow to decide read-from-handle vs go-straight-to-decrypt; it is intentionally _not_ the render condition. Several flows stage a pending encrypted file but leave `showDecryptModal === false` so the **biometric** handoff can take over instead (the `checkBiometricForFamily` paths at lines 169-171, 187-189, 218-219, 262-263, 428-429, 564-565 emit `biometric-available` and never set `showDecryptModal`). Folding `hasPendingEncryptedFile` into the `decrypt` trigger would wrongly render the password panel during that handoff — a real regression. The `decrypt` input is the single `showDecryptModal` ref and nothing else.
     - `isLoadingFile` (initial auto-load **and** the in-flight spinner during permission-grant / file load) → `'auto-loading'`
     - `needsPermissionGrant` (local handle needs permission) → `'permission-grant'`
     - `showDriveEmptyState` → `'empty'`
     - the storage-source cards (default `v-else`) → `'cards'`
     - **new:** `reconnectDriveFile != null` → `'reconnect'`
   - **`lastDriveCheckEmpty` and `selectedSource` are NOT variants — leave them as-is.** Neither selects a top-level branch: `selectedSource` only toggles the local drop-zone _inside_ the `cards` branch (template line 971) and `lastDriveCheckEmpty` only dims the Drive card _inside_ `cards` (line 830). They are **sub-state of `'cards'`**, not modes. Do not fold them into the union — doing so would over-model the machine and risk regressing the "we already checked Drive" affordance. (The original TODO text lists them among the booleans to "consolidate," but the verified template shows they are render-local card state, not exclusive screens.)
   - **Precedence — corrected to match the real template (this is a behavior-preservation fix).** The precedence must reproduce today's render order exactly. Today's order is: outer decrypt wins over everything; then within the rest the inner chain is `isLoadingFile` → `needsPermissionGrant` → `showDriveEmptyState` → cards. Therefore the correct, behavior-preserving precedence is:

     **`decrypt > reconnect > auto-loading > permission-grant > empty > cards`**

     `reconnect` is inserted directly after `decrypt` (it fully replaces the cards like permission-grant/empty do, and a pending decrypt must still win over it — a staged envelope means we're already past loading). **`auto-loading` MUST stay ahead of `permission-grant` and `empty`**, exactly as `isLoadingFile` is the first arm of today's inner chain. This matters concretely: `handleGrantPermission()` sets `isLoadingFile = true` while the `needsPermissionGrant` prop is still `true` (LoadPodView.vue:209) — today the spinner correctly shows because `isLoadingFile` is checked first. An earlier draft of this plan documented `permission-grant > empty > auto-loading`, which would have **regressed** that case (the permission card would stay up instead of showing the spinner on click). The corrected order above eliminates that regression. (`isDriveLoading`, used by the empty-state retry/switch-account handlers, is a separate flag with its own in-card spinner and does not feed the chain, so `empty`'s position relative to `auto-loading` is not behavior-load-bearing — but it is placed after `auto-loading` for consistency with the verified inner-chain order.)

   - **Migration discipline:** do **not** rip out the booleans blindly. Preferred shape: keep the existing primitive refs (`isLoadingFile`, `showDecryptModal`, `showDriveEmptyState`) and the `needsPermissionGrant`/`reconnectDriveFile` props as the _inputs_, and derive `viewState` as a single `computed` with the explicit, documented precedence above so each existing transition keeps its current trigger and only the _rendering selection_ is consolidated. This is the lowest-risk shape **precisely because it does not move the write side**: the booleans are still set imperatively at exactly the same transition points as today, so the only thing that changes is the read/render selection. The rejected alternative — an explicit `viewState` ref assigned at each transition — would multiply the write sites (every handler that flips a boolean would also have to set the union correctly), re-introducing the same "remember to update it everywhere" failure mode this plan fights in `LoginPage` §2. Use the explicit-ref form only if some flag's semantics make a pure-derived computed genuinely impossible, and document why; in that case the `decrypt` input still stays `showDecryptModal`-only per the mapping note above. Either way the template reads `viewState` once.
   - Remove the `TODO(state-machine-refactor)` comment as part of this (the debt is paid, not deferred). Note in passing that the TODO's enumerated flag list is broader than the real branch set — call that out in the commit so the next reader knows `lastDriveCheckEmpty`/`selectedSource` were intentionally left as card sub-state, and that `hasPendingEncryptedFile` is deliberately not a `decrypt` input.

2. **`LoginPage` fallback-state duplication.** The `autoLoadPod` / `needsPermissionGrant` / `biometricDeclined` (+ `loadError` / `loadErrorProviderHint`) reset triplet is hand-written in ~9 places across `handleFamilySelected`, `activateFamilyForBiometric`, `handleLoadDifferentFile`, `handleNavigate`, and `handleBiometricFallback`. The new branch would copy it a tenth time, and the new `reconnectDriveFile` reset has to be remembered at every existing reset site or it leaks across navigations (req. 7's cross-talk risk).
   - **Recommended:** extract two tiny helpers — `resetLoadPodState()` (clears the whole intent group, _including_ `reconnectDriveFile`) and `enterGenericLoadFallback(hint)` (the four-line "show generic load-pod with error" block). Route the new reconnect branch and the existing fallbacks through them. This removes the "remember to reset the new ref everywhere" failure mode by construction and shrinks the diff's blast radius. Keep it to plain functions in the same component — no new abstraction layer.

3. **Single classification matcher (already covered in Layer 1).** Exactly one `/silent refresh failed/i` matcher, reused — never a second copy. Restated here because "two regexes that must agree" is the classic drift-into-unreliability trap.

4. **Keep `handleDriveFileSelected` reconnect-agnostic.** It is shared by the picker path and the new reconnect path. Do **not** add a `reconnectDriveFile`-aware branch inside it. The reconnect handler gets what it needs by reading `handleDriveFileSelected`'s **return value** (the `loadFromGoogleDrive` result, including the structured `reason`) — a clean, caller-neutral seam — and the reconnect-specific 404 recovery lives entirely in the reconnect handler (Layer 2 §4). Coupling shared load logic to one specific caller's mode is exactly the kind of hidden cross-talk that makes this view hard to reason about.

Net: the behavioral surface added is intentionally tiny (one prop, one panel, one thin handler, one store `reason` on each of `loadFromFile` and `loadFromGoogleDrive`). The sustainability work above is about **not amplifying** the two complexity hotspots the code already warns about — collapsing the genuine top-level branches into the documented `viewState` union (while leaving card-local sub-state alone, and keeping `showDecryptModal` as the sole `decrypt` input so the biometric handoff is preserved), de-duplicating the reset boilerplate, keeping the one matcher and the shared load method uncoupled, and classifying both the auth and the not-found failures **structurally in the store** rather than by matching error-message text in the view.
