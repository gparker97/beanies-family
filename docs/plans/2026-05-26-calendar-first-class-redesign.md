# Plan: Calendar first-class redesign — sticky command bar, full-width views, trips A+B, mobile agenda, smart-collapse strip

> Date: 2026-05-26
> Related issues: None — direct implementation (no GitHub issue requested)
> Plan file: `docs/plans/2026-05-26-calendar-first-class-redesign.md`
> Mockup: `docs/mockups/calendar-firstclass-2026-05-26.html` (6 screens; verified via Playwright screenshots)

## User Story

As a member of a beanie family, I want the family calendar to be the clear, full-width hero of the Activities page — with the date/period always visible and what's happening each day easy to read on phone and desktop — so the calendar feels like the first-class feature it is, instead of being pushed below a tall vacations block with a date header that scrolls away.

## Context

The Activities page (`src/pages/FamilyPlannerPage.vue`) currently renders, in order: a subtitle row (also containing the mobile member-filter dropdown and the Add button), a desktop `MemberChipFilter` row, a prominent full-width "Upcoming Vacations" `NookSectionCard` (a horizontally-scrolling/2-up grid of `VacationSidebarCard`s), a standalone `ViewToggle`, then the calendar. The period label ("May 2026") lives INSIDE each view via `CalendarNavBar`, is `text-lg`, and is not sticky. Result: on mobile the calendar starts a full screen down, and the date scrolls out of view. greg wants the calendar to be first-class: full-width, the main element, with the period always visible and each day's events clear.

A recent line of work (member-color chips via `MonthChip`/`useActivityChipClass`, the 2-week `WeekStripNav`, `MonthDayCard`) is the right foundation and is preserved and built upon.

Design decisions (all locked with greg before planning):

- **Ship as one cohesive change** (not phased).
- **Trips = A + B**: an always-on in-grid band on the trip's real dates (every view) PLUS a slim collapsible countdown "ribbon" in the command bar; the rich vacation card moves to tap-through detail.
- **Mobile month** becomes a roomy agenda (strong day anchor, empty days collapse, week dividers).
- **Mobile week** strip **smart-collapses** from 2 weeks to 1 week once the user scrolls into the timeline (reduced-motion-guarded), reclaiming day-timeline space while keeping the fortnight glance at rest.
- **Day view**: adopt the command bar + full-width only; its internal multi-member-column layout is unchanged.
- **Create activity**: keep an explicit labelled Add in the command bar on BOTH desktop and mobile (compact ＋ on mobile); keep the global `QuickAddFab`; keep tap-to-create in week/day.
- **CIG always wins** over the mockup. The mockup's arbitrary px sizes/radii are illustrative; the implementation uses the six-level Tailwind type scale (`text-xs`–`text-4xl`, min `text-xs`), rem-based sizing only (Large-text mode), squircle radii, soft shadows, Heritage Orange for today/active/family/Add (never Alert Red), member colors from `member.color`, vacation accent `var(--vacation-teal)`, Outfit for labels/values/nav and Inter for body/event text.

## Requirements

### Functional

1. **Sticky command bar.** A new page-level bar replaces today's subtitle row, mobile filter dropdown, desktop `MemberChipFilter` row, standalone `ViewToggle`, and the three per-view `CalendarNavBar` instances. It is `position: sticky; top: 0` within the `<main>` scroll container (`src/App.vue:1613-1614` — `class="flex-1 overflow-auto overscroll-y-contain p-4 md:p-6"`, which IS the scroll parent, confirmed) and contains:
   - **Period label** as the page hero (Outfit; `text-2xl` desktop, optionally `text-xl` mobile — both standard scale, NO `text-3xl`-custom px), e.g. "May 2026" / "25 – 31 May, 2026" / "Thursday, 28 May 2026". Note: the label STRINGS already exist via `formatMonthYear`, the week-range formatter in `useWeekNavigation.weekLabel`, and `formatDayLong` — reuse verbatim.
   - **Nav cluster**: prev / Today / next (reuse the SVG arrow markup + Today button styling currently in `CalendarNavBar.vue` — see §B; do not invent new icons).
   - **View toggle** (reuse `ViewToggle` unchanged — it already emits `update:activeView`).
   - **Member filter** (chips on desktop via `MemberChipFilter`; compact button-cluster on mobile — NOT a re-created `MemberFilterDropdown`; see Caveats).
   - **Add** button (reuse the existing gradient Add button markup from `FamilyPlannerPage`; labelled on desktop, compact ＋ on mobile; gated on `canEditActivities`).
   - **Day-view-only "Agenda" action** (relocated from `DailyCalendarView`'s `CalendarNavBar` `#actions` slot — the SVG + `t('planner.agenda')` markup moves verbatim; `DailyCalendarView` ALREADY emits `open-agenda`, confirmed at `DailyCalendarView.vue:44`).
2. **Trip ribbon (A).** A slim, collapsible row in the command bar listing `vacationStore.upcomingVacations` (existing getter — already sorted by start date, and filters on `endDate >= today` so it INCLUDES in-progress trips and excludes only fully-ended ones; confirmed at `vacationStore.ts:32-37`) as countdown pills (emoji + name + countdown via existing `tripTypeEmoji` / `daysUntilTrip`; `tripCountdownKey` is for the trip-type-appropriate countdown label — use it for the pill's `aria-label`/title, not the visible "{n}d"). Collapsible; collapse state persisted device-local via the existing guarded localStorage pattern (see §E — do NOT introduce a new abstraction). On mobile it collapses to a single summary pill ("✈️ {n} trips · {soonest} in {n}d") that expands the pill list on tap. Tapping a pill calls the page's existing `handleVacationClick(id)` (navigates to `/travel?vacation=id`). Hidden entirely (no row, no reserved height) when `upcomingVacations.length === 0`.
   - **Countdown copy must handle the in-progress / today case (real bug, not just missing data).** `daysUntilTrip(startDate)` returns the signed day-delta — it goes ZERO on the start day and NEGATIVE for a trip already underway (and `upcomingVacations` deliberately keeps in-progress trips, per the getter above). The pill must therefore branch: `> 0` → "{n}d"; `=== 0` → "today" (reuse `planner.today`); `< 0` → "now"/"on now" (new key, or reuse the existing in-progress copy that `classifyTripDay`/`tripCountdownKey` already model — prefer reusing an existing key over inventing a parallel one). Never render a bare negative "−2d". This branch lives inline in the ribbon and is unit-tested across the three ranges.
3. **Trip in-grid band (B).** Multi-day trips render as a connected band on their real dates in every view. **Week and Day all-day rows ALREADY render vacation spans** (`WeeklyCalendarView` `vacationSpans` with `gridColumn` placement + teal gradient; `DailyCalendarView` `activeVacations` spanning member columns) — reuse as-is, no change. The **month grid currently renders per-cell vacation chips** in `MonthDayCard` (a teal-tinted box showing the name only on `isStart`, an empty spacer otherwise) — enhance these into a visually connected band (rounded-left on `isStart`, rounded-right on the run's last covered cell, flat in the middle) within each week row, reusing the `CellVacation { isStart }` data already assembled in `CalendarGrid`'s `dateVacations` map (confirmed at `CalendarGrid.vue:149-167`). To round the END correctly the cell data needs an `isEnd` flag, added where `isStart` is computed (`CalendarGrid.vue:160-165`) — one line: `isEnd: dateStr === vEnd`. The `CellVacation` interface in `MonthDayCard.vue` must also gain the `isEnd: boolean` field (the type is exported and consumed by `CalendarGrid`). Tap → existing `vacation-click` emit → `handleVacationClick`.
4. **Demote the vacations block.** Remove the prominent `NookSectionCard` + `VacationSidebarCard` 2-up grid from the page body (`FamilyPlannerPage.vue:557-572`). The rich detail (progress, booking gaps via `bookingProgress`/`computeAccommodationGaps`) is reachable on tap-through to the trip's detail on `/travel`. Remove now-unused imports (`VacationSidebarCard` `:33`, `NookSectionCard` `:34`) if nothing else references them on the page.
5. **Full-width calendar.** The calendar card sits directly under the command bar and uses the full content width in all three views (already the case — the views are full-width; this requirement is mostly about removing the blocks above them).
6. **Mobile month = agenda.** On mobile, month view ALREADY renders as a vertical day-stack of `MonthDayCard`s (DOW + day number on the left, events on the right) WITH week-divider headers and past-aware "This week / Next week / Upcoming" labels (`CalendarGrid` `weekSeparatorIndexes` + `weekRangeByRow`, confirmed at `:320-352`). This requirement is therefore largely SHIPPED. The remaining delta is: (a) strengthen the today anchor (today already gets an orange left bar + wash + orange day number; confirm against mockup and adjust spacing only), and (b) collapse empty non-today days to a thin "nothing planned" line. **Empty days are currently NOT collapsed** (every current-month day renders a full card). Add a compact empty-state branch in `MonthDayCard` when the cell has zero timed/all-day/holiday/segment/vacation items and is not today — a single thin tappable row ("nothing planned", tap → `select-date`). Reuse the existing `dowLabel`/`cell.day` anchor; do not add a parallel layout.
7. **Mobile week smart-collapse.** The `WeekStripNav` shows 2 weeks at rest and collapses to 1 week (the focused week) once the user scrolls into the timeline; expands back near the top. Reduced-motion-guarded. (See §D — the collapse is driven by a small scroll-watch composable and the existing `<SmoothHeight>`.)
8. **Today always findable.** The command bar's "Today" returns to the current period AND triggers the active view's existing scroll-to-today/now behavior. The views ALREADY own the scroll routines: `CalendarGrid.scrollMobileToToday` (scrolls mobile to today's card), `WeeklyCalendarView`'s scroll-to-current-hour, `DailyCalendarView`'s scroll-to-now. The command bar must reach these — see §A for the mechanism (kept simple, no new scroll code in the page).
9. **Drill-in unchanged.** Clicking a day in month/week opens that day in Day view (existing `handleCalendarDateClick` → `focusedDate` + `activeView='day'`). Day view already watches `selectedDate`/`focusedDate`. Preserve exactly.

### Non-functional

10. **No silent failures.** Every fallible op (localStorage for ribbon collapse, scroll listeners, `matchMedia`, date parsing) is guarded with graceful fallback + a `console.warn`/`console.error` breadcrumb, MATCHING the existing proven patterns (`useTodoSort` read/write try/catch + `console.warn`; `useBreakpoint`'s `typeof window` + null-guarded `update()`; `useCalendarSlide`/SmoothHeight reduced-motion guard). User-facing failures use the existing `showToast('error'|'warning', …)` with warm Heritage-Orange messaging, never Alert Red (CIG: Heritage Orange is the alert colour for routine signals). The ribbon/strip degrade gracefully (ribbon stays expanded; strip stays at 2 weeks) rather than erroring.
11. **CIG compliance** (sizes/colors/typography/radii/casing). Type uses the six-level scale only (no `text-[Xpx]`; sub-`text-xs` ornament may use `text-[X.Xrem]` per the existing exception, as `MonthDayCard`/`WeekStripNav` already do). All new strings go through `uiStrings.ts` (`en` + `beanie`), zh regenerated via `npm run translate`. Reuse the existing `planner.*` keys verbatim where they already exist (confirmed present at `uiStrings.ts:4947-5013`: `planner.today`, `planner.agenda`, `planner.openAgenda`, `planner.allDay`, `planner.weekThis/Next/Last/Upcoming/Earlier`, `planner.view.month/week/day`, `planner.addActivity`, `planner.moreEvents`, `planner.subtitle`). Only genuinely-new copy (ribbon "trips", "nothing planned", the trip-summary line, and any in-progress/"dates TBD" copy not already covered by an existing key) needs new keys.
12. **No web/desktop regression to Day view internals**; desktop week grid behavior preserved; E2E (`page.goto`) unaffected. The `__tests__/CalendarGrid.test.ts` suite must be updated to the new prop contract (see Testing) — verify it doesn't assert on the removed internal `currentYear`/`currentMonth` state in a way the refactor breaks.

## Important Notes & Caveats

- **Week view is the highest-risk area, and the smart-collapse compounds that risk — contain it.** `WeeklyCalendarView` already juggles THREE date dimensions: the lifted reference date, the independent `stripAnchorDate`, and `selectedMobileDay` (all confirmed at `WeeklyCalendarView.vue:62-109`). The smart-collapse adds a FOURTH piece of view state (`collapsed`). To keep this component supportable, the collapse state must NOT be threaded into the existing nav/date logic at all — it is purely a render concern that gates whether week-2 of the strip is shown. Keep the `collapsed` ref isolated: it is read only in the template (`v-if="!collapsed"` on week 2, wrapped in `<SmoothHeight>`) and never participates in `advanceBoth`/`goToToday`/`labelFor`/`weekStripData`. Do not let it become a fifth input to any date computation. These interactions need explicit tests. Do not regress: the strip stays static when selecting a day pill (only prev/next/today moves the week via `advanceBoth`/`goToToday`), and the selected-day timeline is the mobile content. The strip's two-week label logic (`labelFor` in `WeeklyCalendarView.vue:531`) is INLINE there — not in `WeekStripNav`. See §D for where the shared helper actually comes from.
- **Do NOT re-create `MemberFilterDropdown.vue`.** A component by that exact name was DELETED for a silent-failure bug (its v-model setter ignored `toggleMember`'s `false` return on last-member deselect); `useMemberFilterChips` was created specifically to replace it (the bug + fix are documented in `useMemberFilterChips.ts:8-14` and Case 2 at `:46-60`). The mobile filter in the command bar must reuse `useMemberFilterChips`'s `onSelectAll`/`onSelectMember` handlers directly (the same handlers the desktop chips use) — NOT a v-model toggle. If the inline mobile dropdown markup (currently in `FamilyPlannerPage.vue:454-535`) is extracted to a presentational child for the command bar, name it something like `MemberFilterMobileMenu.vue`, give it the same prop/handler contract as `MemberChipFilter` (`isAllActive`, `isMemberActive`, `@select-all`, `@select-member`, plus `activeMemberNames`/`allLabel` for the button text), and keep it dumb (no store access, no v-model). The page instantiates `useMemberFilterChips()` ONCE and passes the handlers down to both the desktop chips and the mobile menu (it already does this for the desktop chips at `FamilyPlannerPage.vue:60-61`). This is a genuine de-duplication of the inline block, not a revival of the deleted component.
- **Do NOT delete `useCalendarNavigation.ts`.** It also exports `useTimeGrid` and `groupOverlapping`, which are consumed by `WeeklyCalendarView`, `DailyCalendarView`, AND `DayTimeline.vue` (confirmed via grep + read of the module: `useCalendarNavigation.ts:117-184`). Only the `useWeekNavigation`/`useDayNavigation` nav functions are candidates for consolidation — and even those expose `weekDays`/`weekLabel`/`getWeekStart`/`currentDay`/`dayLabel` that the week and day views (and the strip, via `useWeekNavigation(stripAnchorDate)` at `WeeklyCalendarView.vue:423`) depend on. See §A for the conservative consolidation that preserves these.
- **Controlled views must not call the _mutating_ nav functions of `useDayNavigation`/`useWeekNavigation` on a prop-derived `referenceDate`.** Today, `DailyCalendarView` does `const referenceDate = ref(...)` and feeds it to `useDayNavigation(referenceDate)`, whose `prevDay`/`nextDay`/`goToToday` MUTATE that ref (confirmed at `useCalendarNavigation.ts:30-38`); `WeeklyCalendarView` similarly owns the mutation via `advanceBoth`/`goToToday`. When the views become controlled (§A), `referenceDate` arrives as a prop — the views must consume `useDayNavigation`/`useWeekNavigation` ONLY for their read-only derivations (`currentDay`/`dayLabel`/`weekDays`/`weekLabel`/`getWeekStart`), and must NOT wire the mutating `prevDay`/`nextDay`/`goToToday`/`advanceBoth` to a prop-derived ref (that is the prop-mutation anti-pattern the one-way-data-flow invariant in §A forbids). Navigation intent flows view→page (emit) and command-bar→page (emit); the page is the sole writer of `referenceDate`. `WeeklyCalendarView`'s `advanceBoth` survives ONLY to keep its INTERNAL `stripAnchorDate`/`selectedMobileDay` in step when the page-owned `referenceDate` changes (via a watcher) — it no longer writes `referenceDate` itself.
- The `calendar-views` Help section is ALREADY stale (mentions "dots", the day "agenda sidebar", and a deleted "upcoming activities" list) — this change corrects it.
- The Nook's own vacation card (Help `vacation-card` section) is a DIFFERENT surface and is NOT touched.
- `QuickAddFab` remains global and present on this page (wired via `useQuickAddIntent` → `openAddModal`). The command-bar Add coexists deliberately.
- Keep `MonthChip`'s and `WeekStripNav`'s shipped chip anatomy/radii (`rounded-md`/`rounded-lg`); do not force a 24px squircle on tiny chips (the CIG squircle rule targets cards/buttons/modals/containers; chips/pills use `rounded-full`/`20px`/`rounded-md` and `MonthChip` is already compliant).
- The mobile month agenda, week separators, and past-aware week labels are **already shipped** in `CalendarGrid`/`MonthDayCard`. This plan must NOT re-implement them; the only month-agenda deltas are empty-day collapse (Req 6) and the connected vacation band (Req 3). Treat the rest as a verification-and-polish pass, not a rebuild.

## Assumptions

1. Lifting the canonical reference date into ONE page-level model (controlled views) is acceptable and preferred over the current mix (each view owns its own `referenceDate`; `CalendarGrid` owns `currentYear`/`currentMonth` — confirmed at `CalendarGrid.vue:45-46`). This also fixes the current "switching views resets to today" quirk and removes the `defineExpose`-based `headerSubtitle` plumbing (`FamilyPlannerPage.vue:201-215` currently reads `dayLabel`/`weekLabel`/`monthLabel` AND `activityCount` off view refs to build the subtitle — that whole indirection goes away when the page owns the label; see Assumption 6 for the count).
2. Today is read reactively via `useToday()` where new code needs "today". `useToday()` exposes BOTH `today: Readonly<Ref<string>>` (the date string) AND `startOfToday: ComputedRef<Date>` (the reactive start-of-today as a `Date`) — confirmed at `useToday.ts:36, 85-99`. The command-bar "Today" action and `usePlannerNavigation.goToday` reset `referenceDate` to `useToday().startOfToday.value` (NOT a hand-rolled `new Date()`), so the model stays consistent with the app-wide single source of truth and updates correctly across a midnight rollover. New pure helpers may take `today` as an injectable param (matching `classifyTripDay`/`relativeDayLabel` convention) for testability.
3. Empty mobile-month days collapse to a thin tappable "nothing planned" line (tap → `select-date` for that day → opens Day view), rather than being hidden, to keep the date column scannable. Today is never collapsed.
4. Ribbon collapse is a per-device cosmetic preference. It reuses the EXACT `useTodoSort`-style guarded read/write (try/catch + `console.warn` + validate-or-fallback) inline in the ribbon component or its own tiny composable — NOT a speculative generic abstraction (see §E).
5. The mobile trip summary pill expands the ribbon inline (consistent with the desktop collapse toggle) rather than navigating away.
6. **The per-view activity COUNT in the old subtitle ("23 activities") is being dropped, deliberately.** The current `headerSubtitle` shows label + count; the new command-bar hero shows the period label only (cleaner, matches the mockup). This is a conscious scope decision, called out so it is not mistaken for an accidental regression during review/QA. If greg wants the count retained, it surfaces as a small muted line under the label fed by a single page-level `computed` (NOT by reading `activityCount` off view refs — that indirection is exactly what we are removing). Recorded here so the decision is explicit rather than silent.

## Approach

### A. Unified navigation model (the architectural core)

Create `src/composables/usePlannerNavigation.ts` owning a single `referenceDate: Ref<Date>` plus `activeView: Ref<'month'|'week'|'day'>` (accepted as a passed ref so the page keeps one source of truth for the view). It returns `{ referenceDate, label, goPrev, goNext, goToday }` where `label` and the prev/next step switch on `activeView`:

- month → `formatMonthYear(referenceDate)`; step ±1 month via `addMonths`.
- week → reuse the shared `formatWeekRange` (see below); step ±7d via `addDays`.
- day → `formatDayLong(toDateInputValue(referenceDate))`; step ±1d via `addDays`.

`goToday` sets `referenceDate.value = useToday().startOfToday.value` (Assumption 2 — reactive, midnight-safe, single source of truth). All formatters (`formatMonthYear`, `formatDayLong`, the week-range formatter) and date utils already exist (confirmed in `utils/date.ts`) — this composable COMPOSES them; it does not re-implement label logic. To avoid two parallel week-range formatters, factor the `weekLabel` string-building (currently inline in `useWeekNavigation`, `useCalendarNavigation.ts:71-87`) out into an exported pure `formatWeekRange(first: Date, last: Date): string` in `useCalendarNavigation.ts`, and have both `useWeekNavigation.weekLabel` and `usePlannerNavigation`'s week label call it. `useWeekNavigation`/`useDayNavigation` stay (week view + the strip + day view consume `weekDays`/`currentDay` etc.); they are NOT deleted.

The three views become **controlled** — each accepts `referenceDate` as a `Date` prop (replacing the current `selectedDate?: string` semantics for navigation; `selectedDate`/`focusedDate` continue to drive day-cell highlighting and drill-in):

- `CalendarGrid`: replace internal `currentYear`/`currentMonth` refs (`:45-46`) with a single `computed` deriving `{ year, month }` from the `referenceDate` prop. Drop its `CalendarNavBar`, `prevMonth`/`nextMonth`/`goToToday` (the page model owns nav; note these currently emit `navigated` at `:361/371/380`). KEEP `scrollMobileToToday` (`:415-436`) and the swipe gesture (swipe still navigates — it emits `prev`/`next` to the page to advance the model). Remove the `monthLabel` from `defineExpose` (`:443`); keep `activityCount` in `defineExpose` ONLY if a consumer still reads it after Assumption 6 (default: drop it with the subtitle). The `headerSubtitle` plumbing is removed.
- `WeeklyCalendarView`: `referenceDate` becomes a prop; `stripAnchorDate`/`selectedMobileDay` stay internal (they are NOT the canonical date). Drop `CalendarNavBar`. The internal `advanceBoth` is repurposed: it is driven by a `watch(() => props.referenceDate)` that keeps `stripAnchorDate`/`selectedMobileDay` in step when the page navigates by week/today — it no longer writes `referenceDate` (the page owns it; see Caveats). Remove the local `prevWeek`/`nextWeek`/`goToday` nav-bar wiring; keep swipe (`useCalendarSlide`) emitting `prev`/`next` to the page. The `collapsed` smart-collapse ref is isolated render state (see Caveats + §D) — it does NOT enter `advanceBoth`/`labelFor`/`weekStripData`.
- `DailyCalendarView`: `referenceDate` becomes a prop (replacing the `selectedDate`-derived internal ref at `:57-58`). Use `useDayNavigation` only for its read-only `currentDay`/`dayLabel` (do NOT wire its mutating `prevDay`/`nextDay`/`goToToday` to the prop-derived ref — see Caveats). Drop `CalendarNavBar`; the `#actions` Agenda button markup moves to the command bar (`open-agenda` is ALREADY emitted — `:44`). Keep swipe emitting `prev`/`next`.

**Navigation by swipe / scroll-to-today without imperative ref calls.** Views emit `prev`/`next` (swipe) and the page advances the model. For "Today → scroll", the cleanest no-imperative approach: each view keeps its own scroll-to-today/now routine and runs it inside a `watch(() => props.referenceDate, …)` that fires the scroll when the new `referenceDate` is today/now. The command bar "Today" sets `referenceDate = startOfToday`, which (a) re-renders the period and (b) trips the view's watcher to scroll. This removes the current `calendarGridRef`/`weeklyViewRef`/`dailyViewRef` `defineExpose` reads from the page (those refs are read-only today — used for the subtitle label/count, never to call methods; confirmed at `FamilyPlannerPage.vue:131-133, 201-215`). Net: fewer template refs, one source of truth. Note: `scrollMobileToToday` internally guards on `today.getMonth()/getFullYear() === currentMonth/currentYear` — once `currentMonth`/`currentYear` become a `computed` off `referenceDate`, that guard keeps working unchanged (it compares the still-`new Date()` `today` against the derived month — pre-existing non-reactive `today` behavior is preserved; out of scope to change here).

**Feedback-loop guard (reliability).** The "swipe emits → page mutates `referenceDate` → view's `watch(referenceDate)` syncs `stripAnchorDate`" path is a one-way data flow (props down, events up) and must stay that way. The view must never mutate its own `referenceDate` prop, and the page must never write `referenceDate` back in response to a watcher it owns on the same ref. Keep `referenceDate` flowing strictly page→view; keep navigation intents flowing strictly view→page (emit) and command-bar→page (emit). This avoids the classic prop/watch ping-pong and keeps the data path traceable in one direction. Note as an explicit invariant in `usePlannerNavigation`'s doc comment.

`FamilyPlannerPage.vue` becomes the orchestrator: owns `usePlannerNavigation` (passing in `activeView`), member-filter state (`useMemberFilterChips`, already instantiated once at `:60-61`), modal state; renders `<CalendarCommandBar>` then the active view (full-width). `handleCalendarDateClick(date)` sets `referenceDate = parseLocalDate(date)` + `activeView='day'` + `focusedDate=date` (so the day highlight + drill-in both work). The existing `@navigated="focusedDate = null"` semantics (CalendarGrid emits `navigated` on its internal nav, `CalendarGrid.vue:361/371/380`) fold into the model — when the page-level `goPrev/goNext/goToday` run, the page clears `focusedDate`. The views no longer emit `navigated` (their internal nav is gone), so that emit + handler are removed.

### B. Command bar component

`src/components/planner/CalendarCommandBar.vue` — sticky, responsive, presentational. Props: `label: string`, `activeView`, `canAdd: boolean`, member-filter passthrough (`isAllActive`, `isMemberActive`, `activeMemberNames`). Emits: `prev`, `next`, `today`, `update:activeView`, `add`, `open-agenda`, `select-all`, `select-member`. Composes: period label (Outfit, `text-2xl`/`text-xl`), nav cluster (prev/Today/next — reuse `CalendarNavBar`'s SVG arrow + Today button markup verbatim, then `CalendarNavBar.vue` is deleted), `ViewToggle` (reused), member filter (desktop `MemberChipFilter`; mobile `MemberFilterMobileMenu` — the extracted-but-renamed dropdown, see Caveats), Add button (reused gradient markup, `v-if="canAdd"`), Agenda action (`v-if="activeView==='day'"`), and `<CalendarTripRibbon>` as a second row.

**Keep the command bar a layout/presentation shell, not a god component.** It composes existing child components and emits intents; it must NOT acquire store access, navigation math, or persistence logic. The trip ribbon is its OWN component (§C) with its own store read and its own collapse state — the command bar just slots it. This keeps each piece independently testable and stops the bar from becoming a 400-line catch-all. If the bar's template starts nesting more than ~2 levels deep around the filter/ribbon, prefer extracting another dumb child over inlining.

Sticky: `class="sticky top-0 z-…"` with the existing soft card shadow tokens; a `-mx-4 px-4 md:-mx-6 md:px-6` bleed so the sticky bar spans the `<main>` padding (`App.vue:1614` `p-4 md:p-6`) and its bottom shadow reads cleanly. Note the mobile app already reserves space via `AppHeader` (which is OUTSIDE `<main>`, so not sticky-conflicting), so `top-0` within `<main>` is correct.

Member filter de-duplication: desktop reuses `MemberChipFilter` (unchanged). The mobile dropdown currently duplicated inline in `FamilyPlannerPage` (`:454-535`) is extracted to `MemberFilterMobileMenu.vue` consuming the SAME `useMemberFilterChips` contract via props/emits (`isAllActive`/`isMemberActive`/`activeMemberNames`/`@select-all`/`@select-member`) — removing the inline duplication WITHOUT reintroducing the deleted component's name or its v-model bug. It owns only its open/close UI state.

### C. Trip ribbon + in-grid band

`src/components/planner/CalendarTripRibbon.vue` reads `vacationStore.upcomingVacations` directly (it's a store getter; no need to prop-drill — matches how the views read the store). Renders countdown pills with the existing `vacation.ts` helpers (`tripTypeEmoji(v.tripType, v.tripPurpose)`, `daysUntilTrip(v.startDate)` for the day-delta, `tripCountdownKey` for the accessible label). - **Smart-collapse:** add `src/composables/useScrollCollapse.ts`. Watches a scroll container's `scrollTop` (threshold-down to collapse, lower threshold-up to expand = hysteresis to avoid jitter), returns `{ collapsed: Ref<boolean> }`. Guard ALL DOM access exactly like `useBreakpoint`/`CalendarGrid.scrollMobileToToday`: `typeof window === 'undefined'` early-return; null-guard the resolved element; wrap `addEventListener`/`removeEventListener` in try/catch with `console.warn` on failure and degrade to never-collapsed. Clean up the listener in `onScopeDispose`. Honor `prefers-reduced-motion` (when reduced, `<SmoothHeight>` already no-ops the animation; the collapse still happens but instantly — acceptable and matches SmoothHeight's own contract).

  **Avoid the fragile `document.querySelector('main')` coupling.** A composable reaching out by tag selector into a layout element owned by `App.vue` is a hidden cross-component dependency: if the layout ever changes the scroll container (e.g. nested scroll regions, a wrapper div, two `<main>`s during a transition), the strip silently stops collapsing with no compile-time signal. (Note: `CalendarGrid.scrollMobileToToday` DOES currently use `document.querySelector('main')` at `:422` — that is pre-existing and out of scope; the NEW composable must not add a second such coupling.) Prefer one of these, in order of preference:
  1. **Pass the scroll target in.** `useScrollCollapse` accepts a `target: Ref<HTMLElement | null> | (() => HTMLElement | null)`. `WeeklyCalendarView` resolves the scroll parent from its OWN root via `el.closest('main')` (or walks to the nearest `overflow-auto` ancestor) inside `onMounted`, and passes that ref in. This keeps the DOM lookup anchored to a node the component actually owns, fails loudly (the ref is null → degrade to expanded + `console.warn`), and lets the composable be unit-tested with any element.
  2. If even `closest('main')` feels too layout-coupled, expose the scroll container as a `provide`/`inject` token from `App.vue` (`SCROLL_CONTAINER` injection key) and have the composable `inject` it. This makes the dependency explicit and refactor-safe.

  Default to option 1 (smaller change, no `App.vue` API surface). Either way, the composable itself does NOT hardcode `querySelector('main')`. `WeekStripNav` consumes `collapsed` (mobile only) to drop its 2nd week row, wrapped in `<SmoothHeight :revision="collapsed">` for the animated height change. Since `WeekStripNav` currently renders BOTH weeks always, the collapse is: render week 1 always, render week 2 only when `!collapsed`. Keep desktop unaffected (the strip is `v-if="isMobile"` in the week view already — confirmed — so `useScrollCollapse` only ever runs on mobile).
