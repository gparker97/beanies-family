# Plan: beanies-pre-plan skill — standardized requirements intake feeding beanies-plan

> Date: 2026-06-02
> Related issues: None — direct implementation
> Plan file: `docs/plans/2026-06-02-beanies-pre-plan-skill.md`

## User Story

As the sole developer of beanies.family, I want a standard requirements-intake step before `beanies-plan` so that every plan starts from complete, consistently-structured intent and the resulting plans are more correct and complete.

## Context

The `beanies-plan` skill (`.claude/skills/beanies-plan/SKILL.md`) produces high-quality plans through a mandatory 4-pass review discipline (initial draft → DRY/error-handling → sustainability → fresh-eyes). However, all four passes operate on the requirements they are handed. None can invent a missing requirement, an overlooked platform/surface, or an unstated constraint. The quality ceiling of any plan is therefore set _before_ Pass 1 runs, by the completeness of the initial prompt.

Today that initial prompt is ad-hoc — its quality varies, and `beanies-plan`'s Phase 1 ("Gather & Clarify") has to compensate with a clarifying-question round and by recording assumptions. A standardized pre-planning intake front-loads complete, well-structured requirements so Pass 1 begins from a fully-populated intent layer and the clarifying round shrinks to genuine gaps only.

This is internal tooling/process — no app code, no prod deploy. Empirical check done at plan time: no dev issue-tracker database exists in the Notion workspace (only "Post Tracker", which is launch/marketing content kept deliberately separate per the no-launch-content-in-repo rule confirmed in `CLAUDE.md`). So Notion mode requires creating a new database.

## Requirements

1. Define a CANONICAL field list (single source of truth) for pre-planning intake, organized into tiers: Required (always), Conditional (type-driven), Optional/recommended (blankable).
2. The canonical field list lives in ONE place — the **Canonical Field Table** in `.claude/skills/beanies-pre-plan/SKILL.md`. Every other rendering (the copy/paste template, the Notion schema, the field→`beanies-plan` mapping) is a _projection_ of that one table, generated by reading off its columns — never an independent re-listing. A field is added/renamed/removed by editing one row.
3. Provide a copy/paste markdown template: a sentinel-delimited `=== BEANIES PRE-PLAN ===` … `=== END PRE-PLAN ===` block rendering the canonical fields. The template is presented as derived from the Canonical Field Table (one label per row), not as a second hand-maintained list.
4. Build a NEW skill `.claude/skills/beanies-pre-plan/SKILL.md`, separate from `beanies-plan`, that hands off INTO `beanies-plan` without modifying it.
5. Support TWO entry modes:
   a. PASTE mode — user invokes the skill and pastes a filled template (or, if none provided, the skill emits the blank template for the user to fill). The skill parses it, validates completeness, asks only about blanks that genuinely block planning, then hands off to `beanies-plan` with the intent sections pre-populated.
   b. NOTION mode — "pre-plan the '<X>' issue" / a row reference. The skill queries the Notion issue-tracker DB (by title match or Status filter), maps row properties onto the canonical fields, validates, then hands off to `beanies-plan`.
6. Specify the Notion issue-tracker DB schema: properties mapped 1:1 to the canonical fields (read directly off the Canonical Field Table's "Notion type" column), plus a Status select for triage and a Plan File property for write-back. Document how the skill reads it via the connected `notion-beanies` MCP, including the required database→data-source resolution step.
7. In NOTION mode, after `beanies-plan` saves the plan, write the `docs/plans/…` path back to the row and advance its Status (close the loop) — with explicit handling if the write-back fails. Because `beanies-plan` only saves the file _after_ its own `ExitPlanMode` + user-approval + (possible) iteration loop, the write-back is a deferred post-save action, not a synchronous next step (see Assumption 6 and section C step 7).
8. The canonical field list maps cleanly onto `beanies-plan`'s existing Plan Document Format intent sections (User Story / Context / Requirements / Important Notes & Caveats / Assumptions) so the handoff is near-mechanical. This mapping is the "→ beanies-plan section" column of the Canonical Field Table, not a separate list.
9. Canonical field set: Title; Type (feature|bug|refactor|chore|other); Priority (critical|high|medium|low); Surfaces (platforms + app area); Objective (always); User story + UX/mockup flag (feature-only); Current/Expected/Repro (bug-only); Scope-do; Out-of-scope; Done-when; References; Open questions; Notes.
10. `beanies-plan` runs entirely UNCHANGED — the pre-plan skill's only output into it is a fully-populated initial prompt (the assembled template), supplied as `beanies-plan`'s initial input.

## Important Notes & Caveats

- Pre-prompt is PROBLEM-SIDE ONLY (what/why). It must never specify technical implementation/approach — `beanies-plan` owns the "how", and pre-specifying it would short-circuit the 4-pass design reasoning.
- Do NOT modify `beanies-plan`'s 4-pass internals or output format. Only feed it better input.
- Do NOT restate constraints already baked into `beanies-plan` Pass 2/3 or `CLAUDE.md` (DRY, no-silent-failures, MVO, rem-based text, i18n). Only NON-default constraints belong in the template's Notes field.
- Do NOT auto-generate acceptance criteria / testing plan / files-affected in the template — those remain `beanies-plan` outputs. "Done-when" seeds AC but is not AC itself.
- Do NOT put launch/marketing content in the Notion issue DB — it is product/issue tracking, a distinct DB from "Post Tracker". This is the `CLAUDE.md` no-launch-content-in-repo rule's mirror image in Notion: issue tracking and launch tracking stay in separate DBs.
- Low-friction is a hard requirement: the Required tier stays ~6 fields; everything else is conditional or blankable (`—`). If it becomes a 20-field form it will be abandoned.
- Type drives conditional requirements: feature → User story required; bug → Current + Expected + Repro required. Refactor/chore/other → only the always-required tier.
- **Single-source-of-truth is a maintenance hazard if violated.** The skill body MUST NOT contain the field list more than once. The template block and the schema table are written as "render the Canonical Field Table as X"; if any reviewer sees the same field names typed out in three places, that is the DRY defect to collapse before shipping.
- **Notion's newer API queries by `data_source_id`, not `database_id`.** A DB has one or more data sources; `API-query-data-source` and `API-post-page` need the data-source id, not the database id (confirmed in `launch-status` SKILL.md, which records both ids for the Karma DB: `Karma Building DB: <db-id> (data source: <ds-id>)`). The skill must resolve and record the data-source id at DB-creation time, otherwise NOTION mode silently queries nothing.
- **Cite the canonical file, not a symlink, for borrowed patterns.** The MCP-availability fallback pattern lives in `.claude/skills/start-session/SKILL.md` (step 5: "if `mcp__claude_ai_Google_Calendar__list_events` isn't available, the MCP isn't connected — note … run `/mcp` to authenticate"). `good-morning` is a _symlink_ to `start-session`. All citations in this skill must point at `start-session` (the real file), not `good-morning`, so the reference does not rot if the symlink is renamed or dropped.
- **Status vocabulary is a hidden second source of truth — pin it in one place.** The Status select's option names ("Backlog / Ready to plan / Planned / In progress / Done") are referenced by the schema, by NOTION mode's default query filter, and by the write-back transition. If they live in prose in three spots, a rename silently breaks the default filter (the query matches nothing) without any error. The skill must declare the Status vocabulary and the two transitions it cares about (the _query-for_ value and the _advance-to_ value) **once**, in the Notion-binding block, and every other mention refers back to it.
- **The write-back is asynchronous relative to `beanies-plan`, not a synchronous step.** `beanies-plan` ends Phase 2 by calling `ExitPlanMode`, then iterates with the user (Phase 3), and only _then_ saves the file (Phase 4). The plan path therefore does not exist at handoff time, and `beanies-plan` may even decline/abandon (user rejects the plan, never approves). The pre-plan skill must NOT block waiting for a path, must NOT construct a path, and must NOT assume a plan will be saved at all. It records the row id (the only thing it needs to carry across the boundary) and documents the write-back as an action to perform _when and if_ `beanies-plan` reports a saved path in the same thread. If the thread ends before a save (plan abandoned), the row simply stays at its pre-plan Status — no error, no half-written state.

## Assumptions

> **Review these before implementation.** Valid at planning time; may have changed.

1. The `notion-beanies` MCP server is connected and authenticated at skill-run time (verified available this session). It may be absent in headless/cron contexts — the skill must degrade gracefully using the established availability-check pattern (`.claude/skills/start-session/SKILL.md` step 5: if the `mcp__notion-beanies__*` tools aren't available, the MCP isn't connected — tell the user to run `/mcp` and fall back to PASTE mode).
2. SKILL.md is the right single source of truth (per the open question); the Notion DB schema is documented in SKILL.md but physically created in the Notion workspace at implementation time.
3. No dev issue-tracker Notion DB exists yet (verified) — implementation creates one named "beanies Issue Tracker" and records both its `database_id` and its `data_source_id` in the single Notion-binding block of SKILL.md (mirroring how `launch-status` records both for the Karma DB).
4. The user will usually paste a filled template; the skill should also support emitting a blank template on request.
5. **Handoff to `beanies-plan` is in-thread, not via an unverified cross-skill args call.** No existing skill in this repo invokes another skill with arguments via the Skill tool, so that path is unproven. The robust, simple handoff is: the pre-plan skill assembles the filled template and then continues in the same conversation by invoking `beanies-plan` (Skill tool / `/beanies-plan`) with the assembled template as its initial prompt. If the Skill-tool invocation can't carry the prompt as args, the skill presents the assembled block to the user and invokes `beanies-plan`, which captures the block as its Phase 1 "initial prompt" (which `beanies-plan` already stores verbatim). Either way the assembled block is the single artifact crossing the boundary — there is no second copy of the data.
6. **`beanies-plan` reports the saved plan path only at its Phase 4, after `ExitPlanMode` + user approval — and write-back is keyed off that report, not predicted.** `beanies-plan` saves to `docs/plans/YYYY-MM-DD-<slug>.md` only after the user approves the plan in plan mode (its Phase 3 → 4). The pre-plan skill does not predict or construct the path (the slug is `beanies-plan`'s to choose) and does not block on it. In NOTION mode, the only state it carries across the handoff is the **matched row id**, stated plainly in-thread at handoff ("NOTION write-back pending for row `<id>` once the plan is saved"). If and when `beanies-plan` reports a saved path in the same thread, the write-back runs against that row id. If the plan is abandoned or the thread ends before a save, no write-back occurs and the row keeps its pre-plan Status — this is correct, not a failure.

## Approach

### A. Canonical Field Table (the single source of truth, in SKILL.md)

ONE table. Every other rendering in this document and in the skill is read off its columns. Columns: Field | Tier | Applies to | Notion property (type) | → beanies-plan section.

| Field                | Tier           | Applies to | Notion property (type)                                | → beanies-plan section                   |
| -------------------- | -------------- | ---------- | ----------------------------------------------------- | ---------------------------------------- |
| Title                | Required       | all        | Title (title)                                         | plan Title                               |
| Type                 | Required       | all        | Type (select: feature/bug/refactor/chore/other)       | labeling                                 |
| Priority             | Required       | all        | Priority (select: critical/high/medium/low)           | labeling                                 |
| Surfaces — platforms | Required       | all        | Platforms (multi-select: web/PWA/iOS/Android/tooling) | Approach + DRY-pass targeting + labeling |
| Surfaces — area      | Required       | all        | Area (rich text)                                      | Approach + labeling                      |
| Objective            | Required       | all        | Objective (rich text)                                 | Context                                  |
| Scope-do             | Required       | all        | Scope (rich text)                                     | Requirements                             |
| User story           | Conditional    | feature    | User Story (rich text)                                | User Story                               |
| UX/mockup flag       | Conditional    | feature    | Mockup needed (checkbox)                              | Important Notes                          |
| Current              | Conditional    | bug        | Current (rich text)                                   | Context                                  |
| Expected             | Conditional    | bug        | Expected (rich text)                                  | Requirements                             |
| Repro                | Conditional    | bug        | Repro (rich text)                                     | Context / Testing seed                   |
| Out-of-scope         | Optional (`—`) | all        | Out of Scope (rich text)                              | Important Notes                          |
| Done-when            | Optional (`—`) | all        | Done When (rich text)                                 | seeds Acceptance Criteria                |
| References           | Optional (`—`) | all        | References (rich text)                                | Context / Related issues                 |
| Open questions       | Optional (`—`) | all        | Open Questions (rich text)                            | Assumptions + clarify loop               |
| Notes                | Optional (`—`) | all        | Notes (rich text)                                     | Important Notes                          |

Two Notion-only properties exist that are NOT canonical intake fields (they are workflow state, not intent): **Status** (select: triage) and **Plan File** (url: write-back target). They are documented in section D, not in the table above, precisely because they are not part of the paste template — keeping the table a clean 1:1 of intake intent. The three tiers are read straight off the **Tier** + **Applies to** columns — no separately-maintained tier list.

### B. Copy/paste template (a rendering of the table)

A `=== BEANIES PRE-PLAN ===` … `=== END PRE-PLAN ===` sentinel block whose lines are the **Field** column, in table order, with conditional rows grouped under `# Feature only` / `# Bug only` headers (read off the "Applies to" column), and `—` placeholders pre-filled on every Optional row (read off the "Tier" column). The skill body presents this as "render the Canonical Field Table as the block below" with the literal block shown once as the canonical output shape — it is the table projected, not a re-typed field list. The sentinel makes the hand-off unambiguous even pasted into a noisy message.

### C. The skill (`.claude/skills/beanies-pre-plan/SKILL.md`)

Sections mirroring the house style of existing skills (When to Invoke, Workflow, Rules). The workflow is deliberately a **flat, linear sequence of guarded steps** — each step has one job and one explicit failure outcome, so there is no deep branching to maintain.

- **When to Invoke:** `/beanies-pre-plan`, or phrases like "pre-plan this", "intake this issue", "prep a plan for X".
- **Workflow:**
  1. **Determine mode.** Filled template block → PASTE. Notion issue reference → NOTION. Neither/no content → emit the blank template and stop.
  2. **NOTION pre-check (fail loud, then fall back).** Confirm `mcp__notion-beanies__*` is available (pattern: `start-session` step 5). If not: tell the user to run `/mcp` or paste a template, then emit the blank template. Never run a query that will silently no-op.
  3. **PASTE — parse.** Parse the block into canonical fields. Sentinels present but body unparseable → say so explicitly + emit a fresh blank template; never guess field contents.
  4. **NOTION — resolve, query, capture.** Single canonical resolution path: recorded `data_source_id` → `API-query-data-source`; fall back to `API-retrieve-a-database` on `database_id` only if the recorded id is absent/rejected (and report it stale). Filter by title or Status _query-for_. Explicit failure handling for: DB/data-source not found; no row matches (list candidates); ambiguous (disambiguate). On success, map properties via the "Notion property" column and **capture the matched row id**.
  5. **Validate (shared, both modes).** Enforce Required tier + type-driven Conditional rows. One targeted question per genuinely blocking gap. No interrogation on Optionals. State which fields were auto-filled vs. left `—`.
  6. **Assemble + hand off.** Fill the template and hand off to `beanies-plan` in-thread. Confirm the handoff. In NOTION mode, announce: "NOTION write-back pending for row `<id>` once the plan is saved."
  7. **NOTION write-back — deferred post-save action (NOT synchronous).** Only when `beanies-plan` reports a saved `docs/plans/…` path: `API-patch-page` the captured row (Plan File = url, Status = _advance-to_). Failures: patch failed → surface error + exact values for manual entry; row id lost → ask for issue reference; no save ever reported → do nothing (row keeps pre-plan Status; never guess a path; never advance Status for an unsaved plan).
- **Rules:** problem-side only; never modify `beanies-plan`; never fail silently; low-friction; single source of truth (one-row edits); Status vocabulary + transitions only in the binding block; write-back deferred + conditional on an actual save.

### D. Notion binding + DB schema ("beanies Issue Tracker", created at implementation time)

The **single place** that holds (a) the runtime ids the skill needs and (b) the Status vocabulary. Nothing in sections A–C re-states these — they refer back here.

**Notion binding (recorded after DB creation):**

```
beanies Issue Tracker
  database_id:    <filled in at creation>
  data_source_id: <filled in at creation>   ← what API-query-data-source / API-post-page actually use
Status vocabulary: Backlog · Ready to plan · Planned · In progress · Done
  query-for value (NOTION mode default filter): "Ready to plan"
  advance-to value (write-back after planning):  "Planned"
```

**Schema.** Intake properties = the "Notion property (type)" column of the Canonical Field Table (one property per row — not re-listed here). Plus two workflow-only properties: **Status** (select, values = Status vocabulary) and **Plan File** (url). Read via `API-query-data-source` on the recorded `data_source_id` (default filter Status = _query-for_); write-back via `API-patch-page`; `API-retrieve-a-page` only if a property value is truncated.

## Testing Plan

1. Paste a fully-filled feature template → confirm handoff with no/minimal questions.
2. Paste a template missing a required field (e.g. Objective) → confirm a targeted question naming that field, not a full interrogation.
3. Invoke with no content → confirm the blank template is emitted.
4. Paste a block with sentinels but garbage body → confirm explicit "couldn't parse" message + fresh blank template (no silent guess).
5. Bug-type template missing Repro → confirm the type-driven conditional is enforced.
6. (Deferred, needs DB) NOTION mode happy path → data source resolved from recorded id, row read, row id captured, handoff with pending-write-back note; after `beanies-plan` saves, Plan File + Status (advance-to) written back.
7. (Deferred, needs DB) NOTION mode, recorded data-source id stale/absent → fallback re-resolves AND reports staleness.
8. (Deferred, needs DB) NOTION mode, DB not yet created → "DB not found" guidance, not a silent empty result.
9. (Deferred, needs DB) NOTION mode, ambiguous title → candidate list + disambiguation prompt.
10. (Deferred, needs DB) NOTION mode with MCP disconnected → explicit "run `/mcp`" message + graceful fallback to PASTE mode.
11. (Deferred, needs DB) NOTION mode, plan abandoned → NO write-back; row keeps pre-plan Status.
12. (Deferred, needs DB) NOTION write-back patch fails → error + exact Plan File url and target Status surfaced for manual entry.
13. (Deferred, needs DB) NOTION write-back, row id lost → skill asks for the issue reference rather than guessing.
14. Confirm `beanies-plan` runs its normal 4 passes (and its `ExitPlanMode` + approval gate) unchanged on the handed-off prompt.
