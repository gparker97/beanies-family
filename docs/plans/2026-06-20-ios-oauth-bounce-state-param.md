# Plan: iOS OAuth Onboarding — Carry Redirect State Through the OAuth `state` Param (Bounce-Tracking Fix)

> Date: 2026-06-20
> Related issues: None — direct implementation
> Plan file: `docs/plans/2026-06-20-ios-oauth-bounce-state-param.md`

> **No GitHub issue created.** This plan was approved for direct implementation. Full prompt history is embedded under `## Prompt Log`.

## User Story

As a new user creating (or joining) a family on **iOS Safari** (the primary onboarding surface until the native apps ship) **or** the installed PWA, I want to complete Google Drive sign-in without being bounced to a recovery screen, asked for my password twice, or frozen on "counting beans…" — so that onboarding just works, the first time, on every iOS surface.

## Context

### The confirmed root cause (three independent captures)

Onboarding fails on iOS Safari because **WebKit's bounce-tracking protection clears the initiating site's script-writable storage across the cross-site OAuth redirect.** `app.beanies.family → accounts.google.com → app.beanies.family` is a classified "bounce," and on return Safari has purged the `sessionStorage` written _before_ the redirect — **independently of the "Prevent Cross-Site Tracking" toggle** (it reproduces with that toggle OFF, in a plain Safari tab).

Diagnostics proved storage itself is NOT broken: every telemetry event — including at the exact instant of failure — reports `web_storage: ls=true,ss=true` (a fresh probe round-trips fine). Only the **pre-bounce** values vanish. Captured three ways: the `#beanies-errors` Slack alert (`oauth.redirectStateLost`, `ls=true,ss=true`), and two CloudWatch runs after the telemetry Lambda was updated.

### Why it breaks, precisely

`startRedirectAuth()` (`src/services/google/googleAuth.ts:1717-1755`) writes `sessionStorage['beanies_redirect_auth']` = `{ codeVerifier, returnPath, state? }` **before** redirecting to Google (`REDIRECT_AUTH_KEY` constant at `:1671`; the `setItem` is at `:1731-1734`). The bounce clears it. On return:

- `OAuthCallbackPage.vue:42` reads `beanies_redirect_auth` → **missing** → falls to the `code && !stateJson` branch (`:62-75`) → `reportError('oauth.redirectStateLost', critical)` → redirects to `/welcome?authError=storage` (the "browser blocked storage" toast).
- `completeRedirectAuth()` (`:1762-1809`) reads `REDIRECT_AUTH_CODE_KEY` + `REDIRECT_AUTH_KEY`; with the state key gone it short-circuits at `:1771` (`if (!code || !stateJson) return null`) → token exchange never runs → no token in memory.
- The create flow's round-2 sessionStorage blob (`PENDING_CREATE_KEY` + `PENDING_CREATE_PW_KEY`, `resumePaths.ts:114-126`) is **also** pre-bounce → cleared → `ResumePodSetup.vue:144` fast-path can't fire → the user falls into the generic recovery screen and re-enters the password (`app.onboardingZombieState`, `App.vue:859-895`). A race in the what's-new seed (`newFamilyFlag.ts` consumed by the `useNotifications` ready-watcher at `:104-128`) then auto-opens the drawer, and the half-finished-create state hangs on "counting beans…" (a silent init wedge — no telemetry, because it doesn't throw).

### The two architectural facts that make this simple

1. **The OAuth proxy Lambda is a CONFIDENTIAL client.** `infrastructure/lambda/oauth/index.mjs:147` adds `GOOGLE_CLIENT_SECRET` server-side to the token exchange. An intercepted authorization code is useless without that secret, so **PKCE is defense-in-depth, not load-bearing**, for this flow. (PKCE is _required_ for public clients; for a confidential server-side exchange it is optional — RFC 6749 §4.1 / RFC 7636.)
2. **ADR-026 already deems the web redirect CSRF-safe** ("same-origin top-level navigation is inherently CSRF-safe"; web carries no `state` today — `state` is native-only for deep-link CSRF, confirmed: `googleAuth.ts:1728` sets `state` only `if (isNative())`, and `buildAuthUrl:1512-1514` only appends it when present). So carrying _routing_ in `state` does not regress the CSRF posture.

Together: we can move the only thing that must survive the bounce — the **routing** (`returnPath` + a create-mode flag) — into the **OAuth `state` parameter**, which round-trips through Google in the URL and is immune to storage clearing, and **drop the client-stored PKCE verifier for the web redirect** (the confidential client secures the code). No datastore, no server-side session store, no auth redesign.

### What stays the same (deliberately)

- **The password is re-entered once.** ADR-026's accepted design is "no secrets stashed across the redirect — the user re-enters the password." The password is the family-data encryption secret; it genuinely cannot survive the bounce (storage is cleared) and must not go in a URL or server. The round-2 attempt to stash it in `sessionStorage` is exactly what's broken. **We revert to a single, clean password re-entry** — not the current double-password + zombie-screen mess.
- **The native (Capacitor) path is untouched.** Native storage is not bounce-cleared (the OS routes the deep-link back into the same WebView), and the native path already validates a CSRF `state` (`handleNativeAuthRedirect:1890`, validate block `:1890-1898`). It keeps working as-is; only the web redirect path changes.

## Requirements

1. **Web redirect carries routing through the OAuth `state` param, not pre-bounce `sessionStorage`.** `startRedirectAuth()` (web branch) encodes `{ returnPath, mode, v }` into the OAuth `state` parameter and does **not** write `beanies_redirect_auth` to `sessionStorage`. The value survives the Google bounce because it lives in the callback URL.
2. **Drop the client-stored PKCE verifier on the web redirect.** The web auth URL omits `code_challenge`; `completeRedirectAuth()` (web) exchanges the code with **no `code_verifier`**. The OAuth proxy Lambda must accept a token-exchange request **without** `code_verifier` (currently it 400s if absent — `index.mjs:130-132`).
3. **The authorization code reaches `completeRedirectAuth()` without depending on pre-bounce storage.** The code arrives in the callback URL _after_ the bounce; `OAuthCallbackPage.vue` reads `state` (routing) + `code` from the URL and hands the code to the return leg via the existing `REDIRECT_AUTH_CODE_KEY` sessionStorage hop (post-bounce, same-origin — see Caveats for the hardening option).
4. **One clean password entry on create-resume — remove the broken round-2 stash.** Delete the `PendingCreate` password-stashing path entirely; route the return straight into the resume-setup "finish creating your family" step via the `state` `mode`, where the user enters the password **once**. No second password prompt, no zombie detour.
5. **The "counting beans…" hang can never strand the user.** Add an onboarding init **watchdog** that reuses the existing `withTimeout` util and the existing `initError` recovery overlay: if init has not settled within a bounded interval on an onboarding route, set a recoverable `initError` and fire `reportError('app.onboardingStallTimeout', …)` so the hang becomes visible telemetry instead of a silent freeze.
6. **The what's-new / notifications drawer must not auto-open mid-onboarding.** Harden the `newFamilyFlag` → `useNotifications` ordering so a brand-new family can never auto-open the drawer during the create/resume flow.
7. **Accurate diagnostics copy.** The `oauth.redirectStateLost` message and the user-facing toast must stop blaming "Private Browsing" — the cause is bounce-tracking storage clearing, which the fix removes from the critical path. Keep the surface for genuinely malformed callbacks with an accurate message.
8. **Works on Safari tab AND installed PWA AND all redirect-auth entry points.** Because the fix lives in the shared `startRedirectAuth`/`completeRedirectAuth`/`OAuthCallbackPage` layer, it must fix create, **join**, and Settings → Reconnect uniformly, on both iOS surfaces. **This means every one of the five `startRedirectAuth` call sites must be updated to supply a `mode`** (see Change 1 — the mode argument is made _required_ so the compiler enforces full coverage).
9. **No regression to the native path, the popup path (non-iOS desktop), or the silent-refresh path.**

## Important Notes & Caveats

- **`state` is non-secret and transits Google + URLs/logs.** Put ONLY non-sensitive routing in it: `returnPath`, a `mode` enum, and a small version tag `v`. **Never** put the password, tokens, family key, email, or the family/owner name in `state`. The owner name and family name are re-collected on the resume screen (they were always re-collected pre-round-2), so they don't need to ride in `state`.
- **DO NOT add a third base64url implementation.** The codebase already has TWO: `bufferToBase64url`/`base64urlToBuffer` in `src/utils/encoding.ts` (`:30-42`) and an inline copy in `src/services/google/pkce.ts` (`:8-15`). The new codec MUST reuse the **identical** URL-safe replace-chain (the JSON path is just `btoa(JSON.stringify(...))` → `.replace(/\+/g,'-').replace(/\//g,'_').replace(/=+$/,'')`, mirroring exactly `encoding.ts:31`; decode reverses it and restores padding exactly like `base64urlToBuffer` at `:36-41`) — see Change 1 for the exact reuse contract. Keep `state` well under the ~512-byte practical limit Google tolerates.
- **Validate on return: missing/malformed/old-version `state` is a genuine, reported error — never a silent drop.** `decodeRedirectState` returns `null` (never throws) on any failure; every `null` at a call site routes to an actionable surface AND reports.
- **Backward/transition compatibility (TIME-BOXED, see Change 7 for the enforced removal).** In-flight redirects started by the _old_ build still carry `beanies_redirect_auth` in storage (when it survives). Both `OAuthCallbackPage` and `completeRedirectAuth` must handle **both** transports for **exactly one release**: prefer the new `state`-param path; fall back to the legacy `sessionStorage` path when a legacy state is present. The Lambda must accept requests **with or without** `code_verifier` so old (verifier-present) and new (verifier-absent) clients both work during rollout. The legacy fallback is dead weight by design and is removed on a _scheduled, test-enforced_ basis (Change 7) so it cannot silently rot.
- **Lambda deploy is separate (Terraform).** The `code_verifier`-optional change ships via a **targeted** `terraform apply -target=module.oauth.aws_lambda_function.oauth` after reviewing the one-resource plan. **Deploy the Lambda first** (accept-without-verifier is backward-compatible), then ship the Vue app that stops sending the verifier — so there's no window where a new client sends no verifier to an old Lambda that still requires it.
- **CSRF posture is explicitly preserved, not regressed.** Web stays same-origin-top-level-navigation (ADR-026's accepted basis); `state` adds routing only. A future server-HMAC-signed `state` (the Lambda already holds env secrets) is the belt-and-suspenders option — **out of scope here**.
- **PKCE drop is a deliberate, documented security decision**, sound _because_ the proxy is a confidential client. Do not drop PKCE on any path where the token exchange is NOT brokered by the confidential proxy (there is none today). **This rule must outlive this plan** — it is recorded as a durable invariant in three places (Change 1 doc-comment, the new ADR, and a unit test on the Lambda), so a future maintainer adding a public-client path can't quietly inherit no-PKCE (Pass 3, finding d).
- **Native path is out of scope and must not be refactored "for symmetry."** Critically, the native completion is a **separate entry path** — `handleNativeAuthRedirect()` validates its CSRF `state`, writes `REDIRECT_AUTH_CODE_KEY` + keeps `REDIRECT_AUTH_KEY`, then calls the shared `completeRedirectAuth()` (`googleAuth.ts:1911-1913`). So the "triple branch" people fear is really only a **two-way branch inside `completeRedirectAuth`** (legacy-stash-present vs. new-web-no-stash); native simply _produces_ a legacy-shaped stash and rides the legacy branch. Keep the web/legacy branch explicit and commented, and document this so a reader doesn't hunt for a third arm that isn't there (Pass 3, finding a). **Native still calls `startRedirectAuth` from inside that function's own native branch — so when `mode` becomes a required param (Change 1), the native branch keeps writing its `codeVerifier`+CSRF-`state` stash and simply ignores `mode` for routing (it carries `returnPath` in its stash, not the OAuth `state`). The `mode` value passed for native is immaterial but must be supplied to satisfy the signature; pass the create-flow's actual mode through unchanged (it's already the right value at every native-reachable call site).**
- **Do not store the password anywhere to "improve UX."** The single re-entry is the correct, secure outcome on iOS redirect auth.
- **The freeze is a _hang_, not a throw** — the watchdog (Req 5) is the only thing that will capture/recover it. The nested timeouts must be **ordered, not coincidental** — see Change 6's centralized constants (Pass 3, finding c).
- **`mode` threading touches five call sites, not two (Pass 4, finding d).** `startRedirectAuth` is called directly from FIVE places — verified by grep: `connectStorage.beginDriveAuthRedirectIfNeeded` (`:73`), `useGoogleReconnect.ts:42`, `usePickBeanpodFile.ts:87`, `SettingsPage.vue:327`, and the native branch inside `startRedirectAuth` does not re-call itself but the function is _entered_ from `beginDriveAuthRedirectIfNeeded`, `useGoogleReconnect`, `usePickBeanpodFile`, and `SettingsPage`. `beginDriveAuthRedirectIfNeeded` is in turn reached from `connectDriveStorage` (`:147`, always create-flow), the `syncStore` resume probe (`:2355`, create-flow), and the `syncStore.beginDriveAuthRedirect` delegate (`:2557-2562`, used by `LoadPodView` → join/load). Making `mode` a **required** parameter on `startRedirectAuth` (and a required pass-through on `beginDriveAuthRedirectIfNeeded` + `syncStore.beginDriveAuthRedirect`) forces the TypeScript compiler to flag every unmigrated caller — so no call site can be silently missed. See Change 1 for the per-site mode mapping.

## Assumptions

> **Review these before implementation.** Valid at planning time (2026-06-20); may have changed.

1. Current `main` tip is `9ab3d971`. The oauth Lambda live env already has `NATIVE_REDIRECT_URIS` + `https://localhost`; only `code_verifier`-optional is new.
2. The OAuth proxy remains a confidential client and all token exchanges are brokered by it. If a public-client path is ever added, PKCE must return for that path (enforced as a durable invariant — Caveats + Change 1 + ADR + Lambda test).
3. Google echoes `state` unchanged on the callback and tolerates a base64url(JSON) payload of the size we use. (Standard OAuth; verify in the manual iOS test.)
4. The post-bounce callback→returnPath leg (same-origin) reliably preserves `sessionStorage` (greg's runs showed the `code` _was_ available on return; only pre-bounce state was lost). If this ever proves false, switch the code to URL-fragment passing (Caveats).
5. `shouldUseRedirectAuth()` correctly identifies all iOS/iPadOS surfaces; the fix applies wherever it returns true.
6. Re-entering the password once on the resume screen is acceptable UX on iOS. Zero re-entry is impossible without persisting a secret across the bounce.
7. **(Pass 4) Every `startRedirectAuth` caller's `returnPath` is already a same-origin relative path** — the reconnect/pick callers pass `${window.location.pathname}${window.location.search}` (`useGoogleReconnect.ts:41`, `usePickBeanpodFile.ts:86`, `SettingsPage.vue:327`), which begins with a single `/`, so the new `decodeRedirectState` same-origin `returnPath` validation accepts them unchanged. Verified at planning time.

## Approach

The fix is at the **shared redirect-auth layer**, so create / join / reconnect all benefit from one change. Seven coordinated changes.

### Change 1 — `state`-param routing codec + `startRedirectAuth` (web) + `mode` threading — new `src/services/google/redirectState.ts` + `src/services/google/googleAuth.ts` + all five callers

- **New `src/services/google/redirectState.ts`** — a tiny, pure, well-tested codec, the single source of truth imported by `startRedirectAuth`, `completeRedirectAuth`, and `OAuthCallbackPage`:
  - `export type RedirectMode = 'create' | 'join' | 'reconnect';`
  - `export interface RedirectStatePayload { returnPath: string; mode: RedirectMode; v: 1; }`
  - `export const REDIRECT_STATE_VERSION = 1 as const;` — the single literal; `encode` writes it, `decode` compares against it. No magic `1` scattered.
  - `encodeRedirectState(p): string` — `btoa(JSON.stringify(p))` then the **exact** URL-safe transform already used in `encoding.ts`/`pkce.ts` (`.replace(/\+/g,'-').replace(/\//g,'_').replace(/=+$/,'')`). DRY note: do **not** reach for `bufferToBase64url` (that takes a buffer); the string path is a one-liner that reuses the identical replace-chain — keep the codec self-contained so the routing contract lives in one file, and add a code comment pointing at `encoding.ts:31` as the canonical replace-pattern so a future reader doesn't think it's a third divergent impl.
  - `decodeRedirectState(raw: string | null): RedirectStatePayload | null` — restore padding + reverse-replace (mirroring `base64urlToBuffer` at `encoding.ts:36-41`), `JSON.parse` inside a `try`, validate `v === REDIRECT_STATE_VERSION`, `mode ∈ {create,join,reconnect}`, and `returnPath` is a non-empty **same-origin relative path** (must start with a single `/`, NOT `//` — reject absolute/protocol-relative to prevent an open-redirect via a malicious echoed `state`). **Returns `null` on any failure; never throws.** The same-origin check is a genuine new security boundary (the old transport never put `returnPath` in a URL), so it must be explicit and unit-tested.
  - **Forward-compat contract (Pass 3, finding b), as a doc-comment at the top of the file:** `v` is an **exact-match** gate, not a `>=`. A payload whose `v` is unknown to the running build (e.g. a future `v:2` echoed back to a not-yet-updated tab) decodes to `null` → reported "state lost" → user retries → the retry is minted by whatever build is now serving them. This is the _correct_ conservative behavior: an old client must NEVER best-effort-parse a newer shape it doesn't understand. To add a field later you bump to `v:2` and — for one release — `decode` accepts **both** `1` and `2` (a small allow-set), exactly mirroring the legacy-transport one-release window. Until then there is a single version and `decode` branches on nothing but equality, so there is no speculative version-dispatch machinery to maintain.
- In `startRedirectAuth(returnPath, loginHint?, mode: RedirectMode)` — **`mode` is a required positional parameter** (see the mode-mapping below; required so the compiler flags every caller):
  - **Web branch** (`!isNative()`): set the auth URL's `state` = `encodeRedirectState({ returnPath, mode, v: REDIRECT_STATE_VERSION })`; build the auth URL **without** `code_challenge`/`code_challenge_method`; **do not** call `sessionStorage.setItem(REDIRECT_AUTH_KEY, …)`.
  - **Native branch**: unchanged (keeps `codeVerifier` + its CSRF `state` + sessionStorage; its storage survives). `mode` is accepted but not used for routing on native (native carries `returnPath` in its own stash); it is supplied only to satisfy the now-required signature.
  - Add a short doc-comment on the web branch stating the **PKCE-drop invariant** verbatim: _"No `code_verifier` here is safe ONLY because the confidential OAuth proxy adds `client_secret` server-side. If any token exchange ever bypasses that proxy, PKCE MUST return on this path."_ (Pass 3, finding d — durable in-code.)
- `buildAuthUrl` must conditionally omit `code_challenge`/`code_challenge_method` (they're currently always set at `:1506-1507`). Make the PKCE challenge optional (`codeChallenge?: string`) and append the two challenge params only when present, so the web-redirect call builds a no-challenge URL while popup/silent/native keep theirs. Single builder, no duplicate URL assembly. (The current signature is `buildAuthUrl(clientId, codeChallenge, prompt, loginHint?, state?)` at `:1494-1500`; the popup/silent/native callers always pass a challenge, so making it optional is backward-safe.)
- **Thread `mode` from ALL FIVE call sites (Pass 4, finding d — the prior draft addressed only two).** Making `mode` required surfaces each one at compile time. The mapping:
  | Call site                                                                         | File:line                  | `mode`                     |
  | --------------------------------------------------------------------------------- | -------------------------- | -------------------------- |
  | `connectDriveStorage` → `beginDriveAuthRedirectIfNeeded(RESUME_SETUP_PATH, …)`    | `connectStorage.ts:147`    | `'create'`                 |
  | `syncStore` resume-probe → `beginDriveAuthRedirectIfNeeded(RESUME_SETUP_PATH, …)` | `syncStore.ts:2355`        | `'create'`                 |
  | `syncStore.beginDriveAuthRedirect` delegate (LoadPodView / join+load)             | `syncStore.ts:2557-2562`   | caller-supplied (`'join'`) |
  | `useGoogleReconnect` redirect                                                     | `useGoogleReconnect.ts:42` | `'reconnect'`              |
  | `usePickBeanpodFile` redirect                                                     | `usePickBeanpodFile.ts:87` | `'join'`                   |
  | `SettingsPage` reconnect                                                          | `SettingsPage.vue:327`     | `'reconnect'`              |
  - Add a `mode` parameter to `beginDriveAuthRedirectIfNeeded` (`connectStorage.ts:56`) and to its `syncStore.beginDriveAuthRedirect` delegate (`syncStore.ts:2557`), threading it straight through to `startRedirectAuth`. `connectDriveStorage` (`:138`) hard-codes `'create'` at its single redirect call (`:147`) — correct for both its callers (`CreatePodView.vue:311` and `ResumePodSetup.vue:451` are both the create/finish-create flow). The `LoadPodView` redirect (via `syncStore.beginDriveAuthRedirect`) passes `'join'`.
  - **Do NOT re-derive `mode` from `returnPath` string-matching** — pass it explicitly so the codec input is unambiguous. The `mode` is mostly used today as a routing/telemetry discriminator on return (all three modes currently land on a resume/recovery surface via their `returnPath`); it is carried in `state` now so the return leg and future logic can branch on it without re-parsing the path.

### Change 2 — `OAuthCallbackPage.vue` reads `state` from the URL — `src/pages/OAuthCallbackPage.vue`

- In redirect mode, read `code` + `state` from `window.location.search` (it already reads `code`/`error` at `:19-21`).
- New precedence (all branches wrapped so nothing throws to a blank page):
  - **New path** — `decodeRedirectState(stateParam)` returns a payload → `sessionStorage.setItem(REDIRECT_AUTH_CODE_KEY, code)` (post-bounce, same-origin, survives) and `window.location.href = payload.returnPath`. No dependency on `beanies_redirect_auth`.
  - **Legacy fallback** — no decodable `state`, but `sessionStorage['beanies_redirect_auth']` is present and parses → keep the existing legacy branch (`:47-56`) for one release (in-flight old-build redirects).
  - **Genuinely lost** — `code` present, no valid `state`, no legacy storage → keep the `reportError('oauth.redirectStateLost', critical)` branch (`:62-75`) but with **accurate copy** (Change 7) and route to an actionable surface. The `sessionStorage.setItem` write itself is wrapped in `try/catch`; a throw here is reported (not silently swallowed) and routed identically to "state lost," since a code-in-hand we can't forward is a hard onboarding block.
- Popup (`:23-28`) + iframe (`:30-34`) branches unchanged. The inline `sessionStorage.getItem` for the legacy read (`:41-45`) keeps its `try/catch` (a throw is treated as "legacy absent," then falls to the new-path/lost logic).
- **Keep this precedence as a flat `if/return` ladder, not nested `try`-in-`if`-in-`if`.** Each transport is one guarded block that either forwards-and-returns or falls through to the next — the current file is already written this way and the new path slots in at the top; do not deepen the nesting (Pass 3, simplicity).

### Change 3 — `completeRedirectAuth` exchanges without a verifier (web) — `src/services/google/googleAuth.ts` + `src/services/google/oauthProxy.ts`

- The function already has a **single exchange chokepoint** (`exchangeCodeForTokens` at `:1782`) and a single commit chokepoint (`commitAcquiredToken` at `:1799`) — keep both. The only branch needed is how the verifier is sourced. **There are exactly two arms** (Pass 3, finding a — there is no third):
  - Read `code` from `REDIRECT_AUTH_CODE_KEY`. Read `REDIRECT_AUTH_KEY` **only** to detect a legacy in-flight redirect (this same key is _also_ how native hands off — native is not a separate arm here, it deliberately produces a legacy-shaped stash with a `codeVerifier`).
  - **Legacy/native present** (`beanies_redirect_auth` parses with a `codeVerifier`): exchange **with** `state.codeVerifier`. Branch explicit + commented as "legacy web (one release) OR native hand-off."
  - **No stash** (the new web path — code present, no legacy state): exchange with **no** `code_verifier`.
  - Guard the early-return: today `:1771` returns `null` when _either_ key is missing. New logic returns `null` only when `code` is absent; a present `code` with no legacy state is the new happy path, not a no-op.
- `exchangeCodeForTokens` param type (`oauthProxy.ts:93-98`): make `codeVerifier?: string` optional and only add `code_verifier` to the POST body (`:104-109`) when present (no empty-string sends). This is a one-line change to the body object (spread-in conditionally) — `fetchWithTimeout`, `safeJsonParse`, and error handling at `:119-128` are untouched and already report non-2xx with the Google `error_description`.
- Scope-validation (`DriveConsentDeniedError`, `:1789-1794`), `commitAcquiredToken`, and timeout handling all unchanged.

### Change 4 — OAuth proxy Lambda: `code_verifier` optional — `infrastructure/lambda/oauth/index.mjs` (+ tests, SPEC.md)

- In `handleTokenExchange`, remove the hard `code_verifier` required-field check (`:130-132`); build the Google `URLSearchParams` and append `code_verifier` **only when present** (currently unconditional at `:144`). All other validation (`code` `:129`, `redirect_uri` allowlist `:138`, `client_id` `:136`) unchanged. The existing `!googleRes.ok` pass-through (`:159-160`) already forwards Google's 4xx body verbatim to the client — no silent failure to add.
- **Add a durable comment at the dropped check** recording WHY verifier-less is acceptable: _"`code_verifier` optional because THIS proxy is a confidential client (adds `client_secret` below at `:147`). Do not relax any other field — and if a public-client path is ever added, it must send + we must require PKCE."_ (Pass 3, finding d — the security reasoning lives at the exact line a future maintainer edits.)
- Update `infrastructure/lambda/oauth/SPEC.md` + `__tests__` to reflect optional `code_verifier`. Add an assertion that `client_secret` is still always attached (so "optional verifier" can never be misread as "optional secret").
- **Deploy first** via targeted `terraform apply` (backward-compatible).

Keep `RESUME_*`, `isPodlessRecoveryQuery`, and the `ResumeSetupReason` helpers (`:18-87`).
  - **Coherence check (Pass 3, finding e):** what remains is a single, well-scoped module — the `RESUME_*` path constants + `isPodlessRecoveryQuery` (routing tokens for the resume/load surfaces) and the `ResumeSetupReason` consume-once hint (`drive-consent`). These are _all_ "how LoginPage resumes after an OAuth return" concerns — the module's stated purpose in its own header comment (`:1-16`). ### Change 6 — Onboarding watchdog + what's-new race hardening — `src/App.vue`, `src/composables/useNotifications.ts`

**Nested-timeout ordering (Pass 3, finding c) — make the layering deliberate, not coincidental.** There are now four time bounds on the init/auth path, and they must form a strict nesting (innermost shortest) so an inner layer always fires first and the outer layers are pure safety nets, never racing the inner one:

| Layer                       | Where                                                                                             | Current value | Role                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------- | ------------- | -------------------------------------------------- |
| fetch abort                 | `oauthProxy.fetchWithTimeout` (`:52`, `FETCH_TIMEOUT_MS`)                                         | 15s           | one network round-trip                             |
| `completeRedirectAuth` race | `App.vue:783` `withTimeout`                                                                       | 20s           | the whole exchange (one fetch + commit)            |
| data-load skeleton dismiss  | `App.vue:961` `setTimeout` (`INIT_TIMEOUT_MS`, fires at `:963`, clears `isLoadingData` at `:967`) | 30s           | dismiss skeleton, keep loading in bg               |
| **init watchdog (new)**     | `App.vue` outer init                                                                              | **35s**       | last-resort: flip `isInitializing` false + recover |

- **Centralize these four as named constants together** (e.g. an `INIT_TIMEOUTS` block with a one-line comment: _"strictly increasing; each layer is the safety net for the one above — do not reorder or collapse"_). Today they're scattered as inline literals (`15_000` in oauthProxy, `20_000` at `App.vue:785`, `30_000` at `App.vue:961`); co-locating the App.vue ones (and referencing the oauthProxy ceiling in the comment) makes the invariant auditable and stops a future tweak from accidentally setting the watchdog _below_ the data-load timeout, which would make it fire on a slow-but-healthy load (the exact "confusing failure mode" to avoid). The watchdog value is asserted `> dataLoad > completeRedirectAuth > fetch` by a unit test. _(Note: the 15s fetch ceiling lives in a different module — `oauthProxy.ts` — so the App.vue `INIT_TIMEOUTS` block documents it as the assumed innermost bound rather than owning it; the test imports `FETCH_TIMEOUT_MS` to assert the full chain.)_
- **Watchdog (reuse, do not hand-roll):** App.vue already imports `withTimeout` (`:38`), already has the `initError`/`initErrorDetail` recovery overlay + `handleReload` (catch sets `initError.value` at `:1139`; overlay template at `:1379` onward), and already wraps `completeRedirectAuth` in a 20s `withTimeout` (`:783-787`) and the data-load in a 30s `setTimeout` that only clears `isLoadingData`, **not** `isInitializing` (`:963-967`). The gap: if the init chain wedges _before_ reaching the data-load timeout (e.g. `completeRedirectAuth` resolves but a downstream `switchFamily`/`reload` hangs), `isInitializing` can stay `true` with no escape — the "counting beans" freeze.
  - Wrap the **outer** init body (or the longest-pole awaited segment) in `withTimeout(initWork, INIT_TIMEOUTS.watchdog, '…')`. On rejection-by-timeout, run the **existing** failure path: set `initError.value = t('app.initError.stalled')`, `initErrorDetail.value = initBreadcrumbs.join('\n')`, flip `isInitializing`/`isLoadingData` false, and `reportError({ surface: 'app.onboardingStallTimeout', severity: 'critical', context: { route_path: route.path } })`. No new timer system, no new overlay — it converges on the same overlay the catch block at `:1139` already drives.
  - **The watchdog does not fight the inner timeouts** — because it is strictly the largest bound, the 20s `completeRedirectAuth` race resolves/rejects first (its rejection is already caught at `:806-807` and lets boot continue), and the 30s data-load dismiss fires first for a slow load; the watchdog only ever wins when something _outside_ those two wedges. That is the gap it exists to close, and the ordering guarantees it can't pre-empt a healthy-but-slow path.
- **What's-new race:** in `useNotifications.ts` the ready-watcher (`:104-128`) already calls `consumeFamilyJustCreated()` (`:115`) and seeds all releases as read **before** `openToLatestAutoOpen()` (`:125`). Harden the ordering against the _resume_ path (where the family is created on the resume screen, possibly after the watcher's first `ready()` flush): gate `openToLatestAutoOpen()` on "not mid-onboarding" — i.e. skip the auto-open when the current route is a podless/onboarding route, so a brand-new family can **never** auto-open the drawer during create/resume regardless of watcher-flush timing. The seed itself (mark-all-read) still runs, so when the user does land in `/nook` nothing pops.
  - **Keep the predicate shared, not re-implemented.** `useNotifications` must import the _same_ `isPodlessRecoveryQuery` / `isPodlessExpectedRoute` predicates App.vue uses (from `resumePaths.ts` and `src/utils/appChrome.ts:47` respectively), not inline a second copy of the route-matching logic — otherwise the two drift and the gate silently stops matching what App.vue treats as onboarding (Pass 3, coupling/duplication).
  - **(Pass 4) `useNotifications` has no route reference today** — verified: the composable imports nothing from `vue-router` and never reads a route. `isPodlessExpectedRoute(route)` requires a route argument. So the gate must acquire one: call `useRouter()` (already available app-wide) and read `router.currentRoute.value` at the moment the watcher fires, or accept the route via the composable's existing wiring if one is already passed in. This is a _small_ addition (one `useRouter()` call + read the current route inside the watcher), not a new dependency graph — but it must be called out so "just import the predicate" isn't mistaken for a zero-plumbing change. Prefer `router.currentRoute.value` over `useRoute()` so the gate reads the live route at watcher-fire time rather than binding to a component-scoped route that may not exist in this composable's setup context. Unit-test that the gate reads the shared predicate against the live route.
