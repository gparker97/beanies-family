## Context

Production `load-perf` telemetry (2026-07-05, a real ~2 MB family document, one family_id across several devices) proved the long-standing "app freezes while the orange sync bar slides" report is the **JS main thread being pinned by synchronous, whole-document Automerge WASM**:

| Op                     | Count/4h | Duration                | When                                                     |
| ---------------------- | -------- | ----------------------- | -------------------------------------------------------- |
| `automerge.cacheLoad`  | 5        | **4.3–5.2 s** (avg 4.7) | every cold start (IndexedDB cache → `Automerge.load`)    |
| `automerge.remoteLoad` | 36       | **1.8–3.9 s** (avg 2.6) | every cross-device sync (whole 2 MB doc re-deserialized) |
| `automerge.save`       | 93       | 0.44–0.59 s             | every debounced persist (full `Automerge.save`)          |
| `automerge.mergeClone` | 10       | 0.28–0.71 s             | each merge (balloons on a stale/return-from-trip doc)    |

The orange `BackgroundSyncBar` is a non-blocking 3 px strip; it animates on the compositor thread while the main thread is frozen — which is why it keeps sliding during the hang and sometimes trips Chrome's "page unresponsive" dialog. `Automerge.save()` already produces a _compressed_ document, so the 2 MB is genuine state + history — **compaction is not a lever** (dropping history breaks CRDT merge with the family's other devices). Chunking is impossible (a single `Automerge.load`/`merge` is one atomic WASM call). The **only** way a load stops freezing the UI is to run it **off the main thread**. That is Plan A. Making each sync do _less_ work (KB-deltas instead of a whole 2 MB re-load) is Plan B.

Instrumentation to gather the above is already shipped and deployed (`src/utils/perfTiming.ts`, surface `load-perf`).

## ADR-032 (decision record — save to `docs/adr/032-off-main-thread-automerge.md`)

**Status:** Proposed · **Date:** 2026-07-05

**Decision — two phases, one boundary:**

- **Phase 1 (Plan A) — the Automerge document lives in a dedicated Web Worker.** The main thread never runs Automerge WASM. The worker owns the in-memory `Automerge.Doc` (source of truth) and the whole synchronous persistence pipeline: `load/save/clone/merge/change`, AES-GCM encrypt/decrypt, base64, and the IndexedDB **cache** (doc + envelope). The main thread keeps a **read-only reactive projection** of materialized collections; stores read it synchronously and issue mutations via async RPC. Google Drive network I/O (needs OAuth tokens) stays on the main thread — the split is "ciphertext bytes in / ciphertext bytes out."
- **Phase 2 (Plan B) — incremental delta sync.** Exchange Automerge _changes_ (`getChanges`/`applyChanges`) with Drive and the cache instead of whole documents.

**Binding constraint on Plan A:** the worker's RPC surface is **change-aware from day one** (`getHeads()`, `getChangesSince(heads)`, `applyChanges(bytes)`) even though Plan A still moves whole docs. Plan B is then a transport swap, not a re-architecture. This is the single decision that lets the two ship separately.

**Key sub-decisions & rationale:**

- **Dedicated Worker, not SharedWorker** — beanies is a PWA used heavily on iOS, where `SharedWorker` is historically unreliable/absent. Per-tab dedicated worker is portable; cross-tab coherence already comes from the Drive-poll + cache path.
- **Wrap the existing `docService`, do NOT adopt `@automerge/automerge-repo`** — automerge-repo would force replacing the bespoke encryption model, the V4 `.beanpod` envelope, and the Drive storage/auth layer with its adapters — a far larger, higher-risk rewrite touching the crypto core.
- **Hand-rolled typed correlation-id RPC over `postMessage`, not Comlink** — the boundary is small and data-integrity-critical (family finances); explicit auditable message types beat an opaque proxy, and add no dependency on a critical path.

**Alternatives rejected:** doc compaction/history truncation (breaks multi-device merge; save is already compressed); main-thread chunking with `await`/`requestIdleCallback` (a single WASM call can't be yielded); automerge-repo adapters (crypto/Drive rewrite); SharedWorker (iOS).

**Consequences:** cold-start load, cross-device sync, save, and merge all stop blocking the UI, at any doc size — directly delivers the product goal. The data layer becomes async end-to-end: the repository's generic CRUD is _already_ `Promise`-returning (low friction), but the real work is that **`changeDoc(fn)` mutation closures cannot cross `postMessage`** and must be re-expressed as declarative ops (mostly generic; a small enumerated set of nested-structure handlers for photos). The main thread still pays a structured-clone cost to receive projection snapshots — far cheaper than Automerge materialization, designed to be incremental, reduced further by Plan B. Ships behind a `docWorker` kill-switch with a retained inline fallback.

## Plan A — implementation

### User story

As a family member opening beanies after time away — or syncing across my phone and laptop — I want the app to stay responsive while my data loads and merges in the background, so it never freezes, never trips the browser's "page unresponsive" dialog, and I can start using it immediately.

### Key facts discovered during planning (some correct the naive framing)

- `automergeRepository` generic CRUD (`getAll/getById/create/createWithId/update/remove`) is **already `Promise`-returning** — array-ref stores through it need no signature change.
- **The real surface is the `changeDoc(fn)` mutation closures, not the `getDoc` readers.** Closures can't be structured-cloned across `postMessage`. BUT most are not truly bespoke — they are multi-entity field patches with no doc-walking (`familyStore.ts:349` normalizeRoles, `familyStore.ts:416` transferOwnership, `photoStore.ts:803` markDeleted, `overlapAckStore.ts:61`, `notificationsStore.ts:188`, settings/recipe/medication repos). These collapse to generic ops. The genuinely bespoke case is **one family**: photo attach/collect over nested hosts.
- **Photos are a runtime plugin registry.** `photoCollections` is a `Map` populated at runtime from `App.vue:111-117` (7 registrations incl. `avatarPhotoHooks`/`vacationPhotoHooks` from `src/services/photos/photoCollectionHooks.ts`); the hooks walk nested Automerge structures (`doc.vacations[*].travelSegments[].photoIds`). `finalizeUpload` (`photoStore.ts:474`) does `set photos[id]` **+** `attachPhotoToEntity` atomically. This whole registry must move into the worker as **static** (compile-time) registration.
- ~10 files read the doc **synchronously** via `getDoc()` (the `docVersion`-computed stores `calendarSyncStore/photoStore/overlapAckStore/notificationsStore`, `recipe/settings` repos, `App.vue`, `SettingsPage.vue`, `e2e/dataBridge.ts`) → move to reading the main-thread `projection`.
- No Web Workers / Comlink today. Vite 6 supports `new Worker(new URL('./x.ts', import.meta.url), {type:'module'})`.
- Reusable plumbing to lean on (do not reinvent): `showToast('error', …, {surface, error, critical})` already fans out to toast + `reportError` + telemetry + console, fault-isolated (`useToast.ts:98`, `errorReporter.ts:243`); `withTimeout` (`utils/timing.ts:16`); feature flags via `src/config/flagRegistry.ts` + `featureFlags.committed.ts`, read with `isFlagEnabled` (`flags.ts:71`, true-in-dev).

### Requirements

1. Automerge doc is owned only by the worker; the main-thread bundle contains no `Automerge.*` load/save/change/merge/clone calls.
2. The worker also runs encrypt/decrypt, base64, and the IndexedDB cache (doc + envelope). `initPersistenceDB` runs **inside** the worker (IDB connections aren't transferable; two openers on one DB deadlock on a future `onblocked`).
3. Drive network I/O stays on main; main hands ciphertext to the worker for merge and receives ciphertext to upload.
4. Main thread holds a read-only reactive `projection`; stores read it synchronously; all mutations go via async RPC.
5. RPC is change-aware from day one (`getHeads/getChangesSince/applyChanges`) even if unused in Plan A.
6. **No silent failures** — every RPC can reject and every rejection surfaces via a single `showToast('error', …, {surface:'doc-worker', error, critical})`. Worker spawn failure, crash, and timeout each handled.
7. **Fallback + recovery:** if the worker can't spawn/handshake, run the identical op set inline (functionality preserved, off-thread benefit lost). If the worker dies **mid-session** (iOS memory kill), re-spawn + re-hydrate from cache (or fall through to inline) with no re-unlock and no data loss (see "Worker lifecycle & re-hydration"). Gated by a `docWorker` kill-switch for instant rollback; degradation is logged.
8. Encryption/envelope/Drive semantics unchanged; `.beanpod` V4 untouched.
9. E2E passes (dataBridge → RPC).
10. Worker-side timing routed back through the existing `load-perf` telemetry (no second buffer).

### Important notes & caveats

- **Neither proxies nor closures cross the boundary** — only plain data (Uint8Array changes, materialized JS snapshots, heads, declarative op descriptors). The worker materializes collections internally and posts plain arrays.
- **Read-after-write is one round-trip** — today `update()` re-reads `getDoc()[collection][id]` (`automergeRepository.ts:109`); over RPC that's two trips + a race. Every mutation op **returns `{ result, delta }`** (the affected entity + the projection delta), so the repository echoes back in one trip and `docClient` applies the delta to `projection` before resolving.
- **`CryptoKey` is structured-cloneable** and posted to the worker once at unlock (non-extractable keys clone fine; same-origin; never leaves device). Verify on iOS in the spike.
- **Ordering — explicit async FIFO required.** `postMessage`/`onmessage` ordering only serializes the _synchronous prefix_ of each handler; the merge and persist handlers are **async** (they `await crypto.subtle` before `Automerge.load`/`merge`), so a naive `onmessage = async e => await handle(e)` lets message N+1 mutate the doc _while N's merge is parked at its decrypt `await`_ — reordering writes into a doc changing underneath a merge. `docWorker`/`applyAndProject` MUST maintain an explicit promise-chain queue (`tail = tail.then(() => handle(msg))`) so each handler fully completes before the next begins. (CI tier-2 test: post `[slowMerge, mutation]`, assert the mutation applies to the post-merge doc.) Stores await the RPC then reflect the projection (no optimistic UI). A timed-out RPC's late reply is **discarded by correlation-id** (`withTimeout` does not cancel underlying work — `timing.ts:9`).
- **`docVersion`** stays the coarse "something changed" trigger, bumped on each projection push; existing `void docVersion.value` subscriptions (`overlapAckStore.ts:35`, `notificationsStore.ts:83`) keep working.
- **Persist/Drive split (two silent-failure guards):** the _cache_ debounce moves into the worker; but the persist callback today ALSO triggers the **Drive** upload (`syncService.ts:1047`), which needs OAuth on main. So the worker emits an explicit **`dirty` signal** (on the projection-update push) after a _local_ change → main maps it to `triggerDebouncedSave()`. For a remote merge, **derive `dirty` from whether the merge advanced local heads beyond the remote's** (i.e. the local doc carried unsynced changes that the converged doc must push back) — the change-aware `getHeads()` makes this cheap — rather than a blunt `dirty:false`. This is more correct than today: `suppressAutoSave` (`syncService.ts:160,677`) only wraps the _synchronous_ `mergeDoc` call, but `schedulePersist`'s 500 ms debounce fires the Drive save _after_ the flag resets, so today every merge (incl. the local-file poll path, which has no other save trigger) eventually re-uploads. A blunt `dirty:false` would stop the local-file poll path from re-uploading a converged merge → silent cross-device divergence (a device carrying an unsynced edit never pushes it); a blunt `dirty:true` re-introduces save ping-pong between two always-open devices. **Exact rule (pin this — a pre-merge `getHeads(local)!=getHeads(remote)` reintroduces the ping-pong):** compute `dirty` from the MERGED doc vs remote, AFTER `migrateDoc` — `dirty = Automerge.getChanges(remote, merged).length > 0` (equivalently heads-inequality). Truth table: remote-ahead-local-clean → false; local-had-unsynced → true; concurrent-both-sides → true; no-op (local already had remote's changes) → false (this is what breaks the ping-pong). A legacy `migrateDoc` change legitimately makes it true once (correct). Local `change` → `dirty:true`.
- **Envelope-cache freshness (prevents a cold-start unlock regression).** Today the persist callback re-persists the _doc cache_ AND `persistEnvelope(currentEnvelope)` on every change (`syncService.ts:1047`), keeping the cached envelope's `wrappedKeys` fresh — that's what lets a device unlock from cache after a password change / join / passkey register / admin reset (each mutates `currentEnvelope` on main via `preserveLocalKeyDicts`, `syncService.ts:693`). The worker now owns the doc cache but the envelope is **main-owned truth**, so this coupling would silently break → a stale cached envelope after a password rotation reproduces the welcome-gate sign-in regression the code warns about (`syncService.ts:684-692`). Fix: **every `currentEnvelope` mutation on main (`preserveLocalKeyDicts`/`replaceEnvelope`/join/changePassword/passkey/admin-reset) RPCs the updated envelope to the worker to re-persist the envelope cache** — replacing the old persist-callback coupling. Envelope truth stays on main; the worker holds only a cache copy (safe — `wrappedKeys` are already at-rest AES-KW ciphertext, not plaintext).
- **Do NOT** move Drive auth/token logic into the worker. **Do NOT** implement incremental sync here (Plan B) — only the change-aware hooks. Validate against a **fresh** dev server (lessons.md #15 — a warm server serves stale worker code and false-greens).

### Assumptions (review before implementation)

1. The ~2 MB size + telemetry durations are representative; structured-clone projection transfer is materially cheaper than on-thread materialization — **confirmed by the spike (Testing step 1) before full migration**.
2. `CryptoKey` posts cleanly on all targets incl. iOS Safari/PWA — verify early.
3. Vite 6 + vite-plugin-pwa bundle a `type:module` worker into the prod build + precache; `worker-src 'self'` allowed if a CSP is set.
4. No store synchronously consumes a repo return as a non-promise.
5. iOS WebKit won't kill the worker mid-session in a way that loses data (cache is durable; a killed worker re-hydrates from cache — design for it).

### Approach

**Architecture**

```
── Main thread ─────────────────────────────      ── docWorker ───────────────────
 components → Pinia stores                          owns Automerge.Doc (truth)
   reads  → projection (reactive, read-only) ◀────  load/save/clone/merge/change ops
   writes → docClient.mutate() ─ async RPC ─────▶   encrypt/decrypt/base64
 syncService: Drive fetch/upload (OAuth on main)    IndexedDB cache (doc + envelope)
   posts ciphertext in, gets ciphertext out         persist debounce; emits `dirty`
 docClient: typed correlation-id RPC
```

**New modules**

- `worker/docOps.ts` — op handlers, split by purity: the **change/merge/materialize** handlers are pure sync `(doc, op) → { newDoc, result, delta }` (this is where the parity/determinism tests apply); the **crypto/persist** handlers (`encrypt`/`decrypt`/cache read+write) are async and isolated (they touch `crypto.subtle` + a `CryptoKey`, so not pure/sync). Holds the domain logic (incl. the photo hooks, statically registered). Imported by BOTH the worker and the inline fallback → one implementation, two contexts.
- `worker/applyAndProject.ts` — shared wrapper around `docOps` that adds persist-debounce, `dirty` derivation, and projection materialization. BOTH the worker message loop and the inline adapter are thin shells calling this — so debounce/dirty/projection logic lives in exactly one place (prevents worker/inline divergence).
- `worker/protocol.ts` — typed request/response discriminated unions + correlation-id envelope. Owns the _envelope only_; imports domain payload types (`CollectionEntity<K>`, `PhotoAttachment`, …) rather than re-declaring them (no wire/entity drift). Includes an **error-serialization registry**: `name → {serialize, reconstruct}` so any typed error (`CorruptPayloadError` with `phase`/`familyId` first; later `PhotoCollectHookError`, etc.) survives the boundary; unregistered → generic `DocWorkerError`. New typed error = one registry line.
- `worker/docWorker.ts` — worker entry; thin shell wiring `applyAndProject` to `postMessage`.
- `worker/docClient.ts` — main-thread RPC client: spawn, correlate, `withTimeout`, crash → reject + fallback, funnels worker perf samples into `perfTiming.record` and worker errors into `showToast`. Exposes an async API (`mutate`, `mergeRemoteEnvelope`, `exportEncryptedEnvelope`, `getHeads`, `getChangesSince`, `applyChanges`, envelope read/write).
- `projection.ts` — main-thread reactive mirror (per-collection `shallowRef`s incl. `settings`/`calendarConnections`/`photos`/`overlapAcknowledgments`/`notificationReads`); applies `projection-update` payloads and bumps `docVersion`. Typed sync getters `projection.get<Collection>()`.

**Mutation ops** — `changeDoc(fn)` is retired.

- **Generic (cover the large majority):** `{op:'set',collection,id,entity}`, `{op:'patch',collection,id,patch,deleteKeys,updatedAt}`, `{op:'delete',collection,id}`, and `{op:'batch',ops:[…]}` applying its sub-ops in a **single `changeDoc`** (atomicity — e.g. `finalizeUpload`'s set+attach) and returning all touched collections.
- **Relative/atomic op — REQUIRED to prevent silent lost financial writes:** `{op:'increment', collection, id, field, delta}` reads the current field value and writes `current+delta` **inside one worker `changeDoc`**, so the read and write are atomic against the authoritative doc. Today `adjustAccountBalance` (`transactionsStore.ts:221`), `adjustGoalProgress` (`:233`), and `applyLoanPayment` (`:280`) read the balance on the main thread and write an **absolute** value via `update()` — atomic today only because the read and the synchronous `changeDoc` share a microtask. Over async RPC a poll-merge can land between the main-thread read and the write, so the absolute write silently discards the peer's balance change (a lost transaction/balance edit on ordinary use). Route all three through `increment`. (This does not change cross-device register-merge semantics — a pre-existing CRDT limitation for Plan B — but it removes the _new_ local lost-update the async boundary introduces.)
- **Governing rule:** prefer generic `set/patch/delete/batch`; a _named_ bespoke op is justified ONLY when it walks nested/array structure `patch` can't express. Under this rule `normalizeRoles`, `transferOwnership`, `markNotificationRead`, `ackOverlap`, `markDeleted` all become generic; the only true bespoke family is **photo attach/collect over nested hosts**.
- Every handler returns `{ result, delta }` where `delta` is the entity-level change(s) + collection name (derived from what the handler actually touched, never a hand-maintained list). `docClient` applies `delta` to `projection` before resolving. First load/merge is the only bulk case (chunked per-collection, see the data-flow contract).

**Photo hook registry → static, in-worker.** `photoCollections` + all `PhotoCollectionHooks` (`flatHooks`, `avatarPhotoHooks`, `vacationPhotoHooks`) are pure `(doc,…)` functions → move into `docOps` verbatim, registered **statically at compile time inside the worker** (not the runtime `App.vue:111-117` path). The nested-attach op covers **both** `finalizeUpload`'s set+attach (`photoStore.ts:474`) **and** the standalone `linkPhotoToEntity` (`photoStore.ts:975`, attach-over-nested-hosts) — enumerate both. **`gcOrphans` stays a main-driven loop** to preserve its two invariants: the fail-safe (if any `collect` hook throws, `collectReferencedPhotoIds` throws → the sweep deletes **nothing**, `photoStore.ts:823`) and the per-photo Drive coupling (delete the Automerge record **only after** its `deleteFile` succeeds/404s; a non-404 failure keeps the record for retry, `:840`). So: the worker exposes `collectReferencedPhotoIds` (throwing preserved) + a **single-id `deletePhotoRecord` op**; main iterates candidates, calls `deleteFile` (token/Drive on main), and RPCs `deletePhotoRecord(id)` only on success/404 — reproducing today's coupling exactly, not a decoupled batch delete. Documented rule: "adding a photo host = edit the worker registry."

**Migration of existing modules**

- `docService.ts` — **retire its mutation/read API** (no async facade under old names — today's `changeDoc` callers don't `await`, so a facade turns them into rejection-swallowing fire-and-forget). Reads → `projection.get…`; writes → awaited `docClient.mutate`. Keep only still-sync helpers (`isDocLoaded`, `resetDoc`, `docVersion`).
- `automergeRepository.ts` — public CRUD signatures unchanged; internals → `projection` reads + `docClient.mutate`; `update()` returns the echoed entity (one trip). **Array-ref stores untouched.**
- `persistenceService.ts` — crypto+IDB internals (`saveDoc`, `encryptPayload`, base64, `db.put/get`, `initPersistenceDB`, teardown `clearCache`/`closeCacheDB`) move into the worker (owns doc + envelope). Main reads/writes envelope + triggers teardown via RPC. Give the worker's `loadCachedDoc` the **same materialize sanity-check + `CorruptPayloadError` wrapping as the Drive path** (`fileSync.ts:134`) — today cache-load (`:94`) calls `Automerge.load` bare, so a materialize-corrupt cache slips past, `replaceDoc`s, and throws later only `console.warn`'d (invisible + can loop corrupt→re-persist-corrupt); detect before `replaceDoc`, report via the error registry, clear-and-rebuild. Preserve `setCachePersistFailed` (`syncService.ts:1054`): a worker cache-persist failure must still drive the persistent "local durability broken" banner, not just a transient toast.
- `fileSync.ts` — the doc-crypto halves move into the worker/`docOps`: `decryptBeanpodPayload` (`:117`, throws `CorruptPayloadError`+materialize check — reconstructed via the protocol registry; the merge RPC must carry `envelope.familyId` since the error is built from it, `fileSync.ts:138`), and the `saveDoc()`+`encryptPayload` half of **both** `reEncryptEnvelope` (`:236`) **and `createBeanpodV4` (`:36`, the sole envelope builder for the create-family flow, `syncStore.createNewFile`→`:1248`)** — miss `createBeanpodV4` and first-run pod creation calls a main-thread `saveDoc` with no doc and throws. **Envelope assembly stays on main:** the worker returns just the base64 `encryptedPayload`; main builds `{...currentEnvelope/new envelope, encryptedPayload}` + `JSON.stringify` — so `wrappedKeys`/`inviteKeys` never leave main for the upload path.
- `syncService.ts` — `fetchAndMergeRemote`: main fetches Drive text → posts ciphertext + `familyId` to `docClient.mergeRemoteEnvelope` → worker decrypts/loads/merges/persists cache and returns heads + projection + a **computed `dirty`** (NOT hardcoded false — see the heads rule below). **`fetchAndMergeRemote` MUST call `triggerDebouncedSave()` on the main thread when the merge reports `dirty:true`** — this is the poll path's ONLY re-upload trigger, and it replaces the old `mergeDoc→schedulePersist→persistCallback→triggerDebouncedSave` coupling that the migration removes. Also **route the `currentEnvelope = preserveLocalKeyDicts(...)` at `syncService.ts:693` through `setEnvelope(...)`** so the envelope-cache RPC fires (this site mutates the envelope directly today and is the one path the `setEnvelope`/`replaceEnvelope` funnel would otherwise miss → stale envelope cache → cold-start lock-out after a peer key-add/rotation). `doSave`: worker returns the encrypted payload → main assembles the envelope and uploads. Timestamp fast-path stays on main.
- `docVersion`-computed stores + `recipe/settings/medication` repos + `App.vue` + `SettingsPage.vue`: `getDoc().X` → `projection.getX()`; keep `void docVersion.value`.
- **`syncStore.ts` (central doc-lifecycle orchestrator — the largest surface).** Imports/calls `replaceDoc`+`mergeDoc` (`:79`) and `initPersistenceDB`/`persistDoc`/`loadCachedDoc` (`:81`) throughout: `mergeDoc` `:567,645,1858,1947`; `replaceDoc` `:564,652,819,985,1396`; `initPersistenceDB` `:555,895,967,1279,1469`; `persistDoc` `:571,896,1280,1470`; `loadCachedDoc` `:559,979`. All become worker RPCs (the worker owns doc + cache + `initPersistenceDB`). The bespoke `replaceDocWithCacheRecovery` (`:550`: `initPersistenceDB`→`loadCachedDoc`→`mergeDoc(cached)`→`replaceDoc(remote)`→`persistDoc`) is re-expressed as **one ordered worker RPC sequence** (the worker's single queue preserves ordering). Every `currentEnvelope` write already funnels through `replaceEnvelope`/`setEnvelope` (`:131`), so the envelope-cache RPC (see Persist/Drive split) hooks there and covers all ~11 key-dict mutation sites.
- **`authStore.ts` `initDoc()` (`:19,479`, create-family)** and **`App.vue` init/seed lifecycle (`:576-601`: dynamic `initDoc()`/`loadDoc()` + the `__e2eSeedDoc` seed path)** — doc creation/load move behind the worker; not just the `getDoc` reader at `:1019`.
- **`isDocLoaded()` re-backed against a main-thread projection "loaded" flag** (today `currentDoc !== null`, `docService.ts:169` — there is no `currentDoc` on main post-migration). Otherwise these non-listed consumers silently read `false` forever: `driveTokenRecovery.ts:76,103,220,314`, `listStore.ts:147,430`, `settingsStore.ts:269`, `useCalendarNudge.ts:71`, `useNotifications.ts:86`.
- **`resetDoc()` becomes an RPC (resets both sides)** — sign-out/family-switch must drop the worker's in-memory doc, clear the projection, AND trigger the worker cache-teardown RPCs (close-then-delete the cache DB; see lifecycle). A main-only reset leaves a live doc + undeleted encrypted cache in the worker → cross-session data bleed + privacy break (`overlapAckStore.ts:10` documents central `resetDoc` clearing; `database.ts:65` `deleteFamilyDatabase`). `isCacheReady` (`syncService.ts:26`) needs a worker-backed readiness signal.
- `e2e/dataBridge.ts` — swap `getDoc/changeDoc` for `docClient` awaits. **BUT `dataBridge.ts:86-96` `beforeunload → snapshotDoc()` calls `saveDoc()` synchronously** to stash the binary in `sessionStorage` (the mechanism that makes UI-created data survive `page.goto()` reloads, restored at `App.vue:592`) — a `beforeunload` handler cannot `await` a worker RPC. Handle via a **worker-synchronous snapshot pre-staged on `visibilitychange`/`pagehide`** (worker posts the current serialized binary ahead of unload so the sync handler only reads it), or a retained main-thread serialization escape hatch used only in the E2E build. This is distinct from the IndexedDB cache flush.
- **Build/test config:** `vite.config.ts` — add a **`worker: { format: 'es', plugins: () => [wasm(), topLevelAwait()] }`** block (top-level plugins do NOT apply to worker bundles; the worker imports the ~2.65 MB Automerge WASM with top-level await and won't build without it); ensure the WASM stays a top-level emitted asset (not base64-inlined) so `workbox.globPatterns` (`:184`, already covers `js`/`wasm`, 4 MiB cap) precaches it; `worker-src 'self'` if a CSP is set. `vitest.config.ts` — happy-dom has no `Worker`; add `@vitest/web-worker` (or ensure `docClient` **lazy-spawns** and never `new Worker` at module scope) so existing tests importing the store/doc chain don't throw at import.

**Reactivity & data-flow contract (single-message entity-delta — fixes BOTH a stale-read race and a per-edit O(n) regression)**

- Reads: synchronous from `projection`; never block.
- **Writes carry their projection delta IN the response — one message, no race.** `store → await docClient.mutate(op)`; the worker mutates, debounce-persists, and returns **`{ result, delta }}`** (the affected entity/entities + collection). `docClient` **applies `delta` to `projection` synchronously in `onmessage` BEFORE resolving the promise** — so anything reading right after `await` (a store's own read-after-write, or `deduplicateRecurringTransactions` after a merge) sees the write. No separate `projection-update` message races the response.
- **Surgical O(1) apply — never re-materialize a whole collection on an edit.** The projection applies the delta to its per-collection `shallowRef` map surgically (add/replace/remove one entity), mirroring today's O(1) store updates (`transactionsStore.ts:373` spread-append, `:416` map-replace). Array-ref stores keep their existing surgical self-update from the echoed `result` (as today); they do NOT full-`loadX()` after their own write. This preserves today's O(1)-per-edit cost — a single-entity edit must never re-clone the whole collection across the boundary (acceptance criterion). Cascading writes (`createTransaction` → `adjustAccountBalance`/`applyGoalAllocation`/`applyLoanPayment`, `transactionsStore.ts:379`) each return their own small delta.
- **Loads/merges push bulk, chunked to stay off the critical path.** First load / remote merge is the only time full or multi-collection snapshots move; the worker **pushes per-collection across successive messages/microtasks (yielding between collections)** rather than one giant `ALL_COLLECTIONS` structured-clone — committed now, not left to a spike verdict, so a big doc's receive can't itself become a long task. `reloadAllStores` still calls each `loadX()` (each re-reads the pushed projection synchronously); the 21-way `Promise.all` (`syncStore.ts:1689`) becomes cheap. **Barrier (load-bearing for ledger integrity):** `mergeRemoteEnvelope` resolves ONLY after its FINAL projection chunk has been applied on main — chunking slices the main-thread task, it does NOT license early resolution. So the post-merge `deduplicateRecurringTransactions` (`recurringProcessor.ts:399`, which reads the WHOLE `projection.transactions`, run at `syncStore.ts:569,674,1864,1953`) always reads the complete merged set — a stale/partial read would let CRDT-merge-created duplicate recurring transactions survive as duplicate ledger rows. This barrier holds for all four merge call sites incl. `replaceDocWithCacheRecovery` (`syncStore.ts:564`, whose "local" for the dirty/heads computation is the cache, not the live doc). Bump `docVersion` **once** after all chunks apply (not per-chunk), so a computed can't observe a transaction referencing an account whose chunk hasn't landed.
- **Writes during an in-flight load queue behind it (worker is sequential).** A tap that issues a mutation while the worker is mid-`cacheLoad`/`remoteLoad` (up to several seconds) resolves correctly but not instantly; the control shows a **pending state** rather than appearing inert (acceptance criterion). Optimistic UI is out of scope (writes are already `await`ed today, so idle-worker round-trips are sub-perceptible).

**Error handling & fallback (no silent failures)**

- `docClient` wraps every RPC in a correlation-id promise + `withTimeout` → typed `DocWorkerError` with op name; late replies dropped by id. **It funnels rejections to `showToast('error', …, {surface:'doc-worker'})` at the client boundary — independent of whether the caller awaits** — so today's fire-and-forget mutators (`markDeleted` `photoStore.ts:800`, `gcOrphans`'s per-photo change `:852`) can't silently swallow a worker failure. **BUT exempt the expected-degradation class:** `CorruptPayloadError` and ordinary decrypt failures on `mergeRemoteEnvelope` are routinely caught-and-swallowed today to fall through to the cached key (`syncStore.ts:1869,1957`, poll classifies its throw as a mere _warning_ `syncService.ts:130`) — e.g. "password changed on another device." `docClient` must NOT blanket-`critical`-toast these; let the existing callers classify (and avoid double-report with their own `reportError`). This makes the error registry's faithful reconstruction of a real `CorruptPayloadError` **instance** (with `phase`/`familyId`) load-bearing, since recovery dispatch is `instanceof CorruptPayloadError` (`syncStore.ts:930,1122,2484`) — a generic `DocWorkerError` would break every recovery branch.
- **The worker must NOT import `errorReporter`/`perfTiming`/telemetry** (they're main-thread-shaped — `errorReporter` uses `sessionStorage`, `logQueue` flushes on `window`/`pagehide`/`sendBeacon`; a second in-worker buffer would never flush and silently lose records). The worker times with raw `performance.now()` and posts `{label,durationMs,ctx}` + structured error records back. `docClient` funnels perf into the existing thresholds by calling the now-**exported** `record` from `perfTiming.ts:38` (single buffer, no duplicated thresholds) and errors into a single `showToast('error', …, {surface:'doc-worker', error, critical})`.
- Worker `onerror`/`onmessageerror`/in-worker rejections → posted as the pending op's error response (with the registry discriminant); no bare catches.
- **Fallback:** worker spawn/handshake failure → `docClient` `mode='inline'`, delegating to the same `applyAndProject`/`docOps` inline (one implementation). `docWorker` flag can force inline. Degradation logged (fallback rate visible in prod).

**Worker lifecycle & re-hydration (mid-session death is a data-loss surface — iOS kills workers under memory pressure).** The worker's in-memory doc is the source of truth; if the worker dies, it's gone until re-hydrated from the encrypted cache (the durable copy). `docClient` watches for `onerror`/termination/unexpected silence and, on mid-session loss: (1) **rejects all pending RPCs** with their op names (→ `showToast`), (2) re-spawns the worker, (3) re-posts the retained `CryptoKey`, (4) issues a **re-hydrate RPC** (`initPersistenceDB` + `loadCachedDoc` → push full `ALL_COLLECTIONS` projection) before resuming the queue. If re-spawn fails, fall through to inline (which itself re-hydrates from cache). Re-hydration runs `initPersistenceDB` in **exactly one** live context — a dead worker's IDB connection is already gone, but guard the inline path against a double-open of `beanies-automerge-{familyId}`. No re-unlock is required (the key is still held on main). The worker **guards every persist/decrypt/merge op with `if (!familyKey) throw`** (symmetric to today's `if (!cacheDb) throw`) and rejects ops that arrive before the key has been (re)posted, with a typed error — so a race after re-spawn can't attempt a crypto op with an undefined key and wedge the queue.

**Backgrounding flush (honest scope — narrows, does NOT fully close, the window).** Main fires a flush on **`visibilitychange:hidden`** (fires while the page is still fully alive on iOS app-switch — earlier and more reliable than `pagehide`) → worker cancels the debounce and persists immediately. But this flush is **async** (postMessage → worker `save` ~0.5s → encrypt → `db.put`); on an iOS memory-kill it may not complete. So: (a) shorten the worker cache-persist coalesce from 500 ms to ~100–150 ms (the 500 ms existed only to spare the _main thread_ the synchronous `save` jank — moot once off-thread; the whole-doc `save` cost still forbids per-edit persistence, so keep a short coalesce, not zero); (b) **document the residual ≤~coalesce-window last-edit-loss as a known Plan-A limitation** whose true closure is a Plan-B exit criterion (incremental `saveIncremental` persist makes a persist cost a delta, enabling persist-on-every-mutation ≈ zero window); (c) on an _unexpected_ worker death detected while the tab is **foreground/visible**, the re-hydrate path surfaces a non-fatal "recovering your latest changes" state rather than silently loading a possibly-one-window-stale cache. Do NOT claim the window is "closed."

**Sign-out / family-switch cache teardown MUST be worker RPCs.** `clearCache`/`closeCacheDB` (`persistenceService.ts:146`) and `deleteFamilyDatabase` (`database.ts:65`) currently run on a main-thread connection that post-migration is always `null` (the DB is only opened in the worker) → `indexedDB.deleteDatabase` runs while the worker still holds an open connection → `onblocked` fires → the handler `resolve()`s "successfully" but **the encrypted cache is never deleted** (privacy break + stale-cache-on-next-unlock hazard). The worker must `close()` its connection **then** `deleteDatabase`, exposed as teardown RPCs; `resetDoc` (below) triggers them. Test: after sign-out, `indexedDB.databases()` no longer lists `beanies-automerge-{familyId}`.

**Rollout:** land behind `docWorker` (auto-on in dev; committed staged value in prod). Keep inline path for one release. Confirm via worker-side `load-perf` that load/merge/save run off-thread and main-thread long-tasks vanish, then remove the inline path in a follow-up once stable.

### Acceptance criteria

- [ ] No `Automerge.*` load/save/change/merge on the main-thread bundle (grep-verified; worker file excepted).
- [ ] Cold start: shell interactive, **no main-thread long task > ~200 ms** while a ~2 MB doc loads (DevTools + worker `load-perf`).
- [ ] Cross-device sync does not freeze the UI; taps respond throughout.
- [ ] All unit + E2E pass on a **fresh** server, incl. migrated `dataBridge`.
- [ ] Worker spawn failure / forced `docWorker` off → app works end-to-end via inline fallback; degradation logged.
- [ ] Every RPC failure surfaces via `showToast` + telemetry; no new silent failure.
- [ ] Data integrity: create/edit/delete across accounts/transactions/todos/activities round-trips to `.beanpod` and reloads identically; multi-device merge converges.
- [ ] **Drive auto-save fires exactly when needed** — after a local edit (worker `dirty` → `triggerDebouncedSave`), AND after a poll-merge that left local heads not covered by remote (`getChanges(remote, merged)`>0 → `fetchAndMergeRemote` calls `triggerDebouncedSave`); a no-op/remote-ahead merge does NOT re-upload — no dropped unsynced edit, no ping-pong between two always-open devices.
- [ ] Corrupt/undecryptable payload still surfaces as `CorruptPayloadError` (class + `phase`/`familyId` reconstructed).
- [ ] Static `ref<T[]>` stores re-derive from `projection` after their own mutate (no stale list).
- [ ] Change-aware RPC (`getHeads/getChangesSince/applyChanges`) exists + unit-tested (unused by Plan A transport).
- [ ] Worker-origin errors + perf reach the **single** existing telemetry buffer (`doc-worker`/`load-perf` in CloudWatch).
- [ ] **Parity test (semantic, not byte-level)**: identical op sequence (create→patch→attachPhoto→merge→delete) through worker vs inline yields **deep-equal materialized projection snapshots**, and loading both `save()` outputs into a fresh doc yields **identical `Object.values()` per collection**. Byte-identical `save()`/`getHeads()` is NOT asserted — Automerge actorIds and change `time` fields are nondeterministic across instances.
- [ ] **Projection invariant test**: for each op, collections in the push == collections whose materialized snapshot actually changed.
- [ ] **Worker-death recovery test**: force `worker.terminate()` mid-session → app re-hydrates the doc from the encrypted cache without a re-unlock and without data loss; in-flight mutation RPCs reject and surface via `showToast`.
- [ ] **Envelope-cache freshness test**: after a password change, a cold start unlocks from the cached envelope with the new password (the envelope cache stayed in sync with main's `currentEnvelope`).
- [ ] **Backgrounding flush test**: a local edit followed immediately by `pagehide`/`visibilitychange(hidden)` is persisted to cache (no lost last-edit inside the debounce window).
- [ ] **No per-edit whole-collection re-clone**: editing one entity in a large collection sends only an entity-level delta across the boundary and applies to the projection surgically (assert the message payload is ~one entity, not the whole array; O(1) not O(n)).
- [ ] **First-load/merge is chunked**: the initial projection arrives per-collection across microtasks with no single main-thread long task > ~200 ms even on a ~2 MB doc.
- [ ] **Post-merge dedup reads fresh data**: after a merge that introduces duplicate recurring transactions across devices, `deduplicateRecurringTransactions` removes them (the merge delta was applied to projection before the RPC resolved) — no duplicate ledger rows persist.
- [ ] **Multi-device merge re-uploads correctly**: a local-file poll that merges a peer's changes re-uploads the converged doc when local had unsynced changes (heads-derived `dirty`), and does NOT ping-pong when it didn't.
- [ ] **Write-during-load**: a mutation issued while the worker is mid-load resolves correctly and its control shows a pending state (not inert).
- [ ] **`isDocLoaded` + `resetDoc`**: `isDocLoaded` reflects the real loaded state for all consumers post-migration; sign-out/family-switch clears BOTH the worker doc and the projection (no cross-session data bleed).
- [ ] **create-family first run**: a brand-new user with no cache creates a family end-to-end (worker `initDoc` + `createBeanpodV4` path), and via the inline fallback when the worker is forced off.
- [ ] **E2E reload persistence**: UI-created data survives a `page.goto()` reload (the snapshot path works without a synchronous main-thread `saveDoc`).
- [ ] **Atomic balance/goal/loan**: a transaction added while a poll-merge lands a peer's balance change does NOT lose either write (both applied via the worker-atomic `increment` op) — assert final balance = base + both deltas.
- [ ] **Worker async-FIFO**: posting `[slowMerge, mutation]` applies the mutation to the post-merge doc (no interleave); no write is reordered ahead of an earlier one.
- [ ] **Post-merge dedup barrier**: `mergeRemoteEnvelope` resolves only after the final projection chunk; forcing chunking, `getAllTransactions()` right after `await` returns the complete merged set and dedup removes the CRDT-created duplicates.
- [ ] **Envelope cache fresh via poll-merge** (not just password change): a peer adds a member wrapped-key and pushes; this device's poll-merge re-persists the envelope cache; a subsequent cold start unlocks (`syncService.ts:693` routed through `setEnvelope`).
- [ ] **Sign-out deletes the cache**: after sign-out, `indexedDB.databases()` no longer lists `beanies-automerge-{familyId}` (worker closed its connection before delete).
- [ ] **Corrupt-cache detection**: a materialize-corrupt cache surfaces `CorruptPayloadError` (telemetry) and triggers clear-and-rebuild, not a silent later throw.
- [ ] **Expected decrypt failures are quiet**: a merge-RPC `CorruptPayloadError` (e.g. peer password change) does NOT raise a critical `#beanies-errors` toast; the existing caller classifies it and recovery dispatches on a reconstructed `instanceof CorruptPayloadError`.

### Testing plan
