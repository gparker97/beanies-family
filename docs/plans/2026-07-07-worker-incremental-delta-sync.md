# Plan: ADR-032 Plan B / Layer 2 — incremental Automerge delta sync (worker large-doc durability)

> Date: 2026-07-07
> Related issues: Notion #42 (no GitHub issue — direct implementation)
> Plan file: `docs/plans/2026-07-07-worker-incremental-delta-sync.md`
> Depends on: ADR-032 Plan A (`docs/plans/2026-07-05-automerge-web-worker.md`, shipped), Layer 1 (`docs/plans/2026-07-06-worker-ios-large-doc-load.md`, shipped 0.9.2R3). Rides the EXISTING `docWorker` kill-switch — no new flag.

## User Story

As a family member with a large, long-lived beanies file (especially on iPhone), I want the app to sync only what changed instead of reloading my whole file each time, so that opening and syncing stay fast and my most recent edit is never lost when I background the app.

## Context

ADR-032 Plan A moved the Automerge doc off the main thread (no more UI freeze) but still moves **whole documents**: every poll-merge decrypts + `Automerge.load`s + whole-doc-merges the entire ~2 MB envelope (`automerge.remoteLoad`, ×36/session desktop, far worse on iOS JSC), and every cache persist runs a whole-doc `Automerge.save()`. Plan A deliberately built a **change-aware RPC surface** (`getHeads`/`getChangesSince`/`applyChanges`, docOps.ts:54-66 + dispatch applyAndProject.ts:450-455 + client docClient.ts:520-525) **specifically so Plan B is a transport swap, not a re-architecture**. Verified during this planning pass: those primitives have **zero production callers and no direct unit tests** today (they exist only as impl + wrapper + dispatch case). This is Plan B: make each sync do LESS work by finally wiring them up.

**The three levers, and what each actually fixes (this framing is load-bearing — see Important Notes):**

| Lever                                                   | Fixes                                                                                                  | Does NOT fix                                                                                                                                                           |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B1 — incremental cache persistence** (delta chunks)   | The backgrounding last-edit-loss window (persist ~ per mutation instead of a debounced whole-doc save) | Cold-load latency; poll-merge remoteLoad                                                                                                                               |
| **B2 — incremental Drive delta transport** (change-log) | Poll-merge `automerge.remoteLoad` (apply KB deltas, not load 2 MB)                                     | Cold-load latency                                                                                                                                                      |
| **(neither)**                                           | —                                                                                                      | **The iOS cold first-load `Automerge.load` floor** — only history compaction removes that, which ADR-032 **rejected** as merge-breaking and #42 lists **out of scope** |

The honest consequence, resolved in **Open Questions** below and surfaced to greg at approval: **incremental delta sync alone does NOT make the very first cold load of a huge deep-history doc fast** — `Automerge.load` replays the whole change history regardless of transport. Layer 1 already made that cold load _non-erroring and responsive_ (120s ceiling + "counting beans" spinner). Plan B's iOS load-time target therefore applies to the **warm / ongoing** path (poll-merge + re-open with a live cache), not the first cold load. A genuinely fast first cold load is a separate concern (see Open Question 1).

## Requirements

1. **B1 — incremental persistence.** The worker persists changes incrementally (delta chunks captured via the **existing** `docOps.getChangesSince(currentDoc, lastPersistedHeads)`, docOps.ts:58) rather than a whole-doc `Automerge.save()` on every debounce, so a cache persist costs a delta. This enables persist-on-(near-)every-mutation, effectively closing the ≤coalesce-window last-edit-loss documented as a Plan-A limitation (`docs/plans/2026-07-05-automerge-web-worker.md:162`).
2. **B1 — cache format + load.** The cache stores a base snapshot + appended incremental change chunks; `loadCachedDoc` reconstructs by loading the base (`loadAndVerify`) and applying the increments (**reusing** `docOps.applyChanges`). A periodic **base re-compaction** (rewrite base = whole `save()`, clear increments) bounds cache growth and reload cost. Base re-compaction preserves full history (a `save()` is loss-less) — it does NOT drop history, so multi-device merge is unaffected.
3. **B2 — incremental poll sync.** A poll that ingests a peer's changes applies only the deltas via `getChangesSince`/`applyChanges`, NOT decrypt + `Automerge.load(whole 2 MB)` + whole-doc merge. This requires a durable "changes since `<heads>`" representation on Drive (Requirement 4).
4. **B2 — durable Drive change representation (append-only, self-describing, NO shared mutable manifest).** Because the `StorageProvider` abstraction is confirmed **single-file** (storageProvider.ts: `write(content)`/`read()`/`getLastModified()` only — no multi-object API), B2 must first extend the provider with a minimal multi-object family-folder API (Requirement 10), then define an encrypted, append-only per-device change-log alongside the existing whole-doc `.beanpod` V4 base envelope. **The change-log is a set of immutable, uniquely-named, self-describing chunk objects (`changes/<deviceActorId>-<seq>.beanchanges`), each carrying its own `{ changes, frontierHeads }`, discovered by listing the folder (`listAux()`) — NOT a single shared `manifest.json` that multiple devices rewrite.** A shared mutable manifest on a transaction-less store is a lost-update race (two devices publishing concurrently clobber each other's entries → an orphaned/invisible chunk); the append-only-per-device + folder-listing design has no shared mutable object and therefore no such race (Important Notes). A polling device lists the folder, applies (idempotently) any chunk whose `frontierHeads` are not already in its doc heads, **then verifies the apply actually landed (no missing causal deps left buffered — Requirement 5a)**, and derives everything else from the doc's real heads. The whole-doc base envelope stays maintained (Requirement 7) for first-load / new-device / mixed-fleet compatibility.
5. **B2 — `applyChanges` delta projection (reuse, do not duplicate).** The worker's `applyChanges` hook (applyAndProject.ts:339-345) today pushes a **FULL** projection (`pushProjection(doc)`, line 343). Change it to the **same guarded delta pattern already used by the merge branch** (applyAndProject.ts:308): capture `localHeads` before applying, then `pushDeltas(projectionDeltasBetween(currentDoc, localHeads, newHeads) ?? buildFullProjection(currentDoc))`. Add `getChangesSince`/`applyChanges` to `HEAVY_METHODS` (docClient.ts:314-319, one line each) so a large incremental apply gets the 120s ceiling, not 45s.
   5a. **B2 — `applyChanges` silently BUFFERS changes with missing dependencies; detect it, don't assume it threw.** VERIFIED against `@automerge/automerge` 3.2.6 (`implementation.d.ts:463-465`): `Automerge.applyChanges` does **not** throw when a change's causal dependencies are absent — "those will be stored in the document and applied when the depended-on changes arrive." Two consequences the transport MUST honour: (a) apply the changes of ALL selected chunks in **one** `applyChanges` call so intra-batch deps resolve in a single pass; (b) because a genuinely unsatisfiable dep produces **no error and no heads advance** (the change sits buffered, invisible, and the same chunk is re-selected every poll forever), after applying the worker MUST verify the apply landed — the applied chunks' `frontierHeads` are now all in `getHeads(currentDoc)` (equivalently `Automerge.getMissingDeps(currentDoc, [])` reports none of the just-applied frontiers). If any applied frontier is still missing → the incremental path returns `{ outcome: 'fallback', reason: 'missing-deps' }` and the whole-doc base adopt (which carries every dep) reconciles. The `applyChanges` worker hook therefore returns not just `heads` but a `landed: boolean` (all requested frontiers now in heads) so the caller can branch without re-deriving. This is the ONLY correct way to detect a stranded chunk given silent buffering; a thrown-error-only fallback would miss it.
6. **Correctness parity (non-negotiable).** Incremental transport must yield the SAME merged state as today's whole-doc merge. Cross-device convergence must not regress. `dirty` derivation (the re-upload trigger) must stay correct so no unsynced edit is dropped and no ping-pong is introduced — reusing the same `getChangesSince`-based signal as `mergeDocs` (Requirement 6a).
   6a. **`dirty` under B2 reuses one signal, computed from chunk-carried frontier heads (no manifest), and ONLY after the apply landed.** `mergeDocs` computes `dirty = Automerge.getChanges(remote, merged).length > 0` (docOps.ts:85). The applyChanges path has no separate `remote` doc, so compute the byte-equivalent from the **remote frontier** = the union of the `frontierHeads` carried in the chunks just applied (plus the current base heads): `dirty = getChangesSince(mergedDoc, remoteFrontierHeads).length > 0`. **Precondition (ties to Requirement 5a):** this is computed ONLY on the `landed` path — i.e. after confirming every applied chunk's frontier is now in `getHeads(mergedDoc)`. Computing `getChangesSince(doc, remoteFrontierHeads)` against a frontier that references still-buffered (unapplied) changes is undefined — `getChanges(view(doc, heads), doc)` can crash or mis-signal when `heads` aren't materialized in `doc` (`getChanges` "will crash if there are changes in oldState which are not in newState", `implementation.d.ts:449`). The missing-deps path falls back before `dirty` is ever derived, so `dirty` is only ever computed against a fully-applied frontier — keeping it byte-identical to `mergeDocs`'s truth table (a merged doc that advanced beyond the remote frontier means local carried unsynced changes → re-upload). This reuses the existing `getChangesSince` helper — no new dirty logic is invented.
7. **Backward compat + mixed fleet.** Existing `.beanpod` V4 files (no change-log) load and sync exactly as today. A device on an old build (or with `docWorker` OFF) that only understands the whole-doc envelope must still fully interoperate — so incremental clients keep the whole-doc base envelope current. No re-login; `.beanpod` V4 base shape unchanged (the change-log is additive Drive objects, not a V4 field change). Rides the EXISTING `docWorker` kill-switch (rollback = flip flag + redeploy). **This "keep the base current forever" contract is a documented, bounded complexity tax with a sunset criterion — see Open Question 4; it is NOT permanent by default.**
8. **No silent failures — reuse the existing error channel.** Every new decrypt / applyChanges / manifest-parse / provider-list path is wrapped in try/catch and routed through the **existing** channels: worker-side via the `sink.perf`/`sink.cachePersistFailed` signals + `console.error('[applyAndProject] …')` / `console.warn('[docOps] …')` prefixes already in use; main-side via `reportError({ surface: 'doc-worker-…' })` (`@/utils/errorReporter`) + `showToast` (`@/composables/useToast`) + docClient's `surface()`/`quiet` classifier (docClient.ts:414). Do NOT add a new error channel or banner. Any incremental path that cannot proceed safely **falls back to the whole-doc path** (a correct, slower answer) — including the silent-buffering "missing-deps" case (Requirement 5a), which produces no error to catch and must be detected by the explicit heads-landed check — and logs a non-critical breadcrumb via the same `console.warn('[syncService] …')` + `reportError` pattern the poll-tick catch already uses (syncService.ts:128-129); a wrong delta is never acceptable.
9. **Telemetry.** The poll path reports the incremental apply cost (reusing the `sink.perf` relay → `automerge.*` labels) so the warm-path load-time target is measurable against the Layer-1 `automerge.remoteLoad` / `automerge.pushProjection` baseline. A `missing-deps` fallback is counted (a distinct `perf`/breadcrumb label) so an unexpectedly high rate — the signal that pruning is stranding slow peers — is visible rather than silent.
10. **B2 provider extension (gating).** Extend `StorageProvider` with an OPTIONAL, additive multi-object API (`listAux`/`readAux`/`writeAux`/`deleteAux` scoped to the family folder), implemented for `GoogleDriveProvider` and, where feasible, the file-based providers. Absent-method → the provider does not participate in incremental transport and stays whole-doc-only (graceful, logged degradation). `listAux()` returns the append-only chunk object names (the folder listing IS the change-log index — no separate index object to maintain or race). This is the largest single piece of B2 and its risk gate (see Important Notes).

## Important Notes & Caveats

- **B1 and B2 are separable; sequence B1 → B2, and B2 may split to its own issue.** B1 (incremental persistence) is worker-internal, low-risk, and closes a real acceptance criterion (backgrounding window) on its own. B2 is the larger, higher-risk piece — and planning verified the provider is single-file, so B2 must first build a multi-object provider extension (Requirement 10) before any change-log work. Ship B1 first behind the same flag; land B2 as a second phase within this plan **with its own test gate**, and if the provider extension proves heavy, promote B2 to a separate issue rather than bloating this one. This gives a natural checkpoint and isolates the risky transport change.
- **One delta primitive for everything (DRY).** B1 persistence, B2 transport, and the B2 `applyChanges` projection all reuse the SAME two existing helpers: `docOps.getChangesSince(doc, heads)` (capture) and `docOps.applyChanges(doc, changes)` (apply), plus `projectionDeltasBetween` + `pushDeltas` for the projection. Do NOT introduce `saveIncremental`/`loadIncremental` as a parallel mechanism (see Assumptions) and do NOT invent a second delta path. One capture primitive, one apply primitive, one projection-delta path for mutate, merge, and applyChanges.
- **Two cursors, both DERIVED, never a stored source of truth (no drift).** B1 and B2 each track a heads cursor, and they are **distinct concerns that must not be conflated**: (a) the **cache-persist cursor** `lastPersistedHeads` (B1) = "what have I written to the local IDB increments", and (b) the **Drive-publish cursor** (B2) = "what heads have I published to Drive as base+chunks". CRITICAL invariant: **neither cursor is an independent durable source of truth.** The single source of truth is always the doc's real heads (`Automerge.getHeads(currentDoc)`) plus the objects actually present in IDB / Drive. On worker respawn or page reload, both cursors are RE-DERIVED from the reconstructed doc and the present objects — they are in-memory memos, never separately persisted values that could drift from the doc (the classic `lastPersistedHeads`-vs-real-heads dual-source-of-truth bug this plan explicitly avoids). See Approach for the derivation of each.
- **`applyChanges` currently clones the whole doc** (`Automerge.applyChanges(Automerge.clone(doc), changes)`, docOps.ts:63) — a redundant whole-doc load, the same defect Layer 1 removed from `mergeDocs`. Apply in place (`Automerge.applyChanges(doc, changes)` — the WASM handle applies in place and only reads `changes`; reassign `currentDoc`) with the same actorId/exception-safety reasoning Layer 1 pinned for `mergeDocs` (`docs/plans/2026-07-06-worker-ios-large-doc-load.md:60`,103). A mid-`applyChanges` throw is near-unreachable (changes already decrypted+validated); if it ever proves flaky, escalate to a `needsRehydrate` rather than re-introducing a clone. **`applyChanges` silently BUFFERS a change whose deps are absent (it does NOT throw — `implementation.d.ts:463-465`); it therefore also never throws "missing dep", so the caller must detect a stranded chunk by checking heads advanced / `getMissingDeps`, not by catching (Requirement 5a).** NB: for the B1 _cache reload_ path (building a doc from base+increments), in-place apply is unconditionally safe (no live handle is shared), and increments are always applied in seq order so their deps are present by construction.
- **B1 persist + re-compaction must be single-flight (they mutate shared `seq`/`lastPersistedHeads`/row state that the old whole-doc persist did not).** The current `persistNow` is safely re-entrant only because a whole-doc `saveDoc` is idempotent/last-write-wins with no cursor. B1 gives it mutable state (the `seq` counter, `lastPersistedHeads`, and the `inc:*` rows), and `persistNow` CAN overlap itself (a debounce-fired persist already awaiting IDB while `flush()` calls `persistNow` again). The **synchronous** capture (`doc`/`captureHeads`/`changes` read before the first `await`) is atomic under the single-threaded FIFO — that reasoning holds — but two overlapping _async_ persists (or a persist overlapping a re-compaction that clears rows + resets `seq`) can regress `lastPersistedHeads` or interleave an `inc:*` write with a `changes/` reset. Serialize them with a single-flight guard (an in-flight `persistPromise` that `flush`/`schedulePersist`/re-compaction await and chain onto), so at most one persist-or-compaction runs at a time. Increment `seq` synchronously at capture (before any await) so even a bug in the guard can't mint two rows with the same key. Reload stays correct regardless (idempotent apply), but the guard keeps the log clean and the cursor monotonic.
- **The cold-load floor is out of scope and must NOT be silently promised.** No history compaction/truncation (ADR-032 rejected it; #42 out-of-scope). The plan's iOS load-time target is the warm/poll path. Say so in the acceptance criteria; do not write a criterion that implies a fast first cold load.
- **`dirty` / re-upload correctness is the highest convergence risk.** Preserve the exact truth table from Plan A (`docs/plans/2026-07-05-automerge-web-worker.md:86`): remote-ahead-local-clean → false; local-had-unsynced → true; concurrent → true; no-op → false. Under B2 reuse the `getChangesSince`-based signal against the chunk-carried `remoteFrontierHeads` (Requirement 6a), computed ONLY after the apply landed (Requirement 5a) so the frontier is materialized, so the truth table is byte-identical to `mergeDocs`, not a re-derivation. A wrong `dirty` either drops an unsynced edit (data loss) or re-introduces save ping-pong.
- **No shared mutable manifest — the change-log is append-only, immutable, self-describing chunks (concurrency safety on a transaction-less store).** Drive/FSA have no transactions and no CAS. A single `manifest.json` rewritten by every publishing device is a lost-update race that orphans chunks. Instead: each device writes ONLY its own uniquely-named `changes/<deviceActorId>-<seq>.beanchanges` objects (append-only, never mutated after write), and the **folder listing (`listAux()`) is the index**. A reader lists, then applies (idempotently — `Automerge.applyChanges` on an already-known change is a no-op) any chunk whose `frontierHeads` aren't already in its doc heads. There is no shared object any two devices write, so there is no manifest race, no lost update, and no orphaned-because-clobbered chunk.
- **Chunk wire encoding must delimit the `Uint8Array[]` (build-time detail, called out so it isn't fumbled).** A chunk's plaintext is `{ changes: Uint8Array[], frontierHeads: Heads }`; AES-GCM encrypts _bytes_, not a JS object, so the encode step (new helpers in `fileSync.ts`, mirroring `reEncryptEnvelope`/`parseBeanpodV4`) must serialize to a single buffer that **length-prefixes each individual change** (and the frontier-heads string list) so `parse` restores the exact array boundaries — never a naive concatenation of the changes into one ambiguous blob (that loses the per-change split `applyChanges(Change[])` needs). Each Automerge change is already an opaque length-known binary; a simple `[count][len,bytes]…` frame (or the existing envelope helper's framing) is sufficient. The base64 and `postMessage`/structured-clone hops preserve `Uint8Array` bytes intact — no data-shape risk there; the only risk is the encode/decode framing, which a round-trip unit test pins.
- **Change-log compaction is NOT history compaction, and it is bounded even if the writer never returns.** Compacting the _log_ = rewriting a fresh whole-doc base envelope (loss-less `save()`) and pruning change chunks now provably included in the base heads. It does not truncate Automerge history. Prune a chunk ONLY when `getChanges` proves its changes are in the base heads AND it is older than a safety window (so a slow-polling peer isn't stranded — a too-aggressive prune is exactly what turns into a `missing-deps` fallback, so the safety window is the real knob and its fallback rate is telemetered per Requirement 9). Concurrent compaction/prune is safe: `deleteAux` of an already-deleted or mid-read chunk is a no-op for the deleter and, for a reader, resolves via the whole-doc fallback (a missing chunk → whole-doc base adopt). **Growth bound:** because compaction is opportunistic, a family whose only recent writer went offline could otherwise grow the log unbounded. So **any** incremental device — not only the one that wrote the base — enforces an opportunistic ceiling: past a chunk-count/age ceiling it triggers a base re-compaction + prune on its next save. This keeps `changes/` bounded regardless of which device returns.
- **Encryption unchanged in kind.** Each change chunk is encrypted with the same family key (AES-GCM) via the **existing** `encryptPayload`/`decryptPayload` (`familyKeyService`) that `docOps`/`cache` already use. `wrappedKeys`/`inviteKeys`/`passkeyWrappedKeys` live ONLY in the base envelope (as today) — the change-log carries ciphertext changes + (encrypted) frontier heads, never key material.
- **Mixed-fleet during a service-worker update is the real backward-compat hazard** (not just legacy files). Because a family's devices update the PWA at different times, an incremental device and a whole-doc device can be live simultaneously on the same Drive files. Incremental clients therefore keep the whole-doc base current so a whole-doc client always has a coherent file; the change-log is purely additive for incremental readers. A whole-doc client's write (whole base overwrite) must not silently orphan the change-log — on the next incremental poll, if the base heads have advanced beyond what a chunk represents, the incremental client detects it (base-heads ⊋ chunk frontier) and reconciles (fall back to a whole-doc `mergeRemoteEnvelope(base)` adopt, then resume incremental). This detection is a normal branch, logged via the existing breadcrumb pattern. **This whole contract is bounded by the Open Question 4 sunset, not carried forever.**
- **Do NOT build a base-write coalescer in v1.** The plan's dual-publish (base + chunk) publishes BOTH on every save initially — the simplest correct thing. Only add base-write coalescing later, and only if telemetry shows the redundant base write is a measured cost. Building a separate coalescing cadence up front is premature optimization and added state to get wrong.
- **Keep the incremental poll behind a clean seam — no deep nesting in `fetchAndMergeRemote`.** The incremental path (list → fetch new chunks → apply → confirm landed → derive dirty → fallbacks) must NOT be inlined into `fetchAndMergeRemote` (already a branching function). Extract it as a single-purpose `fetchAndApplyIncremental()` returning a discriminated result — `{ outcome: 'applied'; dirty } | { outcome: 'fallback'; reason }`. `fetchAndMergeRemote` becomes: "if aux present, try incremental; on `fallback`, run the EXISTING whole-doc merge path unchanged." The whole-doc path stays the single, untouched fallback sink; the incremental path is independently testable and cannot deepen the existing function's nesting.
- **Validate against a FRESH dev server** (lessons.md #15 — a warm server serves stale worker code and false-greens). B2 additionally needs a two-device test (worker device ↔ inline/whole-doc device) to prove mixed-fleet interop.
- **Do NOT move Drive auth/token logic into the worker** (Plan-A boundary). Provider I/O (list/fetch/write of change chunks + base) stays on main; the worker decrypts/applies chunk ciphertext and produces chunk ciphertext to upload — same "ciphertext in / ciphertext out" split as today.

## Assumptions

> Review before implementation.

1. **RESOLVED during planning — use the existing `getChangesSince`, not `saveIncremental`.** Verified against `node_modules/@automerge/automerge` (3.2.6): `saveIncremental`, `loadIncremental`, `getChanges`, `applyChanges`, `view`, `diff`, `getMissingDeps` all exist. But `docOps.getChangesSince(doc, heads)` (docOps.ts:58-60) already wraps `getChanges(view(doc, heads), doc)` — the exact primitive we need — and it does NOT depend on `saveIncremental`'s handle-bound internal "last saved" cursor, which is fragile because the worker reassigns `currentDoc` on every mutate/merge. **B1 therefore captures deltas with `getChangesSince(currentDoc, lastPersistedHeads)` and an explicitly-tracked (in-memory, derived) `lastPersistedHeads`, and reloads with `applyChanges`.** This removes the original Assumption-1 verification risk entirely and unifies B1 with B2 on one primitive.
2. `Automerge.applyChanges` applied to the live handle in place (dropping the redundant `clone`) converges identically to a whole-doc merge for the same change set (Layer 1 established the in-place semantics for `merge`; the WASM binding applies in place and only reads `changes`). **Also VERIFIED against the API surface and asserted by tests: (a) applying a change already present in the doc is an idempotent no-op — this is what makes list-and-apply safe without a mutable cursor; and (b) applying a change whose causal deps are absent does NOT throw — it is buffered silently and does not advance heads (`implementation.d.ts:463-465`), so a stranded chunk is detected by a heads-landed / `getMissingDeps` check, never by a thrown error (Requirement 5a).**
3. **CONFIRMED single-file provider — B2 needs a provider extension.** `StorageProvider` (storageProvider.ts) exposes only `write`/`read`/`getLastModified`. Google Drive DOES allow per-family sibling objects, but the abstraction hides that today. B2 must add the optional multi-object API (Requirement 10) before change-log work; this is scoped INTO B2 and flagged as its risk gate.
4. The worker-path telemetry (`automerge.remoteLoad`/`pushProjection`) needed to set a numeric warm-path target is available from greg's own devices / a `docWorker`-on cohort. Since `docWorker` is prod-off, a fleet-wide baseline may not exist yet — the target is calibrated from greg's device numbers + the Layer-1 spike, and refined once `docWorker` is on. (Resolves Open Question 3.)
5. Persist-on-every-mutation (B1) at the incremental cost does not itself create IDB write pressure that regresses mutation latency; a small coalesce (the existing 120ms `PERSIST_DEBOUNCE_MS`) is retained as a safety valve, not removed to zero. A no-op capture (`getChangesSince` returns `[]`) skips the IDB write entirely.
6. **A folder listing per Drive poll is an acceptable cost.** Drive uses save-time `fetchAndMergeRemote` (not a 15s poll), so one `listAux()` HTTP call per save/poll is the right shape; FSA directory enumeration is cheap. If a future high-frequency poller adopts this, revisit (not in scope).

## Approach

### Phase B1 — Incremental cache persistence (worker-internal, ship first)

**Goal:** persist a delta, not the whole doc, so persistence can run ~per mutation → the backgrounding last-edit-loss window closes.

- **Cache schema (cache.ts:32-42) — keep ONE object store, no version bump.** The existing `doc` store is keyed by `id`. Reuse it: a `base` row (whole-doc `save()` binary, encrypted, as today) + `inc:<zero-padded-seq>` rows (each an encrypted delta chunk from `getChangesSince`). IDB string keys sort lexicographically, so zero-pad the seq for correct increment ordering on load. **Load increments via an `IDBKeyRange.bound('inc:', 'inc;')` range query** (`'inc;'` is the next char after `'inc:'`), so the load reads ONLY increment rows in key order — it never scans/materializes the `base`/`envelope` rows, and ordering is free. This avoids an `openDB` version migration and reuses `withIdbRetry`/`encryptPayload` verbatim. **Backward-compat:** a legacy cache holds only `DOC_KEY='current'` and no `base`/`inc:*` rows → `loadCachedDoc` treats `current` as the base (zero-increment load). Keep `ENVELOPE_KEY`. One-writer invariant preserved (worker owns the cache).
- **Seq generation survives respawn.** On cache open, initialize the in-memory `seq` counter from the highest existing `inc:*` key (a single reverse range read), NOT from 0 — otherwise a worker respawn without a preceding re-compaction could reuse `inc:00001` and clobber a not-yet-superseded increment. Seq is monotonic within a base epoch and resets to 0 only when re-compaction clears all `inc:*` rows.
- **Persist (applyAndProject `persistNow`, applyAndProject.ts:105-126) — single-flight.** Replace the whole-doc `saveDoc` with, computed atomically from ONE doc snapshot: `const doc = currentDoc; const captureHeads = headsOf(doc); const changes = changesSince(doc, lastPersistedHeads);` — if empty → return (no IDB write); else claim the next `seq` **synchronously** (before any await), encrypt just that chunk, append an `inc:<seq>` row, and only AFTER the IDB write resolves set `lastPersistedHeads = captureHeads`. CRITICAL: advance to `captureHeads` (the heads of the exact snapshot the changes were captured from), NOT a re-read of `headsOf(currentDoc)` after the await — `currentDoc` may have advanced during the IDB write, and re-reading its heads would skip the intervening mutation from the next capture (silent loss). **Serialize persist + re-compaction behind one in-flight `persistPromise` (single-flight, Important Notes):** `flush`, the debounce, and re-compaction all await/chain onto it so two persists (or a persist and a compaction) never interleave their shared `seq`/`lastPersistedHeads`/row mutations. Because the chunk is tiny, `schedulePersist` may keep the 120ms coalesce as a safety valve (Assumption 5). Rename the perf label `automerge.save` → `automerge.saveIncremental` with `perf_chunk_bytes`. Persist failure keeps reusing the EXISTING `sink.cachePersistFailed(true)` durability signal (applyAndProject.ts:121) — no new banner, and `lastPersistedHeads` is NOT advanced on failure (the chunk will be re-captured next tick).
- **Load (cache.ts:86-99).** `loadCachedDoc` reads `base` (or legacy `current`), `loadAndVerify`s it (unchanged materialize check), then applies `inc:*` rows in seq order via `docOps.applyChanges` (in-place, safe here — deps present by construction since increments are applied in order). **Partial-recovery on a bad increment (data-integrity hardening):** if increment at seq _k_ is missing/corrupt/won't apply, load base + increments `[0..k-1]` (every increment BEFORE the first failure — preserving as much durable unsynced tail as possible), then STOP, `console.warn('[cache] …')` breadcrumb, and schedule a re-compaction. Do NOT discard all increments (that would drop every persisted mutation after a single mid-log corruption — unacceptable for a finances doc). Never a silent partial without the breadcrumb.
- **Base re-compaction.** When increments exceed a threshold (count or bytes), rewrite `base = saveDoc(currentDoc)` (whole, loss-less), delete all `inc:*` rows, reset `seq` to 0, reset `lastPersistedHeads` to current heads. Runs off the debounce, opportunistically (after N increments or on the visibility flush), **inside the single-flight guard** so it never races a persist. Bounds cache size and cold-reload cost.
- **`lastPersistedHeads` lifecycle (in-memory, derived).** Module state in applyAndProject, **initialized from the reconstructed doc's real heads** on `initAndLoadCache`/`mergeRemoteEnvelope`-adopt/`initDoc`/`openCache`+flush, advanced on each successful incremental persist (to that persist's `captureHeads`), reset on re-compaction and `reset()`. It is never persisted as its own row — it is always recoverable as `headsOf(currentDoc)` at the moment the last increment was written, which after any reload equals the heads of the reconstructed doc. This keeps a single source of truth (the increments actually in IDB) and makes drift structurally impossible.
- **Backgrounding flush (`flush`, applyAndProject.ts:365-371).** With per-mutation incremental persist, the `visibilitychange:hidden` flush now flushes a tiny pending chunk (or nothing) — the ≤coalesce window shrinks to ~one mutation. Update the Plan-A limitation note honestly: a hard kill between a mutation and its ~immediate incremental persist is the only residual, far smaller than the old debounce window.
- **No Drive changes in B1.** The Drive write path still exports the whole `encryptedPayload` (`exportEncryptedPayload` → `reEncryptEnvelope`). B1 is purely the local cache — small, independently shippable.

**Goal:** a poll applies KB of peer changes instead of loading the whole 2 MB remote.

- **Drive layout (append-only, no shared mutable object).** Beside the family `.beanpod` (whole-doc base envelope, unchanged shape), add a `changes/` folder of:
  - `changes/<deviceActorId>-<seq>.beanchanges` — each an encrypted (family key, AES-GCM via existing `encryptPayload`) **self-describing** chunk containing `{ changes: Uint8Array[], frontierHeads: Heads }`, length-delimited on the wire (Important Notes — the `Uint8Array[]` must survive the encode/decrypt/`postMessage` round-trip with its array boundaries intact), append-only, written only by its owning device and never mutated after write.

- **Poll — extracted `fetchAndApplyIncremental()` (clean seam, Important Notes).** Returns `{ outcome: 'applied'; dirty } | { outcome: 'fallback'; reason }`:
  1. `listAux()` the `changes/` folder; select chunks whose `frontierHeads` are NOT already in the local doc heads (derive the "already applied" set from the doc's real heads — a chunk fully covered by current heads is skipped; if in doubt, apply anyway — it's an idempotent no-op).
  2. Fetch + decrypt only those chunk ciphertexts; post the **union** of their `changes` to the worker in ONE `applyChanges` call (in place, delta projection per Requirement 5) so intra-batch deps resolve in a single pass.
  3. **Confirm the apply landed (Requirement 5a):** the worker's `applyChanges` returns `{ heads, landed }` where `landed` = every selected chunk's `frontierHeads` is now in `getHeads(currentDoc)` (no change left buffered on a missing dep). If `landed` is false → return `{ outcome: 'fallback', reason: 'missing-deps' }` (a slow-peer prune stranding; the whole-doc base carries the deps). Do NOT derive `dirty` in this case.
  4. On `landed`: derive `dirty` per Requirement 6a from the union of the applied chunks' `frontierHeads` (+ base heads); if local carried unsynced changes, `triggerDebouncedSave()`. Return `{ outcome: 'applied', dirty }`.
  5. **Return `{ outcome: 'fallback', reason }` (never throw into the caller)** on: no aux support / any chunk decrypt or applyChanges _error_ / the `missing-deps` non-landed case (step 3) / a base-envelope mtime advance beyond the chunks (base heads ⊋ all chunk frontiers). `fetchAndMergeRemote` then runs the EXISTING whole-doc `mergeRemoteEnvelope(base)` adopt unchanged, logs a non-critical breadcrumb (`console.warn('[syncService] …')` + `reportError`, with the `reason` labeled so a `missing-deps` spike is visible per Requirement 9), and resumes incremental next tick.
- **Write (syncService.doSave, syncService.ts:715+).** On a local change that must publish: `exportIncrementalPayload(sinceHeads)` (new client method mirroring `exportEncryptedPayload`, wrapping the worker's `getChangesSince`+`getHeads`+encrypt into a self-describing, length-delimited `{ changes, frontierHeads }` ciphertext) → `writeAux('changes/<thisDevice>-<seq>.beanchanges', …)`, AND keep the whole-doc base current (Requirement 7 — `exportEncryptedPayload` + `reEncryptEnvelope` + `write` exactly as today). The **Drive-publish cursor** `sinceHeads` is DERIVED, not stored: it is the heads of the base this device last published (recoverable from the just-written base's heads / `getHeads` after the previous publish). On the first publish after reload, if the derived cursor is unknown, publish a chunk from the base heads (correct, at worst a slightly larger first chunk). **v1 publishes BOTH base + chunk every save** (no coalescer — Important Notes); measure before optimizing.
- **`applyChanges` delta projection (applyAndProject.ts:339-345).** Change `pushProjection(doc)` → capture `localHeads` before applying, then `pushDeltas(projectionDeltasBetween(currentDoc, localHeads, newHeads) ?? buildFullProjection(currentDoc))` — identical guarded pattern to the merge branch (applyAndProject.ts:308). The hook additionally returns `landed` (Requirement 5a). Drop the redundant `clone` in `docOps.applyChanges` (docOps.ts:63). Add `getChangesSince`/`applyChanges` to `HEAVY_METHODS` (docClient.ts:314-319).
- **Compaction of the change-log (bounded, Important Notes).** A device that just wrote the whole base prunes chunks provably included in the base heads and older than a safety window via `deleteAux`. **Additionally, ANY incremental device enforces an opportunistic count/age ceiling** (triggers a base re-compaction + prune on its next save) so the log stays bounded even if the original writer never returns. Idempotent and safe under concurrent prune (deleting an absent chunk is a no-op; a reader that hits a just-deleted chunk falls back to whole-doc adopt). The safety window is sized to keep the `missing-deps` fallback rate (Requirement 9 telemetry) near zero.
