# Plan: Native app store / play store release readiness

> Date: 2026-07-08
> Related issues: None — direct implementation
> Plan file: `docs/plans/2026-07-08-native-store-release-readiness.md`

## User Story

As the beanies.family publisher, I want the Capacitor iOS + Android apps to be fully submission-ready — every code/config gap closed and a clear submission runbook in hand — so that the moment the Apple and Google organization accounts finish verifying, I can build, sign, and submit to both stores without discovering blockers mid-flight.

## Context

Org enrolment for both Apple Developer Program (Organization) and Google Play Console (Organization) was kicked off 2026-07-08 and is pending verification (gated on the now-obtained D-U-N-S). The Tinfoil DPA (AI data processor) is signed. Per ADR-029 the native apps are "built-and-dormant": both `ios/` and `android/` Capacitor 8 projects exist, OAuth/filesystem code is implemented, icons/splash/portrait-lock are present, and four CI lanes exist (two active validation lanes; two dormant signed-release lanes). A readiness audit this session found the remaining gaps are almost entirely (a) a handful of concrete file additions and (b) values that can only be filled after the store accounts approve (Apple Team ID, Play App Signing SHA-256). This plan closes the code/config gaps now and documents the account-gated steps and validation milestones as a runbook, so nothing is discovered late.

Key architectural facts confirmed by reading the repo (do not re-derive):

- **Two `.well-known` origins, two purposes.** `public/.well-known/` is served from **app.beanies.family** (Vue app / S3+CloudFront via `deploy.yml`, which sets `include-hidden-files: true`) and hosts the **passkey** association (`assetlinks.json` → Android `delegate_permission/common.get_login_creds`; `apple-app-site-association` → iOS `webcredentials`, already carrying a `<APPLE_TEAM_ID>` placeholder in `webcredentials.apps`). `web/public/.well-known/` is served from **beanies.family** (Astro marketing site via `deploy-web.yml`, which ALSO sets `include-hidden-files: true` — confirmed line 49) and hosts the **OAuth App Link** association (`assetlinks.json` → Android `delegate_permission/common.handle_all_urls` for `https://beanies.family/oauth/native`). The iOS OAuth Universal Link association (`applinks`) on **beanies.family** does **not** exist yet. (Relation strings confirmed by reading both live files: `get_login_creds` for passkeys, `handle_all_urls` for the OAuth App Link — do not swap them; a wrong relation string silently fails verification with no error.)
- **Android App Link intent filter is already wired (confirmed).** `android/app/src/main/AndroidManifest.xml` already declares an `<intent-filter android:autoVerify="true">` with `VIEW` + `BROWSABLE`, `android:scheme="https"`, `android:host="beanies.family"`, `android:pathPrefix="/oauth/native"`. So on Android the ONLY missing piece for App Link auto-verification is the Play App Signing SHA-256 in the served `assetlinks.json` (Tranche 2). Note this in the runbook so the manifest side isn't re-investigated.
- **Both native-OAuth round-trips are code-complete but never confirmed on-device**, because App Link / Universal Link verification is gated on the _release-signing_ fingerprints (Play App Signing SHA-256 for Android; real Apple Team ID for iOS) which don't exist until the accounts approve. This is the central sequencing constraint.
- **The app IS data-collecting.** `src/utils/errorReporter.ts` fires a Slack webhook enriched (via `src/utils/diagnosticContext.ts` `enrichAndRedact`, `includeEmail: true`) with error context, build SHA, and the **owner's email**, and mirrors every reported error into a telemetry firehose (`src/services/telemetry` `logEvent` → `logQueue` → the AWS ingest endpoint) that ships diagnostic events correlated by `family_id`, with `includeEmail: false`. So both stores' privacy declarations — AND the public privacy policy — must declare Email + Diagnostics/Crash data, NOT "no collection." (This is the single most important correction from the audit; see R13 + the privacy-policy reconciliation in R8b.)
- **The telemetry firehose is NOT currently strictly PII-free — Pass-4 correction.** `enrichAndRedact` sets `raw.family_name = ctx.activeFamilyName` and this key is on the `ALLOWED_CONTEXT_KEYS` allowlist (line 53), so it survives redaction and ships on the `includeEmail: false` telemetry path — confirmed by the existing test fixture `logEvent.test.ts`, which passes `activeFamilyName: 'Robinsons'` (a surname). A user-typed family name is commonly a surname and is therefore personal data. This directly contradicts the plan's repeated "PII-free diagnostic stream, correlated by a random family_id" framing. Resolution is baked into T1.1 (gate `family_name` behind `includeEmail`, symmetric with the existing `family_email` treatment) so the firehose becomes genuinely PII-free before any "PII-free" claim is published — see T1.1, R13, and the amended R14/Important Notes. `family_id` = `activeFamily.value?.id`; T1.1 must confirm this id is a genuinely random per-family UUID (not derived from email/name) before it is characterised as non-PII, and must evaluate whether it is a declarable Identifier (Apple "User ID" / Google "Device or other IDs").
- **Release version stamping** in both dormant lanes is hardcoded `1.0.<run#>` (`mobile-android-release.yml` `ANDROID_VERSION_NAME` line 110; `mobile-ios-release.yml` `MARKETING_VERSION` line 88, re-stamped in `Fastfile` via `xcargs`). The in-app sidebar shows `APP_VERSION` = `0.9.4R1` (`src/constants/appVersion.ts`). Decision (2026-07-08): tie the store marketing version to `APP_VERSION`, shipping as `0.9.x`.
- **Test harness reality (verified).** `vitest.config.ts` `include` is `['src/**/*.{test,spec}.ts']` (line 12) — it matches ONLY `.ts` files under `src/`. `npm run validate` runs `test:run`. There is currently **no** script-test location and no `.mjs` test is picked up anywhere (`updateTranslations.mjs`'s exports are not unit-tested by vitest). Any test for the new version helper must therefore either live under `src/` as `.ts`, or the vitest `include` glob must be widened — otherwise the test file exists but never executes (a silent coverage hole). This plan chooses the widen-the-glob path (T1.6) so the helper stays a single `.mjs` module.

## Important Notes & Caveats

- **Do NOT deploy to prod or trigger any release lane** as part of this work. The AASA/assetlinks/delete-account/privacy changes reach the live origins only on the next normal `deploy` / `deploy-web` — greg triggers those when ready. Landing on `main` is safe (inert on web; the one runtime change is the PII-reducing `family_name` gate, which only ever _removes_ a field from the telemetry payload and is covered by a test).
- **Team ID + Play cert are placeholders until the accounts approve — with ONE greppable convention where the file format allows it.** The Apple Team ID uses the literal token `<APPLE_TEAM_ID>` in every file that needs it, so `grep -rn '<APPLE_TEAM_ID>' public web ios` returns the _exact, complete_ set of pending iOS substitutions — a mechanical checklist that cannot silently miss a file. The **Play App Signing SHA-256 is the asymmetric case**: `assetlinks.json` is served, parsed JSON, so it cannot carry a `<PLACEHOLDER>` token (an invalid fingerprint string could be rejected by Android and would ship to the live origin). Its "pending" state is therefore invisible to grep. That gap is guarded three ways, all pointing at ONE authority: (1) the two-files-must-sync table in `public/.well-known/README.md`, (2) the runbook's Tranche-2 substitution checklist which links to that table rather than re-listing paths, and (3) the Tranche-3 on-device App-Links verification, which fails loudly if either origin was missed. The runbook must state this asymmetry explicitly so nobody assumes the `grep` alone is complete.
- **On-device OAuth is unverified on BOTH platforms** and cannot be verified until release-signing fingerprints exist. Treat "native Google sign-in round-trips" as a post-account validation milestone, not a done item — the audit's green marks are for _code presence_, not on-device confirmation.
- **`family_name` on the telemetry firehose is the Pass-4 correctness catch.** The plan's central privacy claim ("PII-free diagnostic stream") was false as written because a user-typed family name (often a surname) rode the `includeEmail: false` path. The fix is the mirror of the existing `family_email` gate — one `if (opts.includeEmail)` guard — so it's the simplest, most DRY, least surprising solution and introduces no new pattern. Do the fix and its test in T1.1 BEFORE authoring any "PII-free" copy, so reality and declaration are consistent by construction. If for any reason the fix is deferred, R8b/R13/R1/R7 must instead declare Name (Contact Info / user content) as collected on the diagnostic path — never publish "PII-free" over an unfixed firehose.
- **Single authority per fact — the runbook is a pointer, not a copy.** The fingerprint-fetch `keytool` commands and the two-origins sync table already live in the `.well-known/README.md` files; ADR-029 owns the native-auth architecture; the 2026-05-22 plan owns the launch-dependency Help articles. The new runbook references these and adds only the genuinely new material (store-account flow, answer sheets, substitution/validation checklists). Duplicating their content would create a second source that silently goes stale — avoid it.
- **iOS `CFBundleShortVersionString` format is strict**: at most three dot-separated non-negative integers. `APP_VERSION` values like `0.9.4R1` are invalid and would be _rejected at upload_. The derivation helper must strip the `R<n>` suffix. Android `versionName` is freeform but uses the same derived value for consistency.
- **The version helper's coupling to `appVersion.ts` is text-level and must fail loud, and is guarded at CI time.** `readAppVersion` extracts the `APP_VERSION` string literal by matching the `export const APP_VERSION = '…'` line (same technique as `updateTranslations.mjs`). This is a deliberately narrow, stable contract: input is the file text, output is the bare version string, failure mode is a thrown `Error` (never an empty/`1.0` fallback). Because text-matching a source file is inherently reformat-sensitive, the real-file guard test (T1.6) parses the _actual_ `appVersion.ts` on every `npm run validate` — so if a future refactor moves the constant to a template literal or renames it, the breakage surfaces in normal CI, not at release time in a dormant lane.
- **CI command-substitution is a silent-failure trap.** You cannot put `$(node …)` inside a YAML `env:` mapping (it is a literal string there, not shell). The derivation must run in a dedicated `run:` step with `set -euo pipefail`, capture stdout into a variable, and export it via `$GITHUB_ENV`; a bare `VAR=$(node …)` without `set -e` would swallow a non-zero exit and stamp an empty version. See T1.6.
- **The `/oauth/native` web fallback page exists** — confirmed at `web/src/pages/oauth/native.astro`. The App Link/Universal Link lands there when the app can't claim the URL (pre-verification window, app-not-installed). Verify it handles the redirect during Tranche-3 on-device testing; nothing to create here.
- **The public privacy policy currently says "we collect nothing."** This is now false (errorReporter email + telemetry firehose) and, left unchanged, would contradict the store data-safety forms and risk rejection. R8b + T1.9 reconcile it. This is copy-only — no runtime change.
- **Privacy manifest completeness can only be fully validated in an Xcode/macOS build** — App Store Connect's automated check runs at upload. Pre-populate from the known plugin set + the R13 data list; treat the first TestFlight upload as the confirmation gate (documented as such, not a silent assumption).
- **The "Install the app" / "Reminders & notifications" Help Center articles** from the 2026-05-22 plan are a launch dependency tracked under that plan, NOT re-scoped here (this plan is compliance/config, no new user-facing feature) — noted so the omission is intentional.
- **AASA serving on Astro (`web/`)**: Astro copies `public/` verbatim, and `deploy-web.yml` already sets `include-hidden-files: true` (line 49, added when `web/dist/.well-known/` was silently dropped), so the extensionless dotfile survives the deploy artifact. The remaining unknown is the served `Content-Type` (`application/json` for an extensionless file) — a post-deploy curl check (T1.8), fixable in the S3/CloudFront config if wrong.

## Assumptions

> **Review these before implementation.** Valid at planning time; may have changed.

1. `appId` / bundle id `family.beanies.app` is final and will not change before first publish (permanent once published; confirmed in ADR-029 Assumption 1 and `capacitor.config.ts` line 4).
2. The existing Google **Web** OAuth client already has `https://beanies.family/oauth/native` registered as an authorized redirect URI (greg-side Track-0 item from the 2026-05-22 plan). If not, iOS/Android OAuth fails with `redirect_uri_mismatch` regardless of this plan — verify.
3. Cloud-managed automatic signing (ASC API key + `-allowProvisioningUpdates`) can provision the Associated Domains capability once the App ID has it enabled; if Apple rejects automatic signing for the entitlement, the runbook's fallback is enabling the capability manually on the App ID (no code change).
4. `APP_VERSION` remains the single human-facing product version and will be bumped per its documented convention; the store marketing version is _derived_ from it, not maintained separately.
5. Local notifications stay deferred (ADR-029 Phase 2); no `POST_NOTIFICATIONS` / notification-permission work in this plan.
6. Sign in with Apple stays reactive-only (add only if App Review rejects); not pre-built here.
7. The telemetry firehose (`logEvent`) and `errorReporter` transmit only the fields enumerated by the R13 audit (the `ALLOWED_CONTEXT_KEYS` allowlist + system fields + owner email on the Slack path). The audit must confirm `family_id` is a genuinely random per-family UUID (not derived from PII) and that, after T1.1, `family_name` no longer rides the telemetry path; if the audit finds additional off-device fields (e.g. IP captured server-side at the AWS ingest endpoint, or a per-install/device identifier), the declaration lists — and the privacy-policy copy — expand accordingly.

## Approach

Three tranches. **Tranche 1 is the entirety of this plan's code/config work** — landable on `main` now, inert on web except the single tested PII-reducing firehose fix in T1.1. Tranches 2–3 are documented in the runbook and executed after the accounts approve (no code in this plan).

### Tranche 1 — code/config (implement now)

**T1.1 — Data-collection source of truth + firehose PII fix (do FIRST; everything privacy-facing depends on it).**
Read `src/utils/diagnosticContext.ts` (`ALLOWED_CONTEXT_KEYS` allowlist, `enrichAndRedact`'s `includeEmail` gating, the system fields written on top) and `src/services/telemetry/*` (`logEvent` input + `LogRecord` schema, `logQueue` ship shape). Enumerate every field that leaves the device and every destination (Slack webhook, AWS ingest endpoint).

- **Firehose PII fix (the one runtime change, R14).** `enrichAndRedact` currently sets `raw.family_name = ctx.activeFamilyName` unconditionally, and `family_name` is on `ALLOWED_CONTEXT_KEYS`, so a user-typed family name (often a surname) ships on the `includeEmail: false` telemetry path — confirmed by `logEvent.test.ts` asserting `family_name` for fixture `'Robinsons'`. Move the `family_name` assignment inside the existing `if (opts.includeEmail) { … }` block (exactly where `family_email` already lives), so the human-readable name ships ONLY on the operator Slack error path (which already carries the owner email) and NEVER on the telemetry firehose. This makes the firehose genuinely PII-free (only the random `family_id` UUID correlates events), so every "PII-free diagnostics" claim downstream is true by construction. Keep `family_id` on both paths. **Confirm** `activeFamilyId` is a random per-family UUID (`familyContextStore` → `activeFamily.value?.id`); if it turns out to be derived from PII, escalate — the "non-PII correlation id" framing would be wrong. Also decide explicitly whether the random `family_id` is a declarable Identifier (Apple "User ID" / Google "Device or other IDs"); default to declaring it as an app-functionality/diagnostics identifier, not-for-tracking, unless there is a documented reason it is out of scope.
- **Extend the existing test** `src/utils/__tests__/diagnosticContext.test.ts` (the `includeEmail gating` describe block): assert `family_name` is present when `includeEmail: true` and ABSENT when `includeEmail: false` (mirroring the existing `family_email` assertions). Update `src/services/telemetry/__tests__/logEvent.test.ts` if it asserts `family_name` on a firehose record (it must now assert its absence, since `logEvent` calls `enrichAndRedact(..., { includeEmail: false })`).
- **Produce one canonical table** in the runbook (R10) mapping each surviving field to {Apple `NSPrivacyCollectedDataType*`, Google Data Safety category, purpose, linked-to-identity?, tracking?}. Expected minimum AFTER the fix: Email Address (linked, App Functionality/support, not tracking — Slack path only), Crash Data (Analytics/App Functionality), Other Diagnostic Data (the PII-free firehose, correlated by random `family_id`), and — per the identifier decision above — possibly a Device/User ID row for `family_id`. This table is the SOLE input to T1.2, the store-form answers in R10, AND the public-policy disclosure in T1.9. No privacy declaration — public or store — is authored except from this table, and none is published claiming "PII-free" until the fix above lands.
- **Anti-drift comment (R13):** one line at `ALLOWED_CONTEXT_KEYS` and at the telemetry `LogRecord` schema pointing back to this table and its four consumers, so a future edit to what the app transmits surfaces the "update the privacy declaration" obligation at the edit site.

**T1.2 — `ios/App/App/PrivacyInfo.xcprivacy`.** Author from the T1.1 table:

- `NSPrivacyTracking` = `false`; `NSPrivacyTrackingDomains` = `[]`.
- `NSPrivacyCollectedDataTypes` = the T1.1 rows (email + crash + other-diagnostic, plus the `family_id` identifier row if the T1.1 decision declares it), each with its purpose array, `Linked`/`Tracking` booleans.
- `NSPrivacyAccessedAPITypes` = required-reason declarations for the app's own usage (candidates from the Capacitor plugin set: UserDefaults `CA92.1`, File-timestamp `C617.1`/`DDA9.1`, System-boot-time `35F9.1`, Disk-space `E174.1`/`85F4.1` — include only those actually reached; err toward declaring the ones the bundled plugins use).
- Audit each `@capacitor/*` dependency (`app`, `browser`, `filesystem`, `local-notifications`, `splash-screen`, `status-bar`, `@capgo/capacitor-passkey`) for its own bundled `PrivacyInfo.xcprivacy`; note any missing one as an upstream risk in the runbook (a plugin missing its manifest can block upload even when the app manifest is correct). Final confirmation = first TestFlight upload (documented gate).

**T1.3 — iOS Associated Domains entitlement.** Create `ios/App/App/App.entitlements`:

```xml
<key>com.apple.developer.associated-domains</key>
<array>
  <string>applinks:beanies.family</string>
  <string>webcredentials:app.beanies.family</string>
</array>
```

**T1.6 — Version derivation helper (shared, tested, fail-loud) + CI wiring.**

- Add `scripts/derive-store-version.mjs`. Structure it as a **pure, importable transform + a thin CLI**, so the risky logic is unit-testable without shelling out:
  - `export function deriveStoreVersion(rawAppVersion)` — strips a trailing `R\d+` suffix, validates the result is a ≤3-part dotted non-negative-integer string, returns it; throws `Error` with a clear message on any malformed input (empty, non-numeric, >3 parts, etc.).
  - `export function readAppVersion(fileText)` — extracts the `APP_VERSION` string literal from `src/constants/appVersion.ts` at the text level (same technique as `scripts/updateTranslations.mjs`'s `parseUIStrings`; throws with a clear message if the `export const APP_VERSION = '…'` line isn't found). This is a deliberately narrow contract: file text in, bare version string out, throw on miss — never a fallback value.
  - CLI (`import.meta`-guarded `main()`): read the file, call the two functions, print the result to **stdout only**, and on any thrown error print the message to **stderr** and `process.exit(1)` (mirrors `updateTranslations.mjs`'s fatal handler). Never print anything but the bare version to stdout, so `$(…)` capture is clean.
- Add the unit test `scripts/__tests__/derive-store-version.test.mjs` covering `0.9.4R1→0.9.4`, `0.9→0.9`, `1.0→1.0`, `1.2.3→1.2.3`, and malformed inputs (`''`, `'abc'`, `'1.2.3.4'`, `'0.9.4R'`) → throws. **Add a real-file guard test in the same file:** read the actual `src/constants/appVersion.ts` and assert `deriveStoreVersion(readAppVersion(realFileText))` returns a valid ≤3-part numeric — so a reformat of `appVersion.ts` (or a bad `APP_VERSION` bump) breaks `npm run validate` at once, converting a release-time-only, dormant-lane coupling into a CI-caught one. **Widen `vitest.config.ts` `include`** to `['src/**/*.{test,spec}.ts', 'scripts/**/*.{test,spec}.mjs']` — verified necessary: the current glob matches only `.ts` under `src/`, so without this the test would silently never run in `npm run validate`. Remove the old hardcoded `ANDROID_VERSION_NAME: 1.0.${{ github.run_number }}` / `MARKETING_VERSION: 1.0.${{ github.run_number }}`.
