# Plan: Account transfers + liability-aware balances (credit-card payments)

> Date: 2026-07-08
> Related issues: None — direct implementation (raised by Discord user miss.cowboy_55439)
> Plan file: `docs/plans/2026-07-08-transfers-and-liability-aware-balances.md`

## User Story

As a family member tracking finances, I want to **transfer money between my accounts** and **pay down / spend on my credit cards** so that my account balances and net worth stay correct without ghetto workarounds (manually editing two account balances).

## Context

A Discord user reported two genuine gaps: (1) you can't link a transaction to a credit card to pay it down, and (2) there's no way to transfer balance between accounts. Investigation shows the data layer is ~80% there but has **no creation UI** and **correctness bugs**:

- **`type: 'transfer'` + `toAccountId` are fully modeled and the balance cascade already debits source / credits destination** (`transactionsStore.ts` create ~380-387, update ~428-458, delete ~499-514), with a working transfers-only filter inside `AccountViewModal.vue` and orphan-safe transfer labels in `transactionLabel.ts` (falls back to `family.unknownAccount`). But **nothing creates a transfer** — `TransactionModal.vue` only offers income/expense (a binary in/out direction toggle, `effectiveType` ~307-309); there is no transfer option and no destination-account picker anywhere.
- **Balances are NOT liability-aware.** Liability balances (`credit_card`, `loan`) are stored as a **positive "amount owed"** (`isLiabilityType`, `accountNetWorthMultiplier` ×−1 for net worth — `finance.ts` 117-131). But `calculateBalanceAdjustment` (`finance.ts` 89-106) applies income `+`, expense `−`, transfer `−source/+dest` **regardless of account type**. So today:
  - An **expense on a credit card** (a purchase) _decreases_ owed — backwards; it should _increase_ owed.
  - A **transfer to a credit card** (a payoff) _increases_ owed — backwards; it should _decrease_ owed.
- **Transfers do no currency conversion** — the destination gets the raw source amount (`transactionsStore.ts` ~384-387), corrupting cross-currency transfers.

**Locked scope decisions (greg, 2026-07-08):**

1. **Unified Transfer feature** — a credit-card payment is modeled as a transfer (source → `credit_card` destination). One `transfer` type; do **not** widen the loan-linker to credit cards. Leave the loan-linker/amortization path (`LoanLinkDropdown.vue`, `applyLoanPayment`) untouched for real amortizing loans.
2. **Include the liability-sign fix** — income/expense on a `credit_card`/`loan` account, and transfers touching one, move the owed balance the correct way.
3. **Cross-currency transfers convert now** — destination delta via `src/utils/currency.ts`.

The unifying rule (verified against every case): **the balance delta applied to an account = `calculateBalanceAdjustment(type, amount, isSource) × (isLiabilityType(account.type) ? −1 : +1)`.** This one formula yields: card purchase → +owed; card refund → −owed; transfer-to-card (payoff) → −owed; cash advance (transfer from card) → +owed; all asset cases unchanged. (Pass 4 re-walked all four hard cases end-to-end, both legs of every transfer — signs confirmed correct.)

## Requirements

1. **Create a transfer** in `TransactionModal.vue`: a `transfer` mode plus a **destination account picker** (excludes the source account; orphan-safe; sensible ordering). Cleanly reconcile `transfer` with the existing income/expense direction toggle and the activity/loan/goal link controls (transfers do not offer goal/loan/activity links, carry no category, and are one-time only).
2. **Liability-aware balance cascade** for transfers (both sides) **and** for plain income/expense on liability accounts, via a single centralized signed-delta helper reused by every cascade site. Reuse `accountsStore.incrementBalance`; never hand-roll balance math.
3. **Cross-currency conversion** of the destination delta (transfer amount is expressed in the **source** account's currency; destination credited in its own currency). The converted destination amount is **persisted on the transaction** so edits/deletes reverse the exact amount that was applied (no rate-drift — see Notes).
4. **Transfers filter** on `TransactionsPage.vue` (currently only all/income/expense, driven off the summary stat cards).
5. **Edit + delete** of a transfer (and of a liability income/expense) reverse correctly with the new signs — reverse-then-reapply stays balanced when the amount, source, destination, type, or currency changes, **and an unrelated edit (description/date/isReconciled) never re-runs FX and never drifts the destination** (see the `toAmount` recomputation contract in Notes).
6. **Net-worth history stays correct** — `netWorthHistory.ts` consumes `accountBalanceDeltaFromTx`; keep per-account reconstruction and the (correct) net-worth-neutral treatment of transfers consistent with the new signs; update the stale "arguably wrong" comment (line ~223-230).
7. **i18n** — every new string via `uiStrings.ts` (`en` + `beanie`, casing standard), used with `t()`; no hardcoded English (CI-enforced).
8. **No silent failures** — a cross-currency transfer with no available exchange rate must be blocked in the UI with a clear, actionable message and, as a defensive backstop, reported via `reportError` in the cascade rather than silently applying a 1:1 rate. The store resolves the rate **before** any balance mutation and aborts the whole cascade on a missing rate — never a half-applied (reversed-but-not-reapplied) state.

## Important Notes & Caveats

- **Centralize the sign — do NOT sprinkle `isLiability` checks at call sites.** Introduce ONE helper (e.g. `signedAccountDelta(type, amount, accountType, isSource)`) in `finance.ts` = `calculateBalanceAdjustment(...) × (isLiabilityType(accountType) ? −1 : 1)`. Every cascade site (`transactionsStore` create/update/delete, `recurringProcessor.ts:261`) and `accountBalanceDeltaFromTx` route through it. `calculateBalanceAdjustment` stays as the asset-perspective primitive the helper composes (keep its tests).
- **Collapse the three parallel cascade copies into ONE routine (Pass 3 — key maintainability fix).** `createTransaction`, `updateTransaction`, and `deleteTransaction` each hold a near-identical "apply source, then if transfer apply destination" block (create ~380-387, update reverse ~428-442 + reapply ~451-458, delete ~499-514). Bolting the liability sign **and** the cross-currency `toAmount` logic onto all three would triple the same intricate math across three sites — a classic drift/maintenance hazard. Instead extract a single well-named routine, e.g. `applyTransactionToBalances(tx, direction: 1 | -1)`, that: resolves the source account and applies `signedAccountDelta(tx.type, tx.amount, sourceAccount.type, true) * direction`; and, when `tx.type === 'transfer' && tx.toAccountId`, resolves the destination and applies `signedAccountDelta('transfer', tx.toAmount ?? tx.amount, destAccount.type, false) * direction`. The three call sites then read: create → `applyTransactionToBalances(created, +1)`; delete → `applyTransactionToBalances(deleted, -1)`; update → `applyTransactionToBalances(original, -1)` then `applyTransactionToBalances(updated, +1)`. This mirrors the store's **existing** symmetric apply/reverse convention for goals (`applyGoalAllocation` / `adjustGoalProgress(..., reverse)`) and loans (`applyLoanPayment` / `reverseLoanPayment`), so it fits the file's grain rather than adding a new idiom. The liability sign and the dest magnitude then live in exactly one place; a future account type or sign change touches one routine.
- **Keep currency conversion OUT of the shared apply routine.** Conversion / `toAmount` computation is a **write-time concern** (it needs the live FX rate and the missing-rate guard) — see the next note for the precise create-vs-update contract. Compute `toAmount` at write time, persist it, and from then on `applyTransactionToBalances` is a pure consumer of the already-stored `tx.amount` / `tx.toAmount` — it never re-derives a rate. This keeps the reversal path rate-independent (drift-free) and keeps the `getRate`/`reportError` missing-rate logic in a single spot rather than smeared across apply/reverse.
- **`accountBalanceDeltaFromTx` needs the account TYPE — and the added map param is a clean, single-caller seam.** It currently takes `(tx, accountId)` and has no account. Change its signature to accept an accounts lookup: `(tx, accountId, accountsById: ReadonlyMap<string, Account>)`, and use `signedAccountDelta` with the resolved account's type for both the source (`tx.accountId`) and destination (`tx.toAccountId`) branches; `balance_adjustment` path unchanged (raw signed delta). If an account can't be resolved, `console.warn` + return 0 (consistent with the existing missing-metadata warn; no silent miscount). Its **only non-test caller** is `netWorthHistory.ts:171,178` (`deriveAccountInitialBalances`) — reuse the `accountById` map already built in `buildNetWorthChanges` (line 124) by passing it down, rather than rebuilding it. (Equally acceptable and marginally simpler-in-signature: build the map internally from the `accounts` array `deriveAccountInitialBalances` already receives. Either keeps the function pure; do NOT reach into a store singleton.) Because there is exactly one production caller and it already holds the map, the ripple is contained and the function stays pure — this is the right seam, not an awkward one. Update `finance.test.ts` accordingly.
- **CRITICAL silent-failure — `convertAmount` returns a 1:1 fallback with NO signal.** Verified in `currency.ts:75-78`: `return rate !== undefined ? amount * rate : amount;`. When no rate/path is found it silently returns the **un-converted** amount. So "reuse `convertAmount`'s behavior" is NOT sufficient — it _is_ the silent failure. The design must call `getRate(rates, from, to)` **explicitly** to detect a missing rate:
  - **UI (modal):** when source/destination currencies differ, compute `getRate(...)`; if `undefined`, disable submit and show an inline message like `t('transfer.noRate')` = "No exchange rate for {from}→{to}. Add one in Settings → Currencies." (developer guidance in the message + a `console.warn`). Never let the user create a mis-converted transfer.
  - **Store (defensive backstop) — resolve BEFORE mutating (Pass 4):** at write time, resolve `toAmount` (and thus the rate) **before touching any balance**. If a transfer needs conversion and `getRate` returns `undefined`, do NOT begin the cascade — `reportError({ surface: 'transactions.transfer-missing-rate', message: 'No FX rate {from}->{to}; transfer not applied', severity: 'error' })` and abort the whole balance cascade (return early; leave existing balances untouched). This ordering matters most on **update**: reversing the original first and only then discovering the new leg can't be converted would leave a reversed-but-not-reapplied destination (corruption). Resolve-then-mutate guarantees an all-or-nothing cascade. This path should be unreachable if the UI guard works, but it guarantees no silent 1:1 corruption and no partial application from any caller.
- **Persist the converted destination amount (drift-free reversal) — and give the field a hard-edged contract.** Income/expense apply the raw `amount` to the account (same currency assumed) so reversal is trivially exact. Transfers are different: the destination delta is a _converted_ value. If update/delete re-derives the conversion at **current** rates, a rate change between create and delete silently drifts the destination balance (create at 1.1 → dest +110; delete later at 1.2 → dest −120; net −10 error). To keep the "every affected balance exactly correct (no drift)" acceptance criterion, **store the applied destination amount on the transaction** (add optional `toAmount?: number` to `Transaction` + `CreateTransactionInput`/`UpdateTransactionInput`, in the destination account's currency) and reverse using that stored value.
  - **Field contract (Pass 3 — prevent an under-specified field that drifts):** document `toAmount` in `models.ts` with the same "only set when …" rigor the neighbouring `adjustment` field already uses. Contract: _"Destination amount, in the destination account's currency, actually applied to `toAccountId`. Set for **every** `transfer` (equals `amount` when source and destination currencies match); **undefined for all non-transfer types**."_ Setting it on same-currency transfers too (rather than only cross-currency) removes the `undefined`-vs-`equals-amount` ambiguity: readers use `tx.toAmount ?? tx.amount` and never have to guess whether an absent value means "same currency" or "old data". This keeps the field self-describing instead of a mystery optional that accumulates conflicting interpretations. (If greg prefers not to add a field, the fallback is re-derive-at-current-rate with an explicit "reversal uses current rates" caveat — but persisting is the recommended, drift-free path.)
  - **The store is the single authority for `toAmount` — and recomputes it ONLY when a conversion input changes (Pass 4 — closes an update-path drift/staleness gap).** The modal computes a `toAmount` for **preview display only**; the store derives and persists the authoritative value on every write so no caller can supply a stale or wrong one. Precise contract:
    - **createTransaction:** always set `toAmount` for transfers — `= amount` when source/dest currencies match, else `= round(amount × getRate(...))` (missing-rate → abort per the note above).
    - **updateTransaction:** recompute `toAmount` **only when a conversion input actually changed** — i.e. `amount`, the source account's currency (via `accountId`), or the destination account (via `toAccountId`, hence its currency) differs from the original. Otherwise **carry `original.toAmount` forward unchanged.** This is the crux of drift-freeness: an unrelated edit (description, date, `isReconciled`) must NOT re-run FX (which would reverse at the old stored rate and reapply at a new current rate → silent destination drift), while a genuine re-conversion (amount/currency/dest change) produces a fresh correct value. It also fixes the **same-currency inline amount edit** (Approach F): amount changed → recompute → same currency → `toAmount = amount`, so a caller passing only `{ amount }` still ends up with a consistent `toAmount` rather than a stale one.
    - **deleteTransaction:** never recomputes — reverses the stored `toAmount`.
    - Net effect: `applyTransactionToBalances(original, -1)` always reverses with `original.toAmount`; `applyTransactionToBalances(updated, +1)` reapplies with the (preserved-or-freshly-recomputed) `updated.toAmount`; the pair is exact in every edit case and rate-independent for unrelated edits.
- **Net-worth history has TWO distinct paths — do not conflate:**
  - `deriveAccountInitialBalances` (per-account) uses `accountBalanceDeltaFromTx` → must become liability-aware (a card-payoff transfer DID reduce the card's owed balance).
  - `transactionToChange` (net-worth total) already returns `null` for transfers (net-worth-neutral). **This is correct** — a card payoff is net-worth-neutral (cash −X, debt −X). It is ALSO already correct for income/expense on liability accounts (a card purchase drops net worth by the expense amount, a refund raises it) with no change needed. Keep transfers null; just fix the misleading comment (lines 223-230) that calls the mixed-class case "arguably wrong."
  - No double-sign: `deriveAccountInitialBalances` operates on per-account balances (liability sign lives in `accountBalanceDeltaFromTx`); `transactionToChange` operates on net-worth deltas directly (amount-based). They reconstruct different quantities and must not both be "corrected" for the same effect. **Verified in Pass 4:** for a mixed-class (checking↔card) transfer the two liability-aware initial-balance shifts (+X on the asset's initial, +X on the card's initial) _cancel_ in the net-worth total once the card's initial is multiplied by −1 — so the total reconstruction stays exactly consistent while `transactionToChange` contributes 0. No double count, no gap.
- **Data back-compat (assess carefully — reaffirmed in Pass 4):** Stored `account.balance` is the source of truth and is **incrementally mutated**, never recomputed for current display — so the code change only affects **future** cascades; existing stored balances are untouched (we do NOT auto-rewrite them; intent of past liability income/expense rows can't be inferred). BUT `deriveAccountInitialBalances` reconstructs history by subtracting `accountBalanceDeltaFromTx` from the current stored balance; for **pre-fix liability income/expense rows**, the stored balance was accumulated with the OLD sign while reconstruction now uses the NEW sign → a bounded discontinuity in the net-worth _history chart_ baseline for accounts that had such rows. Transfers are unaffected (none can exist yet — no producer; verified).
  - **User-facing caveat to surface explicitly (Pass 4):** because we do NOT rewrite stored balances, the _currently displayed_ balance of any credit-card/loan account that already has past purchases/refunds recorded as income/expense is itself wrong today (owed was moved the wrong way by the old cascade) and **remains wrong after this fix until the user manually corrects it** (a balance adjustment). The fix only makes _future_ rows correct. Call this out in the release note and the Help Center article so users aren't surprised that an old card balance doesn't self-heal.
  - **Why not a migration/guard:** a one-time balance rewrite is _computable_ (each pre-fix income/expense row on a liability account was applied with a known, now-flipped sign), but in a local-first CRDT (Automerge), multi-device app a "run exactly once per document" migration against the incrementally-mutated source-of-truth balance is genuinely risky (idempotency across replay/merge, concurrent edits). **Decision: accept + document** (chart correct going forward; balances correctable by the user; no fragile auto-rewrite). Revisit only if telemetry shows liability income/expense rows are common (Assumption 3).
- **Transfer semantics:** a transfer is ONE transaction row (`accountId` = source, `toAccountId` = dest, `type='transfer'`, `amount` in source currency, `toAmount` in dest currency), matching the existing model — NOT two linked rows. No goal/loan/activity link. Category absent or a fixed system constant (simplest: store `category: 'transfer'` for filter/display consistency — a label key already exists). `isReconciled` still applies. **One-time only** (recurring transfers explicitly deferred — hide the recurring/one-time tab + schedule when in transfer mode).
- **Same-account guard:** destination must differ from source (disable/validate with a clear message).
- **Account deletion is already non-cascading:** `accountsStore.deleteAccount` (~235) just deletes; it does NOT reverse balances or clean up referencing transactions (dangling `loanId`/`accountId` already possible). Mirror this for `toAccountId` — no new deletion cascade; transfer **display is already orphan-safe** (`transactionLabel.ts` → `family.unknownAccount`; `AccountViewModal` counterparty lookup is `?.`-guarded). Ensure any new dest display in the view/edit modal is likewise orphan-safe.
- **Recurring transfers:** out of scope (the recurring engine + `RecurringItem.type` are income/expense only). Explicitly defer; do not offer a recurring toggle in transfer mode. (`recurringProcessor.ts` still gets the liability-sign fix for recurring income/expense on liability accounts.)
- **Do NOT touch the loan-linker or `applyLoanPayment`/amortization** — those remain for real loans; a credit-card payoff goes through the transfer path.
- **`balance_adjustment` short-circuit stays untouched** (returns 0 at cascade time; raw delta for history). The new `applyTransactionToBalances` routine is only invoked on the non-`balance_adjustment` paths, exactly where the existing per-site blocks live — the early `balance_adjustment` returns are unchanged.
- **Reuse target correction — there is NO reusable "account select" component.** The source-account picker in `TransactionModal.vue` (~657-685) is a **hand-rolled inline `<select>`**, and the same themed `<select>` markup is duplicated **3×** in that file (account, month, day-of-month). A generic `BaseSelect.vue` exists but is styled differently (not used here). Per the DRY pass, **extract a small themed `AccountSelect.vue`** (props: `modelValue`, `options`/`accounts`, `placeholder`) from the existing inline markup and reuse it for BOTH the source and the new destination picker — removing the current duplication instead of adding a second hand-rolled select. Options must be orphan-safe and exclude the selected source for the destination.
- **Keep the 1082-line `TransactionModal.vue` from ballooning (Pass 3 — maintainability).** Transfer mode adds genuinely new reactive state (destination account, source-currency lock, live FX rate lookup, converted-amount preview, no-rate validation). Threading all of that inline would deepen the existing `v-if` thicket in an already-large SFC. Factor the transfer-specific **logic** into a small composable, e.g. `useTransferForm()` in `src/components/transactions/` (or `src/composables/`), that owns: the destination-account ref, the resolved source currency, the `getRate`-based `rate`/`toAmount`/`hasRate` computeds (preview only — the store re-derives authoritatively), and the transfer validation predicate + message. The modal then consumes a handful of named values instead of growing a dozen new inline refs and watchers. Keep the _markup_ minimal — the destination picker is just `<AccountSelect>` and the converted-amount line is one helper text — so this is one composable, NOT a full modal split (a full sub-component/drawer would be over-engineering for a focused feature). This keeps the diff reviewable and the transfer logic independently testable.
- Consult `.claude/skills/beanies-theme/SKILL.md` for the modal / TogglePillGroup / select / CurrencyAmountInput patterns and the three-tier modal system.

## Assumptions

> Reviewed against code in Pass 2 — statuses updated. Re-walked in Pass 4.

1. **VERIFIED TRUE.** No existing `type:'transfer'` rows exist — grep confirms only _consumers/handlers_ of `'transfer'`, no producer (`spikeWorker.ts` is a type declaration only). The cascade/history handling of transfers therefore only needs to be forward-correct.
2. A transfer's amount is denominated in the **source** account's currency; the destination is converted and the converted value stored as `toAmount`. (If greg wants the amount enterable in either currency, that's a small UI extension — flag.)
3. Existing income/expense rows on `credit_card`/`loan` accounts are rare, so the back-compat discontinuity in §history is minor. If common, revisit migration.
4. **VERIFIED TRUE.** `updateTransaction` reverses on the ORIGINAL account/type and reapplies on the NEW: it reads `input.type ?? original.type`, `input.accountId ?? original.accountId`, `input.toAccountId ?? original.toAccountId` (transactionsStore.ts 446-458), so a changed **source account** and a **type change** (income↔transfer) are already handled, not just amount. The `applyTransactionToBalances(original, -1)` / `applyTransactionToBalances(updated, +1)` pair preserves this exactly (reverse reads the original row, reapply reads the persisted updated row incl. its store-derived `toAmount`). Per the Pass 4 `toAmount` contract, the store recomputes `toAmount` on update only when a conversion input changed, so reapply is correct and unrelated edits don't drift.
5. **CORRECTED — see the CRITICAL note above.** `convertAmount` does NOT surface missing-rate problems; it silently returns a 1:1 amount. We must detect via `getRate` and handle explicitly (UI block + resolve-before-mutate `reportError` backstop). Do not rely on `convertAmount` alone.

## Approach

### Step 0 — UI mockup FIRST (gated on greg's approval, added 2026-07-08 per greg's request)

Before building any modal UI, produce a CIG-clamped mockup of the transfer experience via `/frontend-design:frontend-design`, clamped to `.claude/skills/beanies-theme/SKILL.md` + the CIG (the CIG wins over the generator's defaults). It must cover: the 3-way type selector (Income / Expense / Transfer), the destination-account picker, transfer mode hiding the goal/loan/activity links + category, and the cross-currency "you send X → they receive Y (converted)" row incl. the no-rate blocked state. Save to `docs/mockups/transfer-ui-2026-07-08.html`, iterate to explicit approval, commit only the approved file, and build the modal (Approach C) to match it. The rest of this plan (sign math, cascade, cross-currency, history) is UI-independent and can proceed in parallel, but the modal UI is not built until the mockup is approved.

### A. Centralize the signed balance delta (`src/utils/finance.ts`)

- Add `signedAccountDelta(type: TransactionType, amount: number, accountType: AccountType, isSource = true): number` = `calculateBalanceAdjustment(type, amount, isSource) * (isLiabilityType(accountType) ? -1 : 1)`. Pure, documented with the full case table.
- Refactor `accountBalanceDeltaFromTx` to `(tx, accountId, accountsById: ReadonlyMap<string, Account>)` and use `signedAccountDelta` with the resolved account's type for both the source (`tx.accountId`) and destination (`tx.toAccountId`) branches; `balance_adjustment` path unchanged (raw signed delta). For the destination branch, use the stored `tx.toAmount ?? tx.amount` as the magnitude (the historical effect on the dest was the converted amount). If an account can't be resolved from the map, `console.warn` + return 0.
- Keep `calculateBalanceAdjustment` (asset-perspective primitive) — `signedAccountDelta` composes it; its existing tests stay green.

### B. One shared cascade routine (`src/stores/transactionsStore.ts`, `src/services/recurring/recurringProcessor.ts`)

- **Extract `applyTransactionToBalances(tx, direction: 1 | -1)`** in `transactionsStore` (co-located with `adjustAccountBalance` / `applyGoalAllocation`). It resolves accounts via `accountsStore.getAccountById` and applies, through `adjustAccountBalance`/`incrementBalance`:
  - source: `signedAccountDelta(tx.type, tx.amount, sourceAccount.type, true) * direction`
  - destination (only when `tx.type === 'transfer' && tx.toAccountId`): `signedAccountDelta('transfer', tx.toAmount ?? tx.amount, destAccount.type, false) * direction`
  - If a referenced account can't be resolved, `console.warn` and skip that leg (no throw, consistent with orphan-safe display).
  - This routine is a **pure consumer of the stored `tx.amount`/`tx.toAmount`** — it performs no rate lookups.
- **`toAmount` resolution (write-time, BEFORE any balance mutation):** factor a small create/update helper (e.g. `resolveTransferToAmount(sourceCurrency, destAccount, amount): number | undefined`) that returns the converted dest amount or `undefined` on a missing rate. Both `createTransaction` and `updateTransaction` call it _before_ invoking `applyTransactionToBalances`; a `undefined` result → `reportError(...)` and early-return with **no balance mutation** (all-or-nothing).
- **Call sites collapse to one line each:**
  - `createTransaction`: resolve/persist `toAmount` (same-currency ⇒ `= amount`), then `await applyTransactionToBalances(created, +1)` — replaces the current source + transfer-dest block (~380-387).
  - `deleteTransaction`: `await applyTransactionToBalances(deleted, -1)` — replaces ~499-514 (no `toAmount` recompute; reverses the stored value).
  - `updateTransaction`: recompute `toAmount` **only if a conversion input changed** (amount / source currency / dest account — else carry `original.toAmount`), persist it on the updated row, then `await applyTransactionToBalances(original, -1); await applyTransactionToBalances(updated, +1)` — replaces the reverse-original + reapply-new blocks (~428-458). Goal/loan reverse-and-reapply stays exactly as-is around it. Resolve the (possibly recomputed) `toAmount` **before** the reverse leg so a missing rate aborts without a half-application.
  - This removes the three parallel sign+dest copies; the liability sign and dest magnitude now live in `signedAccountDelta` + this one routine.
- **`recurringProcessor.ts:261`** recurring income/expense — the account is already fetched at line 259, so `signedAccountDelta(item.type, item.amount, account.type)` (income/expense only; never a transfer). Applied via the existing `updateAccountBalance(id, account.balance + delta)` absolute write (unchanged mechanism). This site does NOT use `applyTransactionToBalances` (it operates on a `RecurringItem`, not a `Transaction`, and uses an absolute write) — it just swaps `calculateBalanceAdjustment` for `signedAccountDelta`.
