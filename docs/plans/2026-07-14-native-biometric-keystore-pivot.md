# Plan: Pivot native biometric unlock to BiometricPrompt + hardware Keystore (retire native WebAuthn-PRF)

> Date: 2026-07-14
> Related issues: Notion #52 (biometric passkey can't be enabled on native — High). No GitHub issue — direct implementation.
> Plan file: `docs/plans/2026-07-14-native-biometric-keystore-pivot.md`
> Supersedes the native half of `docs/plans/2026-07-14-native-biometric-prf-and-android-statusbar.md`; decision recorded in ADR-029 (2026-07-14 update).

## User Story

As a family member using the installed **Android or iOS** app, I want to enable "unlock with fingerprint / Face ID" and have it work reliably the first time and every time — without any dependence on WebAuthn passkeys, Google Password Manager PRF, RP-ID/assetlinks validation, or a cloud round-trip — so opening the app is one biometric gesture, and my family encryption key is released only after a genuine, hardware-backed biometric check on this device. Web/PWA biometric (WebAuthn-PRF) is unchanged.

## Context

### Why the pivot

WebAuthn-PRF biometric unlock **works in real browsers (web/PWA)** but fought us at every layer on the installed native apps (full history in ADR-029):

1. The Capacitor WebView can't drive Credential Manager directly (`CreateCredentialUnknownException` / WebView crash) — required the `@capgo/capacitor-passkey` shim to route `navigator.credentials.*` to the native Credential Manager / ASAuthorization.
2. Even shimmed, GMS threw `[50152] RP ID cannot be validated` until we added `handle_all_urls` to the `app.beanies.family` assetlinks (commit `1d93b418`) — that got `create()` past RP-ID validation.
3. A **second wall** then appeared: Google Password Manager does not complete the **PRF** eval on Android (`enroll_declined: no-prf`), so the app can never obtain a PRF output to wrap the family key. iOS PRF never even compiled (the `@capgo` Swift PRF patch targets a plugin not in the iOS SPM package — see below).

**Net: native WebAuthn-PRF never successfully enrolled a single working credential** — every attempt failed at wrap time. So on native it is dead weight plus config/plugin/patch surface that can only ever fail.

**Decision (2026-07-14, greg):** abandon WebAuthn-PRF on native; unlock the local family key with the OS's own biometric-gated key store — Android `BiometricPrompt` + `AndroidKeyStore` `CryptoObject`, iOS `LocalAuthentication` + a biometric-gated Keychain item (Secure Enclave-backed). This has **no** RP-ID / assetlinks / PRF / GPM dependency, is hardware-backed, works offline, and **also unblocks iOS** (drops the never-compiling Swift patch). The only thing PRF bought us — cross-device biometric — is a nice-to-have already covered by the encrypted `.beanpod` cloud copy (new device = one password sign-in + re-enroll). **Web/PWA keeps WebAuthn-PRF unchanged.**

### The mechanism (feasibility-verified against Android/Apple docs)

- **Android:** an AES-256-GCM key in `AndroidKeyStore`, `setUserAuthenticationRequired(true)` + `setInvalidatedByBiometricEnrollment(true)`, per-operation auth binding (`setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)` on API 30+, `setUserAuthenticationValidityDurationSeconds(-1)` on API 24–29), StrongBox via try/catch. Wrap/unwrap the 32-byte family key through `BiometricPrompt` + `CryptoObject(cipher)`; store the GCM IV alongside the ciphertext, device-local. `KeyPermanentlyInvalidatedException` (biometrics changed) → delete + re-enroll.
- **iOS:** store the family-key bytes as a **biometric-gated Keychain item** — `SecAccessControlCreateWithFlags(kSecAttrAccessibleWhenUnlockedThisDeviceOnly, .biometryCurrentSet)`; read via an `LAContext` (the read itself triggers Face ID/Touch ID). The Secure Enclave enforces the gate; the item is cryptographically discarded if the enrolled biometric set changes. Requires `NSFaceIDUsageDescription`.

Both are the canonical, hardware-backed patterns. The at-rest blob is useless without **both** the device's non-exportable Keystore/Keychain key **and** a live biometric.

### Native biometric is device-scoped, not member-scoped (security/identity model)

**A device's OS biometric authenticates the _device_ (any enrolled fingerprint/face passes), not a specific family member.** This is a hard constraint that shapes the design:

- The wrapped blob is keyed by **`account = familyId`** — exactly one biometric-gated blob per family per device (no per-member blobs). Per-member native biometric is impossible to do honestly (the OS can't tell two enrolled humans apart) and undiscoverable at login (biometric unlock happens _before_ the member is identified; unlike WebAuthn there is no credential picker to select a member).
- Consequently there is **exactly one `native-keystore` registry record per family per device**, and it identifies the **enrolling member**. Native biometric logs in as that member. On a genuinely shared physical device, other members use their password (always available). This mirrors the reality that the family AES key is shared and matches "trusted device" semantics. It is documented in the Help Center and the threat model, not treated as a defect.
- **Last-writer-wins on enable:** enabling native biometric for a family **replaces** any prior native record + blob for that family (see Part B `nativeEnable`), guaranteeing the one-record invariant so unlock never has an ambiguous `memberId`.

### Why this is architecturally simpler than the PRF path

The OS store performs the wrapping, so the native path **does not use** any of the app's WebAuthn-PRF crypto/envelope machinery:

- No `deriveWrappingKey`(HKDF) / `wrapDEK`(AES-KW) / `PasskeySecret` / `hkdfSalt`.
- No `passkeyWrappedKeys` **synced** envelope, no `syncStore.addPasskeySecret` / `effectivePasskeySecrets`, no `envelopeMerge`. The native wrapped blob is **device-local and never synced** (a device-bound key is useless on any other device, and syncing it would be a needless exposure).

The native path is therefore: family key (already-extractable `CryptoKey` in `syncStore.familyKey`) → `exportFamilyKey()` to raw 32 bytes → **standard base64** → custom plugin `setKey` (biometric-gated wrap, device-local) on **enable**; plugin `getKey` (biometric prompt → base64 → raw bytes) → `importFamilyKey()` on **unlock**. All the app-level **orchestration and UI stay identical** (see Approach → reuse).

## Requirements

### Functional

1. On the installed **Android** app: enabling biometric unlock succeeds and unlock works on the **first** attempt and every attempt after, with **no** WebAuthn / Credential Manager / RP-ID / GPM / assetlinks dependency.
2. On the installed **iOS** app (Face ID / Touch ID): same — enable succeeds, unlock works first-try and every time, with no WebAuthn dependency.
3. The family AES-256 key is released **only after a live, hardware-backed biometric auth**; it is never persisted in plaintext; the at-rest blob is useless off-device.
4. The native wrapped blob is **device-local**; it is **never** written to the synced `.beanpod` envelope.
5. **Web/PWA biometric (WebAuthn-PRF) is unchanged** — same enable, unlock, cross-device-synced-passkey behavior. No web regression.
6. **Password sign-in remains the permanent root of trust and fallback** on every surface; biometric is only a convenience cache of an already-derived key.
7. **Offer-gating, clean-decline model:** offer native biometric only where it can genuinely be delivered (biometric hardware present + enrolled). Where it can't, don't show the affordance (no pre-warnings per project rule); never show a half-working credential; never treat a user **cancel** as a failure.
8. **No silent failures:** every native enable/unlock failure path is caught, classified, logged, and (where a user action failed) surfaces a friendly message with a password fallback — never a raw platform string, never a bare `catch {}`.
9. **Graceful invalidation & re-enroll:** if the OS key is invalidated (biometrics changed) or the enrolled set is removed, unlock fails cleanly, the stale device-local record is cleared, and biometric is re-offered — the user is dropped to password, never bricked.
10. A native enable failure sets a **recoverable, time-boxed** offer-suppression (reuse the existing cool-off), never a permanent hide — and the suppression only hides the **proactive** offer, never the deliberate Settings enroll surface (preserve the existing `canOfferBiometric` vs `canEnrollBiometric` split; see Approach → Part C).
    11a. **Exactly one native record per family per device** — enabling replaces any prior native record + blob for that family (last-writer-wins), so unlock is never ambiguous; the device-scoped identity model above is honored.

### Retirement / clean switchover

11. **Fully retire the native WebAuthn-PRF path** with no half-working states: remove the `@capgo/capacitor-passkey` plugin, the `patches/@capgo+capacitor-passkey+8.3.9.patch` Swift patch, the `patch-package` devDep + `postinstall` script (**verified: this is the only file in `patches/`**, so both go), the `main.ts` native shim install, the `capacitor.config.ts` `plugins.CapacitorPasskey` block (**verified: it is the only entry under `plugins` — remove the whole `plugins` block**), the `capacitor-passkey.xml` resource, the `AndroidManifest` `asset_statements` meta-data, the app-level `androidx.credentials*` gradle deps (Credential Manager, unused after pivot), and every native `isNative()` branch inside the WebAuthn-PRF JS (so the remaining PRF code is unambiguously web-only).
12. Retire the **native-passkey-only** domain-association entries that are provably unused after the pivot and carry **zero OAuth risk** — the iOS `webcredentials:app.beanies.family` entitlement + the app-origin `webcredentials` AASA, and the `get_login_creds` relation in the `app.beanies.family` assetlinks. **Do NOT touch any OAuth App Link / Universal Link config** (`handle_all_urls` on `app.beanies.family` is verified-then-retired only if nothing else depends on it — default KEEP if uncertain; `applinks:beanies.family`, the `/oauth/native` AASA, and the Android OAuth intent-filter are all KEEP).
13. Migration is trivial by construction (no native WebAuthn credential ever succeeded — `savePasskeyRegistration` only runs _after_ a successful wrap, which never happened on native): on native, a stale WebAuthn-mechanism registry record is **ignored for unlock** and **not counted as a registered passkey** (so it never suppresses the fresh Keystore enrollment offer), and is cleaned up opportunistically. This is realized by the native semantics of `hasRegisteredPasskeys` in Part C — a single, correct site, not a separate ad-hoc hook. A user with a **web** passkey opening the native app is offered fresh Keystore enrollment; their web passkey keeps working on web.

### App-surface correctness (Pass 5 — call-sites the service delegation alone does not cover)

16. **`PasskeySettings.vue`'s component-level gate must be native-aware.** `PasskeySettings.vue:32` gates the whole enroll panel on raw `isWebAuthnSupported()` (checks `window.PublicKeyCredential` / `navigator.credentials`), which on native is currently only present **because the retired `@capgo` shim installs it** (`main.ts:127`). After shim removal this can be false on the native WebView (esp. iOS WKWebView, whose WebAuthn is gated behind the very `webcredentials` associated-domain this plan removes) → the deliberate Settings enroll surface would go dead, directly violating Req 10. Fix: make the gate native-aware — gate on `canEnrollBiometric()` (already native-guarded → `nativeCanEnroll()`), or `isNative() || isWebAuthnSupported()`. This is the one place the "orchestration/UI stays unchanged" claim genuinely needs a touch.
17. **`ReauthChallenge.vue` is a passkey call-site (ownership-transfer re-auth) that must be device-scope-aware.** `ReauthChallenge.vue:63` calls `hasRegisteredPasskeys` and `:103-121` calls `authenticateWithPasskey({familyId})`, then **requires `result.memberId === props.member.id`**, else fires a `severity:'warning'` `reportError` ("authenticated a different member than expected"). On native, `nativeUnlock` returns the **enrolling** member (device-scoped) — on a shared device that legitimately differs from `props.member`, producing spurious `#beanies-errors`-adjacent warning telemetry on every such re-auth (functionally safe — password fallback remains). Fix: when the matched record is `mechanism:'native-keystore'`, treat a member mismatch as expected (drop to password without the `warning` `reportError`, or log it `info`). Add native-delegation coverage.

### Observability & tests

14. New `native-biometric` diagnostic surface so live-only (on-device) failures are triageable from CloudWatch **without a local repro**, including which OS key backing was used and the success/decline/cancel/error outcome — with the success path emitted too so rates are measurable.
15. Unit tests at the JS↔plugin boundary (enable, unlock, user-cancel-is-not-failure, invalidated/lockout → friendly + cleanup, availability gating, one-record-per-family replace, absent-key self-heal) + the retirement of native-PRF test cases; the native Swift/Java plugin is verified by build + on-device + telemetry (live-only).

## Important Notes & Caveats

- **Live-only native testing.** greg verifies on the deployed store/closed-testing build (no local/dev native). The design must be correct-by-construction, unit-tested at the JS boundary, and fully observable. This is why Req 14 is load-bearing.
- **Custom plugin vs off-the-shelf — the key decision (recommend CUSTOM).** Only `@capgo/capacitor-native-biometric ≥ 8.4.0` does true CryptoObject/SecAccessControl binding off-the-shelf; every other Capacitor biometric/secure-storage plugin is boolean-only or encryption-at-rest without a biometric key-release gate (would be a security regression). For a **security-first, open-source** app on its most sensitive path, a small custom plugin (~150–250 lines Java + Swift, mirroring the existing `WindowBackgroundPlugin.java` precedent) is recommended: raw-32-byte storage (no username/password shoe-horn), exact `KeyGenParameterSpec` control (StrongBox try/catch, `AUTH_BIOMETRIC_STRONG`, invalidation policy, API 24–29 branch), typed errors (cancel vs invalidated vs lockout), and no third-party supply-chain surface on the crypto path. **Fallback if greg prefers zero native code:** adopt `@capgo/capacitor-native-biometric ≥ 8.4.0` via its `AccessControl.BIOMETRY_CURRENT_SET` / `getSecureCredentials()` path only (never the legacy non-gated `setCredentials/getCredentials`) — but first read its Android `NativeBiometric.java` to confirm correct `setUserAuthenticationParameters`/validity-`-1` on minSdk 24 and distinct `KeyPermanentlyInvalidatedException` handling.
- **iOS Swift still won't compile on this dev machine (WSL/Linux, no Xcode).** As with the retired patch, the iOS half of the custom plugin first compiles when `mobile-ios-release` runs (Apple enrolment pending). Design it correct-by-construction; Android compiles + runs in CI now.
- **StrongBox is best-effort (API 28+, hardware-dependent).** Try StrongBox, catch `StrongBoxUnavailableException`, rebuild without it → TEE-backed key (still hardware-backed). Log which backing was used (`key_backing`) so we can see the field distribution.
- **minSdk 24 branch:** `setUserAuthenticationParameters` is API 30+; on 24–29 use `setUserAuthenticationValidityDurationSeconds(-1)` (per-op auth via CryptoObject). Both give per-unlock binding.
- **Threat model (document, don't over-claim):** hardware binding protects the **at-rest** blob; on a rooted/jailbroken device a privileged attacker could scrape the live key from WebView memory after a legitimate unlock. Devices without a secure lock screen / no enrolled biometric simply don't get the offer. Native biometric authenticates the _device_, not a specific member (see the device-scoped identity model in Context) — on a shared device it logs in as the enrolling member; other members use password.
- **Family-key raw bytes on enable — reuse the existing export; the key is guaranteed present.** The plugin needs the 32 raw bytes to wrap. **Verified:** every family key held in `syncStore.familyKey` is created extractable — `generateFamilyKey`, `importFamilyKey`, and `unwrapFamilyKey` in `familyKeyService.ts` all pass `extractable = true` — and `exportFamilyKey(key: CryptoKey): Promise<Uint8Array>` already exists there. **Also verified:** the sole caller `authStore.registerPasskeyForCurrentUser` already guards `if (!syncStore.familyKey) return { success:false, … }` _before_ delegating, so `nativeEnable` receives a valid extractable key (it still wraps the `exportFamilyKey` call in try/catch defensively). So `nativeEnable` takes the `CryptoKey` the service already passes in (`registerPasskeyForMember` params carry `familyKey: CryptoKey`) and calls `exportFamilyKey(familyKey)`. This is DRY (no new raw-byte plumbing), avoids the fragile `globalSettings.cachedFamilyKeys` path (only populated on _trusted_ devices — an enable on an untrusted device would have found nothing), and needs no new assumption.
- **base64, not base64url; source it from the shared leaf util — never from `passkeyService`.** The raw 32 bytes cross the JS↔plugin bridge as a **standard base64** string (`keyB64`). **Verified:** `bufferToBase64`/`base64ToBuffer` already exist in the dependency-light leaf `src/utils/encoding.ts` (standard `btoa`/`atob` alphabet, accepts `Uint8Array`, already used by `familyKeyService`). `nativeBiometric.ts` imports them **from `@/utils/encoding`** — **not** from `passkeyService.ts` (which has its own private copies; importing those would re-introduce the exact `passkeyService ↔ nativeBiometric` cycle the plan works to avoid) and **not** base64url (`bufferToBase64url` — different alphabet, would mis-decode). The native side must use the matching **standard** base64: Android `Base64.NO_WRAP` (to match the single-line JS output; `Base64.DEFAULT` inserts newlines), iOS `Data(base64Encoded:)` / `.base64EncodedString()`. This is the single most bug-prone boundary in the plan — pin it in the plugin doc-comment on both platforms.
- **Zero the exported bytes; the base64 string is an unavoidable transient.** Zero the exported raw-bytes `Uint8Array` in a `finally` after `setKey` returns. Note the intermediate `keyB64` **string** cannot be zeroed (JS strings are immutable) — keep it in the narrowest possible scope so it is GC-eligible immediately; this residual is already covered by the rooted-device caveat in the threat model.
- **Avoid a circular import between `passkeyService.ts` and `nativeBiometric.ts` — extract the shared leaf helpers first (maintainability).** **Verified:** the suppression cool-off trio (`isBiometricOfferSuppressed`/`suppressBiometricOffer`/`clearBiometricSuppression`) and the bounded-detail formatter `describeAuthError` are currently **module-private** functions inside `passkeyService.ts`. If `nativeBiometric.ts` imported them from `passkeyService.ts` while `passkeyService.ts` imports `nativeBiometric.ts` to delegate, we'd create a two-way import cycle between the two largest, most security-sensitive files (an `import/no-cycle` smell and a real init-order/TDZ hazard). **Fix:** first move these mechanism-agnostic, dependency-free helpers into a small **leaf module** `src/services/auth/biometricShared.ts` (no imports from `passkeyService`/`nativeBiometric`), and have **both** files import from it. This is a pure extraction (behaviour-identical, single-sourced) that removes the cycle by construction and keeps the cool-off logic in exactly one place. `guessAuthenticatorLabel` (already exported from `passkeyService.ts`, no back-dependency) may stay where it is or move alongside — either is acyclic; keep it put to minimise churn. (base64 helpers do **not** need moving — they already live in the leaf `@/utils/encoding`.)
- **Do NOT reintroduce any synced storage for the native blob.** Device-local only. If a future "biometric on device B" story is wanted, it re-enrolls locally after a password sign-in — that is the intended model, not blob-sync.
- **Family switching does not touch native blobs.** Each family's blob is device-local, keyed by `account = familyId`, held in the OS Keystore/Keychain — independent of `syncStore` state, so `switchFamily` + `syncStore.resetState()` leaves every family's blob intact (and correctly isolated — no multi-family collision). If a family is fully removed from the device, its Keystore alias may orphan; that is inert (biometric-gated, useless without the family) and is not special-cased.
- **Keep the web path physically untouched.** The `isNative()` fork happens at the service boundary _before_ any WebAuthn-PRF code runs (in particular **before** the `isWebAuthnSupported()` early-return at `passkeyService.ts:211` / `:525`, which on the native WebView could otherwise reject before delegation), so the web functions are not edited beyond deleting now-dead native branches. This is the primary guard against a web regression. Note `platformSupportsPRF()` returns a constant `true` on web (`if (!isNative()) return true`), so deleting it and its callers is **web-neutral** — the web `canEnrollBiometric`/`registerPasskeyForMember` behave exactly as before.

## Approach

### Architecture: a native-vs-web fork at the service boundary (minimal blast radius)

Introduce one cohesive module, **`src/services/auth/nativeBiometric.ts`**, that owns the entire Keystore/Keychain path and wraps the custom Capacitor plugin. The **existing service entry points** (`registerPasskeyForMember`, `authenticateWithPasskey`, `canOfferBiometric`, `canEnrollBiometric`, `removePasskey`, `hasRegisteredPasskeys`) gain a thin `isNative()` guard **as their first statement — above the `isWebAuthnSupported()` check** — that delegates to `nativeBiometric.*` and returns the **same result types** callers already handle. This keeps every layer above the service — `authStore` (`registerPasskeyForCurrentUser`/`signInWithPasskey`/`checkHasRegisteredPasskeys`), `App.vue` (`handleEnablePasskey` at `:216`, the offer gate at `:1358`, the persist call-site at `:223`), `BiometricLoginView.vue` (`:41`), `PasskeySettings.vue` (`:81`), `LoginPage.vue`/`FamilyPickerView.vue` (the `hasPasskeys` routing), `LoadPodView.vue` — **completely unchanged**, and confines the whole pivot to (a) one new module + custom plugin and (b) deletion of dead native branches. (A fuller provider-interface refactor that also relocates the web path was considered and rejected: it adds indirection for exactly two implementations and needlessly risks the web path we must not break. Noted in Review Passes.)

**Dependency direction is one-way (no import cycle).** `passkeyService.ts` → `nativeBiometric.ts` (delegation only). Everything both modules share — the suppression cool-off trio and `describeAuthError` — is first extracted into the dependency-free leaf module **`src/services/auth/biometricShared.ts`**, which imports from neither; base64 conversion comes from the pre-existing leaf **`@/utils/encoding`**. So the import graph is `passkeyService.ts → { nativeBiometric.ts, biometricShared.ts }`, `nativeBiometric.ts → { biometricShared.ts, @/utils/encoding, familyKeyService }` — a DAG, no cycle, single source of truth for the cool-off and the base64 codec. Do the `biometricShared.ts` extraction as **step 0**, verified green by the existing suites, before writing any native/JS-boundary code.

**Why the result types line up for free:** the web enable returns a `passkeySecret` that `App.vue:223` persists into the synced envelope via `if (result.passkeySecret) …`. The native enable has **no** `passkeySecret` (device-local, OS-wrapped) → it returns `{ success: true, passkeySecret: undefined }`, and the existing `if (result.passkeySecret)` guard simply skips the envelope write (and the follow-up `syncStore.addPasskeySecret` + `syncNow`). No call-site change.

### Part A — the custom Capacitor plugin (`BiometricKeystore`)

A small first-party plugin (Android Java + iOS Swift), registered like `WindowBackgroundPlugin`. Bridge API (all promises, typed errors; `keyB64` is **standard** base64):

- `isAvailable(): { available: boolean; biometryType?: 'faceId'|'touchId'|'fingerprint'|'face'|'iris'|'none'; reason?: string }` — Android `BiometricManager.canAuthenticate(BIOMETRIC_STRONG)`; iOS `LAContext.canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics)`. No prompt.
- `setKey({ account: string; keyB64: string }): { keyBacking: 'strongbox'|'tee'|'keychain'|'secureEnclave' }` — **enable**: Android generates/uses the auth-bound Keystore key, `BiometricPrompt` + `CryptoObject`, `doFinal(Base64.decode(keyB64, NO_WRAP))`, persists `iv||ciphertext` device-local under `account`; iOS `SecItemAdd` with `SecAccessControl(.biometryCurrentSet, WhenUnlockedThisDeviceOnly)` (delete-then-add so a re-enable is idempotent). Returns which backing was used. Rejects with the same typed codes as `getKey` (`userCancel`/`notEnrolled`/`lockout`/`unknown`) so the JS layer never sees a raw platform string.
- `getKey({ account: string }): { keyB64: string }` — **unlock**: Android `Cipher.init(DECRYPT, key, GCMParameterSpec(iv))` + `BiometricPrompt` + `CryptoObject` → `doFinal` → `Base64.encodeToString(raw, NO_WRAP)`; iOS `SecItemCopyMatching` with `LAContext` (read triggers the prompt) → `.base64EncodedString()`. Rejects with typed error codes: `userCancel`, `notEnrolled`, `lockout`, `invalidated`, `unknown`.
- `hasKey({ account }): { present: boolean }` — presence check, no prompt.
- `deleteKey({ account }): void` — **disable**: delete the Keystore alias + blob / Keychain item. Idempotent (deleting an absent key resolves, never rejects).

`account` is a stable per-family key (`familyId`) so multiple families on one device each get their own biometric-gated blob (no collision), and each family has at most one blob (device-scoped model).

Android specifics: `androidx.biometric:biometric`; AES/GCM/NoPadding; `Base64.NO_WRAP` both directions; `KeyGenParameterSpec` with `setUserAuthenticationRequired(true)`, `setInvalidatedByBiometricEnrollment(true)`, StrongBox try/catch, API-30+/24–29 auth-param branch; map `ERROR_USER_CANCELED`/`ERROR_NEGATIVE_BUTTON` → `userCancel`, `ERROR_LOCKOUT*` → `lockout`, `KeyPermanentlyInvalidatedException` → `invalidated`, `ERROR_NO_BIOMETRICS`/`NONE_ENROLLED` → `notEnrolled`, everything else → `unknown` (never leak the raw message to JS as a code). iOS specifics: `NSFaceIDUsageDescription`; standard `base64Encoded`; map `LAError.userCancel`/`.userFallback` → `userCancel`, `.biometryLockout` → `lockout`, `errSecAuthFailed`/changed-set → `invalidated`, `.biometryNotEnrolled` → `notEnrolled`, else `unknown`. Keep the Swift minimal and correct-by-construction (won't compile until the iOS release runs).

### Part B — the JS native module (`src/services/auth/nativeBiometric.ts`)

Wraps the plugin; maps typed error codes → friendly `t()` copy + telemetry; converts raw bytes ↔ `CryptoKey` via the existing `exportFamilyKey`/`importFamilyKey` (`familyKeyService.ts`) and raw bytes ↔ base64 via `bufferToBase64`/`base64ToBuffer` from `@/utils/encoding`; imports the suppression trio + `describeAuthError` from the shared leaf module `biometricShared.ts` (never from `passkeyService.ts`). Functions (each returns the shared result types so the service delegates cleanly):

- `nativeCanEnroll(): Promise<boolean>` — `plugin.isAvailable().available`, wrapped in try/catch (a plugin-bridge throw → `false`, logged `warning`, never an uncaught rejection). **Does NOT consult suppression** — this is what `canEnrollBiometric` (the deliberate Settings surface) calls, matching the existing web semantics where enroll is never locked out by a prior transient decline.
- `nativeCanOffer(): Promise<boolean>` — `nativeCanEnroll()` AND not currently suppressed (reuse `isBiometricOfferSuppressed` from `biometricShared.ts`). This is what `canOfferBiometric` (the proactive App.vue nag) calls. (This two-helper split mirrors the existing web split at `passkeyService.ts:154`/`:165` and is the fix for Req 10 — a failed enable must not lock out Settings.)
- `nativeHasRegistered(familyId): Promise<boolean>` — the native semantics of `hasRegisteredPasskeys`. Loads `passkeyRepo.getPasskeysByFamily(familyId)`; **opportunistically removes any non-`native-keystore` (stale WebAuthn) records** for this family (Req 13 migration — idempotent, best-effort in try/catch); returns whether a `native-keystore` record remains. This is the single site that (a) routes login to biometric only when a keystore record exists, and (b) keeps a stale/absent keystore record from suppressing the enable offer. It is a **registry-only** check (no plugin round-trip) — deliberately cheap because it runs on every family selection; the OS-key presence self-heal lives in `nativeUnlock` (below), not here.
- `nativeEnable({ memberId, familyId, familyKey, label }): Promise<RegisterPasskeyResult>` — `exportFamilyKey(familyKey)` → `bufferToBase64` → `plugin.setKey({ account: familyId, keyB64 })`; wrap the export+setKey in try/catch, zero the exported `Uint8Array` in `finally`, keep `keyB64` in the narrowest scope. On success: **first remove any existing `native-keystore` record(s) for this family** (`passkeyRepo` — enforces the one-record-per-family invariant, last-writer-wins), then persist a device-local `PasskeyRegistration` (`mechanism: 'native-keystore'`, synthetic `credentialId = native:${familyId}:${memberId}`, `label: label || guessAuthenticatorLabel()` (reuse the existing exported helper), `prfSupported: false`, `publicKey: ''`, timestamps) via `passkeyRepo.savePasskeyRegistration`, clear suppression (`clearBiometricSuppression`), return `{ success: true, passkeySecret: undefined, prfSupported: false }`. On `userCancel` → `{ success: false, cancelled: true }` (NOT a failure — no suppression, no `reportError`, `info` telemetry only). On any hard error code → `suppressBiometricOffer()`, `reportError` `warning` with a bounded `detail`, friendly `{ success: false, error }`. **No local record written unless setKey succeeded** (no half state).
- `nativeUnlock({ familyId }): Promise<AuthenticatePasskeyResult>` — load the device-local `native-keystore` record for `familyId` first (need `memberId`; by the one-record invariant there is exactly one — if somehow multiple, pick the most-recently-created). If no record → `{ success: false, error: … }` (unlock shouldn't have been offered). **Then `plugin.hasKey({ account: familyId })` (no prompt): if `present === false` the OS key is gone (invalidated / cleared for any reason) → clear the stale device-local record + friendly re-enroll message, no biometric prompt** (self-heal for the "OS key wiped" case, platform-independent). Otherwise `plugin.getKey({ account: familyId })` → `base64ToBuffer` → `importFamilyKey(bytes)` → `{ success: true, familyKey, memberId }`. On `userCancel` → `{ success: false, cancelled: true }` (clean "use password", no error toast — same contract `signInWithPasskey`/`BiometricLoginView` already honor). On `invalidated`/`notEnrolled` → clear the stale device-local record + `plugin.deleteKey` defensively (each in try/catch), `reportError` `warning`, return `{ success: false, error: reEnrollMessage }`. On `lockout`/`unknown` → friendly message + `{ success: false, error }`, `reportError` `warning` (do **not** clear the record — lockout is transient).
- `nativeDisable({ familyId, credentialId }): Promise<void>` — `plugin.deleteKey({ account: familyId })` (try/catch — a missing key is not an error) then `passkeyRepo.removePasskeyRegistration(credentialId)`.
