# Plan: Surface-agnostic data-connection resilience (self-healing provider config)

> Date: 2026-07-15
> Related issues: None — direct implementation
> Plan file: `docs/plans/2026-07-15-native-data-connection-resilience.md`
> Investigation: `docs/investigations/2026-07-15-native-data-connection-loss.md` (primary technical backing — read it alongside this plan)

## User Story

As a family owner opening beanies.family on any surface (installed native app, iOS/Android PWA, or desktop web), I want my Google Drive data connection to re-establish itself silently after my device evicts local storage, so that I am never dropped onto a scary "save your data to a file / resume setup" screen for a pod I already own — and I'm only asked to do something when reconnection has genuinely, totally failed.

> **Scope of "silent" (honest boundary).** A fully password-free, invisible heal is possible only when the cached Automerge doc + family key survived the eviction (partial eviction, or a loss that spared `localStorage`). When the OS evicts the **whole** `beanies-file-handles`/IndexedDB origin (the most-likely H1 trigger), the doc cache and cached family key go with it, so after the provider config is healed the existing load pipeline still hits `needsPassword` and the user must re-enter their family password **once** — but they now land on a working password-resume screen (reachable via the Bug-A fix), not the dead-end unconfigured card. That is still a decisive improvement; the plan never claims to conjure the decryption key out of nothing.

## Context

### The incident

On an established owner's **native Android** install, the app showed the **unconfigured** "Family data options" state (`save your data to a file` + `resume setup` + `load existing family data file`) even though the user is the pod owner. Clicking **resume setup** did nothing. The `.beanpod` on Google Drive was never moved or deleted.

The split state is: `authStore.podCreated === true` + `needsPodSetup === false` (established owner, restored from `localStorage`) but `syncStore.isConfigured === false` (no storage provider restored this session).

### Answering the framing question: "isn't native just a thin wrapper around the same Vue code?"

**Yes — and that's the key insight.** The native app is a Capacitor WebView running the **same** production Vue/Pinia bundle (`webDir: 'dist'`). The data-connection logic is **not** forked between PWA and native. There is no separate "native data code." So why does this bite native and not desktop web? Three storage-substrate differences, none of them "different logic":

1. **IndexedDB eviction.** The Drive provider config is restored at boot **solely** from one IndexedDB record — `providerConfig-<familyId>` in the `beanies-file-handles` DB (`syncService.initialize()`, `syncService.ts:539-644`). Mobile WebViews and iOS Safari evict IndexedDB aggressively (storage pressure, iOS 7-day eviction); desktop Chromium almost never does.
2. **No web fallback tier on native.** Desktop web has a _second_ restore tier — the File System Access API handle (`syncService.ts:611-636`). That API is unavailable in a WebView, so native loses that safety net.
3. **No redundancy for the config itself.** The Google _refresh token_ is deliberately dual-written to IndexedDB **and** `localStorage` precisely because "on PWA/mobile, IndexedDB can be evicted" (`fileHandleStore.ts:181-250`). The **provider config was never given the same redundancy**, and `initialize()` has **no fallback** to the durable remote family registry (`registryService.lookupFamily`) that already holds the same `fileId`.

So the fix is exactly what you asked for: **do not add native-specific branches — harden the single shared restore path** so it self-heals from the durable registry and is retried silently on every surface. The web path "rarely hits this" today only because desktop rarely evicts + has the FSA fallback; making the shared path robust fixes native, iOS PWA, and web with one consistent mechanism. This is squarely the MVO pattern: `syncService` exposes the primitives; `syncStore` orchestrates the multi-subsystem re-derivation (registry → Drive → re-persist).

### Two confirmed UX bugs (independent of the root cause, both must be fixed)

- **Bug A — "resume setup" is a dead button for `podCreated` owners.** `handleResumeSetup` (`SettingsPage.vue:370-373`) pushes `/welcome?resume=setup`, but the already-auth router guard (`router/index.ts:347-367`) sees `needsPodSetup === false` for a `podCreated` owner and bounces to `/nook` (`:366`). The registry-resume machinery (`ResumePodSetup` → `attemptResumeFromRegistry`) that _would_ fix the connection is never reached.
- **Bug B — no "reconnect Google & reload my Drive file" affordance.** The unconfigured card (`SettingsPage.vue:1198-1235`) offers only dead resume-setup + a **local** file picker (wrong for a Drive-backed pod). The only reconnect control (`handleSettingsReconnect`) lives in the _configured_ branch (`:1443`), unreachable when `isConfigured` is false.

### The self-heal primitive already exists

`attemptResumeFromRegistry` (`syncStore.ts:2629-2697`) already reads `fileId` from the remote registry and rebuilds the Drive provider — it is simply **unreachable** from the `podCreated && !isConfigured` state. The bulk of this work is making that existing, tested machinery reachable and automatic, not writing new recovery logic.

## Requirements

1. **Self-healing restore.** When `getProviderConfig(familyId)` returns nothing at boot but the family is known to be Drive-backed (per the durable registry / session), `syncService.initialize()` (via a `syncStore` orchestrator step) must re-derive and re-persist the provider config instead of dropping to `isConfigured: false`.
2. **Reuse, don't duplicate.** The **silent** re-derivation reuses `registryService.lookupFamily` (registry read), `GoogleDriveProvider.fromExisting`, and the persist/install seam already factored as `installProvider` (`syncStore.ts:449-489`) — the same primitive `reHomeToOwnDrive`'s adopt branch uses (`syncStore.ts:2196`) — plus `searchBeanpodFilesGlobal` + `resolveExistingBeanpod` for the name fallback and the ownership discipline from `establishDurableHomeAfterLoad`. **`attemptResumeFromRegistry` is NOT the silent engine** — it stages an encrypted envelope and returns `auto-loadable` **requiring a password via `completeAutoLoad`** (`syncStore.ts:2681-2710`); it is reused only for the _interactive password_ recovery path (Layer 3.1), never for silent heal. No new lookup/adopt logic that duplicates these.
3. **Silent background retry.** If re-derivation can't complete immediately (network down, OAuth proxy cold, Drive 5xx, token lapsed), retry silently with backoff driven by the same wake events the token path uses (focus/pageshow/online). No toast/banner during retries.
4. **Only bother the user on TOTAL failure.** Surface UI (reconnect/reload affordance) and page telemetry **only** when retries are exhausted or the registry genuinely has no Drive home for this family.
5. **Un-strand the recovery screen (Bug A).** A `podCreated` owner who is genuinely unconfigured must reach the registry-resume recovery screen — via a let-through early-return in the already-auth guard (mirroring the existing `resume=setup` let-through at `router/index.ts:363`), not a new screen and not a self-redirect.
6. **Correct recovery affordance (Bug B).** Add a Drive reconnect/reload action to the unconfigured card (shown when the pod is Drive-backed) that calls the re-derivation orchestrator — not the dead resume-setup, not the local-file picker. Keep "load existing family data file" only for genuinely local/imported pods.
7. **Local redundancy.** Dual-write the provider config to `localStorage` (mirroring the refresh-token fallback) so a same-origin IndexedDB eviction that spares `localStorage` self-heals without a network round-trip. Attempt `navigator.storage.persist()` on native where the WebView supports it.
8. **Reconnecting UI state.** While the silent retry is in flight, the card renders a lightweight "reconnecting…" state, never the alarming "save your data to a file" unconfigured layout.
9. **Surface-agnostic.** All of the above lives in the shared code path — no `isNative()`-forked recovery logic. Native, iOS PWA, and web all get identical behavior.
10. **Observability.** Every decision/fallback emits a structured diagnostic event so the failure is triageable from CloudWatch without a device repro (see Observability Coverage).

## Important Notes & Caveats

- **Never `createNewFile` in the recovery path.** Re-derivation is **read/adopt only**. Minting a new file here is the Shaun-class data-loss regression explicitly called out at `syncStore.ts:2621-2624`. A lapsed token or transient failure becomes "retry later," never "create a fresh empty pod."
- **Ownership discipline.** Re-resolve by ownership (`ownedByMe`, as `establishDurableHomeAfterLoad` `syncStore.ts:2272-2306`). A device handed a _foreign_ shared file must not adopt it as its own home. Joiners' shared files stay put (the join flow never enters this path).
- **Idempotency.** All re-derivation is a no-op when a valid provider for this family is already installed — mirror the `getProviderFamilyId() === activeFamilyId` guard (`syncStore.ts:2257-2258`). Never run twice concurrently (single in-flight guard).
- **Don't corrupt the doc while healing the provider — the concrete hazard is `installProvider`'s blind upload.** `installProvider` (`syncStore.ts:449-489`) calls `syncNow()` at `:465`, which **uploads the in-memory doc to the file**. In a cold heal where the doc was NOT loaded (the eviction case), that would overwrite the real Drive `.beanpod` with an empty doc — the same Shaun-class data loss we forbid for `createNewFile`. **Hard gate:** the silent heal must `provider.persist(familyId)` + `syncService.setProvider` **without any blind upload** unless `replaceDocWithCacheRecovery` (`syncStore.ts:551-581`) has authorised a loaded doc for this family (cache-hit-authorises-merge, else drop-and-adopt). **Decompose `installProvider` (`syncStore.ts:449-489`) carefully** so the two paths share sub-steps without drifting — but **preserve `installProvider`'s original step order**. Today the order is `persist` → `setProvider` → `syncNow()` (`:465`, throws on write failure at `:466-467`) → `saveSettings` → `registerCurrentFamily` (`:478`, reached only if the write succeeded) → `setupTokenExpiryHandler` (`:485`). The heal path needs `persist` → `setProvider` → `setupTokenExpiryHandler`/`setupAutoSync` **without** `syncNow()`/`saveSettings`-sync-write **and without** `registerCurrentFamily` (the family is already registered — this is a re-derivation, not a create). **Do NOT** define `installProvider` as a naive `installProviderPersistOnly() + syncNow()` composition — that would move `registerCurrentFamily` _before_ the write-confirmation and leave the registry pointing at a never-written file if the first write fails (breaks create/`migrateStorage` rollback semantics `:2426-2429`). Extract only the shared leaf steps; `installProvider` keeps its exact current ordering. **Critical:** the heal seam MUST still call `setupTokenExpiryHandler()` — `onTokenAcquired` is registered only there, and Layer-2's re-arm depends on it; dropping it would silently kill wake-event recovery.
- **Scope the retry.** Fire only for an **authenticated boot with a known Drive-backed family**. It must **not** fire during sign-out teardown (`resetState` legitimately sets `isConfigured:false`, `syncStore.ts:2104`) or mid-create (`membersStepActive`, `router/index.ts:357`).
- **Native local pods can't be re-derived remotely.** If the registry says `provider:'local'`, keep it as an explicit "reconnect needed" surface — don't silently guess a file path.
- **Token expiry is NOT the cause of the unconfigured card** (investigation H4, refuted). An expired token keeps `isConfigured:true`. The R4 auth-masked-404 fix already handles the token case. This plan handles the _missing-config_ case, which is distinct. The two compose: if the token is also lapsed during re-derivation, step 1 attempts a silent refresh (`beginDriveAuthRedirectIfNeeded`/`tryReconnectSilently`) exactly as `attemptResumeFromRegistry` already does.
- **`membersStepActive` exemption** (`router/index.ts:357`) must remain intact after the guard change so a fresh create is never re-routed into recovery.

## Assumptions

> **Review these before implementation.** Valid at planning time (2026-07-15).

1. The most likely trigger is IndexedDB eviction of `providerConfig-<familyId>` while `localStorage` survived (investigation H1, PLAUSIBLE-most-likely). The fix is correct regardless of which of H1/H2/H3 fired, because all converge on "`getProviderConfig` returned none and init gave up." Device logs (the `syncService.ts:568` line) would confirm the specific trigger but are not required to ship the fix.
2. `attemptResumeFromRegistry` (`syncStore.ts:2629-2697`) reads `fileId` from the registry, stages the encrypted envelope, and returns `auto-loadable` **requiring a password via `completeAutoLoad`** — it is the _interactive_ resume path, NOT a silent re-persist. The **silent** re-persist primitive is `GoogleDriveProvider.fromExisting(fileId, name)` + `provider.persist(familyId)` + `syncService.setProvider` (the persist/install seam factored as `installProvider`, `syncStore.ts:449-489` — but see the blind-upload caveat in Important Notes). (Verify contracts at implementation time.)
3. The remote registry (`registryService.lookupFamily`, `registryService.ts:34-46`) reliably holds `provider:'google_drive'` + `fileId` + `displayPath` for an established Drive-backed family (`models.ts:1516-1529`).
4. Name-based fallback uses **`searchBeanpodFilesGlobal`** (`driveService.ts:366`, via `listGoogleDriveFiles` `syncStore.ts:2846-2860`) to find the `.beanpod`, then `resolveExistingBeanpod` (`connectStorage.ts:224-242`) to adopt-or-reject with `ownedByMe` from `getFileMetadata(token, fileId, 'ownedByMe')` (as `establishDurableHomeAfterLoad` does at `syncStore.ts:2275`). `resolveExistingBeanpod` classifies a _known_ fileId — it does NOT search by name.
5. A let-through early-return for `podCreated && !isConfigured` on `resume=setup` (mirroring `router/index.ts:363`) reaches the existing `ResumePodSetup` → `attemptResumeFromRegistry` → `completeAutoLoad` path (`syncStore.ts:2710-2768`) without a new screen.
6. `localStorage` and IndexedDB have independent eviction characteristics on the target platforms (the app already relies on exactly this for the refresh-token fallback).

## Approach

Implement in four coordinated layers. Everything lives in the **shared** code path (no `isNative()` fork), per Requirement 9.

### Layer 1 — Self-healing provider-config restore (the core fix)

`syncService.initialize()` currently treats a missing `providerConfig` as terminal (`syncService.ts:638-643`). The fix keeps that service primitive **unchanged** and puts all heal logic in the store (avoids widening a low-level, multi-caller contract with a new sentinel — the heal decision needs `podCreated`/registry knowledge the service doesn't have):

- `syncService.initialize()` keeps its `Promise<boolean>` contract. When it returns `false` **and** the store knows the family is a Drive-backed pod (`authStore.podCreated` + registry/session), the store invokes one named orchestrator — **`attemptSilentConfigHeal(familyId)`** — the single owner of all heal/retry/state logic (no scatter). `syncStore.initialize` already wraps the service at `syncStore.ts:392-406`.
- `attemptSilentConfigHeal` runs the re-derivation (MVO: store owns the multi-subsystem workflow):
  1. **Registry read** — `registryService.lookupFamily(familyId)` → if `provider === 'google_drive'` + `fileId`, rebuild `GoogleDriveProvider.fromExisting(fileId, displayPath)`, `provider.persist(familyId)`, and `syncService.setProvider` — **persist-only, no blind `syncNow()` upload** (see Important Notes; factor a persist-only seam out of `installProvider` if needed). This is the silent path; it does NOT call `attemptResumeFromRegistry`.
  2. **Name re-resolve** — if the registry says Drive-backed but the `fileId` is stale/absent, `searchBeanpodFilesGlobal` to find the `.beanpod`, then `resolveExistingBeanpod` with `ownedByMe` (`getFileMetadata(token, fileId, 'ownedByMe')`) to adopt the **owned** match (ownership discipline per `establishDurableHomeAfterLoad` `syncStore.ts:2272-2306`), then persist as in step 1. Never adopt a foreign file.
  3. **Local pods** — if the registry says `provider:'local'`, do not guess; hand off to the §Layer-3 "reconnect needed" surface.
  4. **Idempotent + safe** — no-op if a valid provider for this family is already installed (`getProviderFamilyId() === activeFamilyId`, `syncStore.ts:2257-2258`); single in-flight guard; never `createNewFile`.
- On success, `isConfigured` becomes true and the normal load/auto-sync/polling arms as usual. When the doc + key also survived, the heal is invisible; when they were evicted too, the load pipeline surfaces `needsPassword` and the user re-enters their password once (per the User Story scope note).

**Two-tier layering (keep the state machine small).** The **localStorage-mirror tier is awaited inline** inside the store's `initialize` wrapper — it is synchronous and network-free, so the most-likely case ("IDB config evicted but `localStorage` survived") heals **before first render** and never enters the `reconnecting` state or risks a card flash. Only the **registry/Drive network tier** (steps 1–2 above) enters the deferred `reconnecting` retry (Layer 2). So the `reconnecting` state exists **only** when a genuine network round-trip is required.

**Local redundancy + honest reads (Requirement 7):** extend `storeProviderConfig`/`getProviderConfig` (`fileHandleStore.ts:145-171`) to **dual-write the provider config to `localStorage`** and read it back as the inline fallback tier — mirroring the refresh-token dual-write (`fileHandleStore.ts:181-250`).

- **Resurrection safety (critical):** `clearProviderConfig` (`fileHandleStore.ts:176-179`) AND the opposite-type clear inside the providers' `persist` must delete the `localStorage` mirror **in lockstep** with the IDB record. Otherwise `deleteLocalFamily`/`disconnect` leaves a stale mirror that the new inline read happily restores — silently resurrecting a pod the user intentionally disconnected/deleted. The mirror is cleared everywhere the IDB record is.
- **Fix the existing silent failure while here:** `getProviderConfig` (`:160-171`) currently swallows _all_ read errors and returns `null`, making a thrown/evicted IDB read indistinguishable from genuine absence. Mirror `getGoogleRefreshToken` (`:272-289`): on a thrown IDB read, `console.error` + `reportError({ surface:'provider-config-idb-read', context:{ family_id } })` **before** the `localStorage` fallback; the `localStorage` read must also `console.warn` on throw, never swallow.

### Layer 2 — Silent background retry (reuse existing machinery; only surface UI on TOTAL failure)

The **only** genuinely-new retry is re-attempting the Layer-1 **registry-lookup / `fromExisting`** step when it fails transiently (network down at cold start, OAuth proxy cold, registry/Drive 5xx). Everything downstream of a healed config is **already handled** by the existing pipeline — do not re-implement it:

- **New state (all owned by `attemptSilentConfigHeal`, all closure-scoped so `resetState` can clear them — mirror `coldStartReconnectDefer` at `syncStore.ts:261-271`):** a `reconnecting` ref, a `configHealFailed` ref, a `configHealDefer = createDeferredAction(...)` timer, and a **bounded retry budget** (a max attempt count, e.g. 4, or a wall-clock deadline). `createDeferredAction` (`syncStore.ts:225-254`) is single-shot with no counter — the budget is the terminus.
- **Re-arm:** on a transient failure (registry/Drive unreachable), re-arm `configHealDefer` **only while the budget is unspent**. Drive it off `onTokenAcquired` (already fires after the single googleAuth wake listener `googleAuth.ts:508-511` refreshes the token) — register a **separate, idempotent** `onTokenAcquired` subscriber for the heal (follow the existing `if (!tokenAcquiredUnsub)` single-registration guard; store its own unsub; cancel on `resetState`) rather than growing the existing multi-concern `onTokenAcquired` closure (`syncStore.ts:2929-2960`). **Do NOT register a new focus/pageshow/online listener set** (would duplicate `googleAuth.ts:508-511`). Past the budget, wake events are no-ops.
- **Three terminal transitions (exact):** (a) **success** → `isConfigured` true, clear `reconnecting`; hand off to the existing pipeline (below). (b) **budget exhausted** → set `configHealFailed`, clear `reconnecting`, surface Layer-3 UI + page once (below). (c) **non-retryable** (registry has no Drive home / `provider:'local'`) → immediate `configHealFailed` without burning the budget.
- **On success — two sub-cases (the connective tissue between Layer 2 and Layer 3.1):**
  - **Doc + key survived (silent case):** hand straight off to the existing silent-recovery pipeline — `backgroundSyncFromFile` (`syncStore.ts:1892-1955`: `familyKey` → `tryDecryptWithCachedKey` → else surface; its `isBackgroundSyncing` guard `:1893` prevents double-invoke against App.vue path-1a), its `finally` `startDeferredPolling` (10 s poll, `:1950-1953`), and `scheduleColdStartReconnectEscalation` (`:1831-1885`) for auth-transient escalation. Do not duplicate decrypt-retry, polling, or escalation.
  - **Key + doc cache also evicted (needs-password case):** `backgroundSyncFromFile`'s `needsPassword` branch (`:1907-1929`) deliberately does NOT navigate — it assumes "stale cached data is still usable" (`:1925`), which is false after a whole-origin eviction, so it would strand the user on empty data. So when the healed-config load hits `needsPassword` **with no usable doc cache**, the orchestrator must **navigate to `/welcome?resume=setup`** (Layer 3.1's `ResumePodSetup` → `attemptResumeFromRegistry` → `completeAutoLoad`). Only fall back to `backgroundSyncFromFile`'s stale-data surface when a doc cache actually exists. This is what makes Acceptance Criterion 2 true.
  - **Fix the related bare-`/welcome` bounce:** App.vue path1b currently redirects a load failure to **bare** `/welcome` (`App.vue:495`, no `resume` query), which the Bug-A let-through (gated on `isPodlessRecoveryQuery`) will NOT catch → the podCreated owner bounces to `/nook` (the reload-loop hazard documented at `App.vue:517-524`). Route path1b's podless-recovery case to `/welcome?resume=setup` so it reaches recovery.
- Every attempt is silent — no toast/banner. While `reconnecting`, the card reads "reconnecting…" (Layer 3), never the raw unconfigured card.
- **Total failure surfacing (only place we page):** on transition (b)/(c), surface the Layer-3 reconnect/reload affordance and page `sync-config-total-failure` (`severity:'critical'`) behind a **once-per-session/per-family guard** (mirror `zombieStateReported` `router/index.ts:391`; reset in `resetState` so a different family can still page). Reuses the "defer past the recovery window, then critical" pattern at `syncStore.ts:1871-1883`.

### Layer 3 — Correct recovery affordance for `podCreated && !isConfigured`

1. **Un-strand `resume=setup` (Bug A).** In the already-auth guard, add an early **let-through `return`** for `authStore.podCreated && isPodlessRecoveryQuery(to.query.resume)` — mirroring the exact shape the `needsPodSetup` branch already uses at `router/index.ts:363` (`if (isPodlessRecoveryQuery(to.query.resume)) return;`), NOT a redirect to the same path (which would self-redirect). **Gate on `podCreated` (durable) only — NOT on `isConfigured`** (transient; see the guard-rail below). A configured owner who reaches `/welcome?resume=setup` simply lands on `ResumePodSetup`, which harmlessly re-loads their existing pod; a configured owner on bare `/welcome` still bounces to `/nook`. This lets the user reach `ResumePodSetup`, whose existing `attemptResumeFromRegistry` → `completeAutoLoad` (interactive password) machinery is the correct home for the password-required recovery. Preserve the `membersStepActive` exemption (`:357`). Reuses the tested resume path — no bespoke screen. **Guard-rail:** the guard decides routing **only** on `isPodlessRecoveryQuery(to.query.resume)` — it must NEVER branch `/nook`-vs-recovery on the bare value of `syncStore.isConfigured` (which is transiently `false` during every cold boot before the heal completes, and would cause intermittent mis-routing). This keeps the guard a pure function of the URL — deterministic and trivially unit-testable.
2. **Add a Drive reconnect/reload button to the unconfigured card (Bug B)** (`SettingsPage.vue:1210-1217`), shown when the registry/session indicates a Drive-backed pod. It calls the Layer-1 re-derivation orchestrator (reconnect Google via the existing `handleSettingsReconnect`/`reconnect` seam `:306-311`, then re-resolve + reload the Drive `.beanpod`) — **not** `handleResumeSetup` (dead) and **not** the local-file picker. Keep "load existing family data file" for genuinely local/imported pods.
3. **"Reconnecting…" card state.** While Layer 2's silent retry is in flight, render a lightweight "reconnecting…" state in the card (i18n string, all surfaces) rather than the full unconfigured layout, so the "save your data to a file" copy never flashes for a pod merely mid-reconnect.

### Layer 4 — Edge-case handling

- **Init-ordering race (H3):** the silent retry naturally re-runs once the family becomes known, covering "familyId was null on the first pass" (`syncService.ts:553`). Additionally ensure any native resume/deep-link entry activates the family (`setActiveFamily`) before `syncService.initialize()`.
- **Concurrent worker death:** re-derivation reuses `replaceDocWithCacheRecovery`'s discipline (`syncStore.ts:551-581`) so healing the provider never corrupts the doc.
- **Expired token during restore:** Layer-1 step 1 runs `beginDriveAuthRedirectIfNeeded`/`tryReconnectSilently` (as `attemptResumeFromRegistry` already does `syncStore.ts:2662-2670`) — silent refresh before any redirect; on a redirect surface it returns `redirecting` and resumes on return (ADR-026/029).
- **Multi-device / ownership, sign-out scoping, `membersStepActive`** — per Important Notes & Caveats.
