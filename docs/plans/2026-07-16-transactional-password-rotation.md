# Plan: Transactional password rotation — durably save or fully roll back

> Date: 2026-07-16
> Related issues: Notion #54 (no GitHub issue — direct implementation)
> Plan file: `docs/plans/2026-07-16-transactional-password-rotation.md`

## User Story

As a family member changing or resetting a password, I want the change to either be durably saved to my family file OR fully undone with an error, so that I'm never told "done" while the new password lives only in this device's cache — where it could be lost, or leave my old password still working on another device.

## Context

`rotateMemberPassword` (`src/stores/authStore.ts:93-155`) is the single home for the 4-step credential rotation, called by three surfaces (`change-password`, `reset-member-password`, `signin-heal`). Today it:

1. guards `syncStore.familyKey`;
2. `wrapFamilyKeyForMember(memberId, newPassword)` — re-wraps the family key into `envelope.wrappedKeys[memberId]` (in-memory + cache);
3. `hashPassword` + `familyStore.updateMember({passwordHash, requiresPassword:false})` — mutates the Automerge doc;
4. `syncStore.syncNowBounded()` — a **5s `raceTimeout(syncNow(true), …)`** that **resolves-and-proceeds**;
5. returns `{ success:true, syncDeferred:!synced }` regardless of whether Drive actually saved.

So on a slow/offline/token-rejected Drive push the rotation still reports success and the new credential reaches only the local IndexedDB cache. Consequences: the change can be silently lost (cache cleared before the deferred push lands), or another device still unwraps Drive's key with the **old** password. This was intentionally kept as status-quo in 0.9.5R8 (0.9.5R3/R4 only fixed the _spinner hang_); this issue makes the rotation path **durable-or-rollback**.

`raceTimeout` (`src/utils/timing.ts:39`) resolves `undefined` on timeout (best-effort, no throw) and — critically — does **not** cancel the underlying promise; `withTimeout` (`:16`) is the throwing variant (unused here). `syncNow(true)` (`syncStore.ts:576`) → `syncService.save()` returns a `boolean` (true = written to Drive, false = failed; it never throws). `save()` (`syncService.ts:784`) serializes every write through the module-level `saveInProgress` **mutex** — the lever this plan relies on for split-brain convergence. `doSave()`'s `currentProvider.write()` (`syncService.ts:934`) is **non-cancellable**, and `doSave` first runs `fetchAndMergeRemote()` (`:812`) which CRDT-merges the remote doc and does a **local-wins** `preserveLocalKeyDicts` merge of the envelope key-dicts (`:858`).

## Requirements

1. **Transactional user-initiated rotation.** For `change-password` and `reset-member-password`: capture the old `(wrappedKeys[memberId] entry, passwordHash, requiresPassword)` before mutating; block on the **real** Drive save (bounded, ~12s); on durable success report success; on save-failure/timeout **fully roll back** all three pieces, leave the OLD password working, surface the error, and change nothing.
2. **Distinguish saved vs not-saved.** Replace the resolve-and-proceed for the user paths with a bounded call that yields three outcomes: saved (`true`), save-failed (`false`), timed-out (`undefined`) — the latter two both trigger rollback.
3. **Split-brain convergence.** After a rollback, trigger a durable re-save of the rolled-back (old-password) state so it serializes BEHIND any stray in-flight new-password upload via the `save()` mutex and Drive converges back to the old password. If that convergence re-save itself fails, emit a `critical` signal (data-at-risk: possible cross-device lockout window).
4. **No partial rotation.** The existing `updateFailed` path (wrap succeeded but `updateMember` returned null) must also roll back the wrap, so we never persist a half-rotated envelope (wrappedKey rotated, hash reverted, or vice-versa).
5. **Signin-heal stays best-effort.** `signin-heal` (re-wraps with the CURRENT password — no old/new split-brain) keeps the current bounded resolve-and-proceed behavior: NO blocking of sign-in, NO rollback, NO error surface; failures reported via `reportError` only, sign-in proceeds. Branch on `surface === 'signin-heal'`.
6. **Error copy + spinner label (i18n).** User-initiated failure shows, via the modal's existing inline `formError` red panel (NOT a toast — that is the established pattern in both modals): _"Couldn't save your new password. Nothing changed — your current password still works. Please check your connection and try again."_ While the durable save blocks, the modal shows a _"saving your new password…"_ label in place of the default `common.saving` spinner text. Both via `t()` with `en` + `beanie` + `zh`.
7. **Observability.** A `password-rotation` outcome event on BOTH success and rollback (so the failure _rate_ is measurable), carried on **existing allowlisted context keys** (`action` = outcome, `error_code` = reason) per the codebase's documented telemetry convention — no new context keys, no privacy-manifest churn; `critical` (via the already-allowlisted `severity` key) reserved for a convergence re-save that itself fails.
8. **Unit tests** for: durable-save success; save-fail rollback restores all 3 pieces; timeout rollback + convergence re-save; the `updateFailed` wrap-rollback; signin-heal best-effort (no block/rollback/error surface); no-prior-entry rollback (removes the entry).

## Important Notes & Caveats

- **`syncNowBounded` (5s) stays as-is for its other callers** (login-completion best-effort saves + signin-heal). Do NOT change its timeout or semantics — the two user rotation surfaces call the SAME `syncNowBounded(timeoutMs)` with the longer ~12s bound (it already coerces `undefined`→`false`, collapsing timeout+fail into "not saved"), so no new bounded helper is introduced. (DRY: the durable-save + rollback logic itself lives in ONE place — inside `rotateMemberPassword` — not copy-pasted per caller.)
- **`requiresPassword` is DERIVED, not stored.** `familyMemberRepository.applyDefaults` derives `requiresPassword` from `!passwordHash` on every read (authStore.ts:36-38). Restoring `passwordHash` alone therefore already restores `requiresPassword` on the next read. Capture it in the snapshot for the explicit `updateMember` restore call, but treat `passwordHash` as the source of truth; the observable end-state must be the pre-change one either way.
- **Restoring / removing the wrappedKey entry needs a NEW setter.** `syncStore.addMemberWrappedKey` (`syncStore.ts:1641`) is **additive-only** (spread-assign; there is no existing removal helper anywhere — confirmed by grep). Generalize it into `setMemberWrappedKey(memberId, entry: { wrapped; salt } | undefined)` that **deletes** `env.wrappedKeys[memberId]` when `entry` is `undefined` and assigns otherwise, then persists via the same `setEnvelope` RPC (worker cache stays in sync). `addMemberWrappedKey` delegates to it (DRY — one code path, one persist). Rollback (via `restoreCredential`) calls `setMemberWrappedKey(memberId, old.wrappedKeyEntry)` — which correctly **removes** the entry when the member had no prior one (first-time password set), rather than leaving the new one behind. (Note: `wrapFamilyKeyForMember` builds a fresh `env`/`wrappedKeys` object via spread rather than mutating in place, so the captured `old.wrappedKeyEntry` reference stays valid — no aliasing hazard between capture and restore.)
- **Rollback is one restore helper, not scattered mutations.** Both rollback sites reconstruct the pre-change state from the same captured `old` snapshot. To keep `rotateMemberPassword` shallow and the rollback logic single-sourced (so the two sites can't drift), extract a small **local** helper `restoreCredential(memberId, old, { wrapOnly })` inside authStore: it always calls `setMemberWrappedKey(memberId, old.wrappedKeyEntry)`, and (unless `wrapOnly`, the `updateFailed` case where the hash never changed) also `updateMember(memberId, { passwordHash: old.passwordHash, requiresPassword: old.requiresPassword })`. This is a private function-scoped helper — no new module, no new indirection layer — purely to keep the main body linear and the restore identical across both call sites.
- **The convergence argument (state precisely in code comments — do NOT rely on coarse "file LWW"):**
  - `save()` serializes all writes through `saveInProgress`. Because `raceTimeout` does **not** cancel the underlying `save()` promise and `doSave`'s `write()` is non-cancellable, on a ~12s timeout `saveInProgress` still holds the in-flight new-password `doSave`. The subsequent convergence `save()` sees it truthy, `await`s it, and only then runs its own `doSave` — i.e. the old-password write is enqueued strictly **behind** the new-password write.
  - Within that trailing `doSave`, `fetchAndMergeRemote` reads Drive's base (which is this device's own just-pushed new-hash state), CRDT-merges it into the local doc where the **rollback `updateMember` op is causally later** than the original new-hash op → the rollback wins the register (no true conflict; it is our own history). The envelope `wrappedKeys` converge via `preserveLocalKeyDicts` **local-wins** (local is the rolled-back old entry). The trailing write then persists the old-password base → Drive converges to the old password.
  - **Residual window (what `critical` flags):** new-password `write()` succeeds AND the trailing old-password re-save then fails → Drive briefly holds the new password while local is old. It self-heals on the next successful auto-sync of the (old) local state, but a sign-in on another device inside that window would see the new password.
- **`critical` is a deliberate fail-safe over-approximation.** The code trigger is simply "convergence re-save did not confirm" (`!reSaved`), which is _coarser_ than the exact residual-window scenario above: in the pure-timeout path the trailing re-save can queue behind a still-stuck first `save()` and itself time out even though that first `write()` never reached Drive (so there is, in fact, no cross-device exposure). We accept these benign false-positive pages rather than risk a _silent_ cross-device-lockout window — a ~24s-wedged rotation is itself an investigate-worthy anomaly, and paging conservatively on genuine data-ambiguity is the fail-safe choice. The `may hold` / `possible` hedging in the telemetry copy reflects this intentionally.
- **The convergence re-save is intentionally `await`ed** (not fire-and-forget). Awaiting adds up to ~12s of extra spinner _only_ in the already-degraded stuck-save path (where the user is being shown an error regardless), and in exchange gives a deterministic, testable `critical`-on-failure signal with no floating promise / unhandled-rejection surface. The mutex-ordering convergence argument holds whether or not the caller awaits, so awaiting costs nothing structurally — it is the simpler, more robust choice.
- **Do NOT make signin-heal block sign-in.** A durable/blocking heal would regress the very spinner-freeze class fixed in 0.9.5R3/R4. Keep it best-effort. `healStaleWrappedKey` already awaits-and-discards the rotate result, so no caller change is needed there.
- **Telemetry reuses existing allowlisted keys — no new context fields.** The codebase has a documented convention (`diagnosticContext.ts:160-161`, `:168-171`): _outcome rides the existing `action` key; transient cause rides `error_code`; surface rides the report's own `surface` field_. Following it means this change adds **zero** keys to `ALLOWED_CONTEXT_KEYS`, so it does NOT touch the Lambda allowlist mirror + its pinned test, `docs/runbooks/native-store-submission.md`, `ios/App/App/PrivacyInfo.xcprivacy`, the store Data-Safety/App-Privacy answers, or `web/src/pages/privacy.astro`. `member_id_tail` (already allowlisted + store-declared for exactly these rotation surfaces, `diagnosticContext.ts:107-111`) is likewise reused. This deliberately avoids introducing three near-synonym keys (`rotation_surface`/`rotation_outcome`/`rotation_reason`) and the six-surface cross-repo coupling they would create.
- **Out of scope:** the already-fixed login-completion `raceTimeout` sites (0.9.5R3/R4) — untouched. This reworks only the rotation path's durability.
- **No feature gate; no GitHub issue.** All-surface (web/PWA/iOS/Android) — pure TS in stores/services + two Vue modals, no native code.

## Approach

All rotation-durability logic stays inside `rotateMemberPassword` (the single home) — callers are unchanged except for mapping the new failure outcome to their existing inline `formError`.

**A. Capture-before-mutate.** At the top of `rotateMemberPassword` (after the `familyKey` guard), snapshot `old = { wrappedKeyEntry: env.wrappedKeys?.[memberId], passwordHash: member.passwordHash, requiresPassword: member.requiresPassword }` (read `env` from `syncStore.envelope`, the member via the family store). Cheap; captured for all surfaces so rollback is always possible without special-casing the read.

**B. Mutate** exactly as today (wrap → hash → updateMember). If `updateMember` returns null (existing `updateFailed`), **roll back the wrap** via `restoreCredential(memberId, old, { wrapOnly:true })` before returning `updateFailed`, so no half-rotation persists (Requirement 4).

**C. Durable save vs best-effort, by surface.** Split cleanly on surface so each path reads linearly (no interleaved branching):

- **signin-heal:** unchanged — `await syncStore.syncNowBounded()` (5s best-effort). No rollback, no error surface. (Result is discarded by `healStaleWrappedKey`; see E on dropping `syncDeferred`.)
- **change-password / reset-member-password:** `const saved = await syncStore.syncNowBounded(DURABLE_ROTATION_SAVE_TIMEOUT_MS)` (~12000). `saved` collapses timeout+fail into "not saved" (both roll back). If `saved` → return `{ success:true }`. If `!saved` → **roll back** (step D) and return `{ success:false, error:'saveFailed' }`.

**D. Rollback (user surfaces).** `restoreCredential(memberId, old)` restores all three pieces (the wrap via `setMemberWrappedKey` — restoring a prior entry or **removing** the new one if there was none — plus `passwordHash` + derived `requiresPassword` via `updateMember`). Then **convergence re-save:** `const reSaved = await syncStore.syncNowBounded(DURABLE_ROTATION_SAVE_TIMEOUT_MS)` — serialized behind any stray in-flight upload via the mutex. If `!reSaved`, emit the `critical` telemetry (data-at-risk). Return `{ success:false, error:'saveFailed' }`.

**E. Result type + callers.**

- `RotateError` gains `'saveFailed'` (flows into `ResetError` via the union). The closed union gives compile-time enforcement that every caller maps the new case (per the existing no-silent-failures contract at authStore.ts:80-82).
- **`syncDeferred` is now dead under the durable model** — user-surface success is always durable (never deferred), and signin-heal's caller discards the result. Simplify `RotateResult` to `{ success:true } | { success:false; error:RotateError }` (drop `syncDeferred`), and drop it from `resetMemberPassword`'s return type. This removes the now-dead deferred-sync branch in `ResetMemberPasswordModal` (`:92`) and its test (`:152-153`) rather than leaving unreachable code (no dead-code, no silent no-op).
- `changePassword` adds a `saveFailed` entry to its existing `errorMessages: Record<RotateError, string>` record, set to `useTranslationStore().t('changePassword.error.saveFailed')`, displayed inline via `formError` (its existing pattern). Note the three legacy entries in that record are hardcoded English (pre-existing, English-only); only the new `saveFailed` entry is i18n'd via `t()` — migrating the legacy strings is out of scope, and mixing a `t()` value among them is type-safe (`t()` returns `string`) and correct.
- `ResetMemberPasswordModal` already translates `t('family.resetPassword.error.${result.error}')` (`:100`), so it just needs the new `family.resetPassword.error.saveFailed` key. (Per the documented convention at authStore.ts:770-772, each surface owns its error copy — so the same approved sentence lives under each surface's key namespace; this is intended surface-ownership, not duplication to hoist.)

**F. Loading label (shared, DRY).** Add an optional `submittingLabel?: string` prop to `BeanieFormModal` defaulting to `t('common.saving')`; render it in place of the hardcoded `common.saving` at `:171`. Both rotation modals pass `:submitting-label="t('auth.passwordRotation.savingLabel')"`. This is a generic, reusable enhancement to the shared modal (benefits any future long-running save), not per-modal duplication, and the existing `is-submitting` spinner already provides the loading mechanism — only the label text is new.

**G. i18n.** Add to `uiStrings.ts` (en + beanie): `changePassword.error.saveFailed`, `family.resetPassword.error.saveFailed` (the approved error copy, per-surface namespaces), and `auth.passwordRotation.savingLabel` ("saving your new password…", shared). Add zh via the translate pipeline. `common.saving` stays the modal default.

**H. Constant.** `DURABLE_ROTATION_SAVE_TIMEOUT_MS = 12000` colocated with `POST_AUTH_SAVE_TIMEOUT_MS` in `syncStore.ts`. Keep `POST_AUTH_SAVE_TIMEOUT_MS = 5000` unchanged.

## Observability Coverage

Rotation outcomes are reported on the existing per-caller `surface` (the `RotateSurface` value already passed to `reportError` today — `change-password` / `reset-member-password` / `signin-heal`), carrying the outcome on the existing allowlisted **`action`** key and any reason on **`error_code`** — the codebase's documented telemetry convention (`diagnosticContext.ts:160-161`, `:168-171`). No new context keys.

- **Success (user surfaces):** `logEvent({ level:'info', surface, message:'rotation saved durably', context:{ action:'rotation-saved', member_id_tail } })`. Emitting on success makes the failure _rate_ measurable (Requirement 7 / alerting) — queryable by `action`.
- **Rollback (user surfaces):** `reportError({ surface, severity:'warning', message:'password rotation rolled back — durable save did not confirm', context:{ action:'rotation-rolled-back', error_code:'not-saved', member_id_tail } })`. Firehose + console; no page (the user retains a working old password + sees the inline retry copy).
- **Convergence re-save failed (data-at-risk):** `reportError({ severity:'critical', surface, message:'rollback re-save did not confirm — Drive may hold the new password while local reverted (possible cross-device lockout window)', context:{ action:'rotation-resave-failed', member_id_tail } })`. This is the ONE `critical` (Slack page + flush) — reserved for genuine data-at-risk; `severity` is already allowlisted (`diagnosticContext.ts:92`), `ErrorSeverity` supports `'critical'` (verified `errorReporter.ts:42`). As noted in the caveats, the `!reSaved` trigger is a deliberate over-approximation (may fire benignly when the in-flight save merely stuck and never reached Drive) — accepted as fail-safe-toward-paging over a silent exposure.
- **signin-heal:** emit the outcome too (`surface:'signin-heal'`, `action:'rotation-saved'|'rotation-deferred'`) at `info` so its rate is visible without paging.
- **No bare catch:** the `wrapFamilyKeyForMember` / `updateMember` failures already `reportError`; the new rollback branches report as above. No silent fallback.
- **Privacy/store gate — satisfied by reuse, not new keys:** `action`, `error_code`, `severity`, and `member_id_tail` are all already in `ALLOWED_CONTEXT_KEYS` and already store-declared, so nothing is silently stripped and no privacy-manifest/Lambda-mirror edits are required. All carried values are low-cardinality developer-authored enums / a UUID tail — no PII (no full member id, no hash, no password).

## Acceptance Criteria

- [ ] A user-initiated change/reset reports success ONLY after the Drive `.beanpod` write confirms (durable).
- [ ] On save-failure or ~12s timeout, the local `passwordHash` + derived `requiresPassword` + `wrappedKeys[member]` are fully restored (entry removed when there was no prior one), the OLD password still unlocks, and the user sees the approved retry copy inline — with NO partial change.
- [ ] After a rollback, a convergence re-save of the old-password state is issued (serialized behind any in-flight upload); if it fails, a `critical` event fires.
- [ ] The `updateFailed` path also rolls back the wrap (no half-rotation).
- [ ] `signin-heal` never blocks sign-in, never rolls back, never surfaces an error UI; it reports failures via `reportError` and proceeds.
- [ ] Error copy + "saving your new password…" label render via `t()` in en + beanie + zh.
- [ ] `password-rotation` telemetry fires on success + rollback (+ `critical` on re-save failure) using only existing allowlisted keys (`action`/`error_code`/`severity`/`member_id_tail`) — no allowlist or privacy-manifest edits.
- [ ] Unit tests below all pass; full Vitest suite + type-check + lint + `npm run translate` clean.
