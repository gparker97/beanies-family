# P1 — Deployed read paths for a `version: "5.0"` pod (audit of `c3a6be98`)

> Date: 2026-09-06
> Build audited: `c3a6be98` (release 0.16, the last prod deploy). Every `file:line` is from that commit, read with `git show c3a6be98:<path>` / `git grep … c3a6be98 -- src`. The working tree was NOT consulted.
> Labels: **VERIFIED** = I read the lines cited. **INFERRED** = reasoned from adjacent verified code; the inference is stated.
> Status: COMPLETE (all five questions answered).

## Verdict

**PREMISE FAILS.** The deployed build cannot MERGE a v5 pod: every Automerge merge entry point sits behind a strict `'4.0'` check, and no read-path failure wipes the IndexedDB cache or deletes a credential. But it CAN DESTROY one: the Drive create-path collision resolver classifies any file that is not a `'4.0'` envelope as an empty placeholder, adopts it as the write target without asking, and the create flow writes a brand-new pod over it (Finding 1). Separately, the ordinary save path on a warm-cache device overwrites a v5 pod with the local v4 envelope without ever parsing it (Finding 2, owned by P2/P3 but reachable from the read-path trace).

## Findings, most severe first

### F1 — `isStubBeanpod` treats a v5 pod as an orphan stub and the create flow writes over it (DESTRUCTIVE) — VERIFIED

The strict parser is bypassed on exactly one read path, and it is the one that writes.

- `src/services/sync/connectStorage.ts:245-251` `isStubBeanpod(text)`: empty / `'{}'` → stub; then `return detectFileVersion(text) !== '4.0';` with the comment "Anything that isn't a real V4 envelope is treated as a non-pod stub." A `"5.0"` envelope makes `detectFileVersion` return `null` (`fileSync.ts:95-96`), so the predicate returns **true**.
- `connectStorage.ts:224-242` `resolveExistingBeanpod`: reads the colliding file (`:233`, a read-only probe) and returns `{ kind: 'adopt-stub' }` when `isStubBeanpod` is true (`:234-235`). The catch (`:237-241`) fails SAFE to `adopt-existing`, but a v5 pod does not throw, it classifies cleanly as a stub.
- `src/composables/useDriveCollisionRecovery.ts:59-69`: the `adopt-stub` branch is **not confirm-gated**. It calls `adoptDriveStub` and returns `{ kind: 'adopted-stub' }`. Only the `adopt-existing` branch asks the user (`:72-78`).
- `connectStorage.ts:259-269` `adoptDriveStub`: installs a `GoogleDriveProvider.fromExisting(fileId, …)` on the v5 file's fileId via `syncService.setProvider` and persists the provider→family mapping.
- Trigger: `src/services/sync/providers/googleDriveProvider.ts:526-541` `createNew` lists the app folder and throws `FileNameCollisionError` on an **exact filename match** (`:533`), carrying `ownedByMe`. `connectStorage.ts:172-182` turns that into `errorKind: 'name-collision'`. So the precondition is: the pod OWNER's Google account, creating a family whose name yields the same `<name>.beanpod`.

Two callers consume the resolution:

**Chain (a) — fresh create, `CreatePodView.vue` — reaches the write.** `src/components/login/CreatePodView.vue:280-296`: on `name-collision` → `resolveDriveCollision` → `case 'adopted-stub'` sets the storage step to its success state ("write into the adopted file"). The wizard then calls `createNewFile` with the **new** familyId minted at sign-up. `src/stores/syncStore.ts:1785-1807`: the existing-pod registry guard looks up THAT familyId, finds nothing, and proceeds; `:1866 await provider.write(envelopeJson)` writes a fresh, empty, **new-family-key** v4 envelope into the compacted family's file. `:1903 _registerCurrentFamilySync` then registers the new familyId against the same fileId. Every other device (on any build) that next reads the file sees a different `familyId`, and the compacted history is no longer in the file.

**Chain (b) — recovery screen, `ResumePodSetup.vue` — guarded only by the registry.** `src/components/login/ResumePodSetup.vue:263-275`: a v5 pod makes `attemptResumeFromRegistry` return `load-failed` (`syncStore.ts:3676-3684`, since `loadFromGoogleDrive` fails the gate at `:3554-3558`), which routes to the `retry` phase and shows `resumeSetup.couldNotFindPod`. The retry screen's "Set up my family" (`:295-300`, an INFO confirm, described in its own comment as SAFE "because the adopt-existing recovery protects the create path") leads to `finishOnDrive` (`:719-788`) → collision → `case 'adopted-stub': await finalizePod()` (`:735-737`) → `createNewFile` with the **real** familyId. Here the registry guard (`syncStore.ts:1787-1796`) refuses with `reason: 'existing-pod'` and `ResumePodSetup.vue:597` routes back to retry. This chain is blocked **only while the registry answers**: `syncStore.ts:1798-1806` proceeds on a lookup exception, and `:1814-1821` proceeds on `status: 'unavailable'` (a deliberate, logged fail-open). Under a registry outage chain (b) writes over the pod exactly like chain (a).

Why this matters for the proposal: the v5 bump converts a guard that was designed to be safe ("is this file a real pod or my own `{}` orphan?") into the trigger. On the deployed build the file's non-v4-ness is the _evidence that it is safe to overwrite_. The README's motivating case (a cold device on a stale build) is precisely a device that arrives at these screens: a cache-less boot falls through to the recovery overlay (`src/App.vue:690-704`), the login page's generic picker shows "Unsupported file version" (`LoadPodView.vue:421-424`), and the resume screen says the pod could not be found (`ResumePodSetup.vue:273`). A user who then "starts fresh" with the same family name reaches chain (a).

INFERRED (not verified at this commit): whether Google Drive retains the prior revision of an app-folder file after the overwrite, which would make the compacted content recoverable by hand. Nothing in the code relies on it.

### F2 — The save path overwrites a v5 pod without ever parsing it (DESTRUCTIVE; P2/P3 crossover) — VERIFIED

On a warm-cache open, `loadFromPersistenceCache` sets the family key and the **cached v4 envelope** into `syncService` (`syncStore.ts:1461-1463`), so `doSave`'s guard `if (!currentFamilyKey || !currentEnvelope)` (`syncService.ts:1234`) passes. The background open then reads Drive: `syncService.load()` learns the remote marker (the v5 revision) BEFORE the download (`:1429-1431`), and `loadFromFile` fails the version gate (`syncStore.ts:970-974`) and returns without committing anything. The in-memory baseline now holds the v5 revision with `headsFp: null`. The next local edit arms a save; `doSave` → `fetchAndMergeRemote` → `remoteChanged()` → `compareMarkers` sees an equal revision and returns `'unchanged'` (`remoteBaseline.ts:224-226`) → `fetchAndMergeRemote` returns at `syncService.ts:1178` **before** `parseBeanpodV4` at `:1192` → `doSave` continues to `:1286-1309` and `providerAtWrite.write(fileContent)` replaces the v5 pod with the local v4 envelope. Even when the read does happen, the parse throw is swallowed at `:1268-1272` with a `console.warn` only and the write still proceeds. This is the "revert" the README anticipates; the mechanism is the baseline skip, not the swallowed throw. Owned by P2/P3; recorded here because it is the first thing that happens on every warm-cache stale device after the version turns.

### F3 — The version failure never reaches the firehose on the Drive paths (OBSERVABILITY) — VERIFIED

- `loadFromFile` (`syncStore.ts:970-974`) only sets `error.value`; no `logEvent`/`reportError`.
- `backgroundSyncFromFile` classifies the bare `{ success: false }` as `'network'` (`syncStore.ts:2700-2719`); `endOpen` carries the open-guard reason as `error_code` (`:2740`), not the version.
- `doSave`'s swallow is `console.warn` only (`syncService.ts:1271`).
- `loadFromGoogleDrive` (`syncStore.ts:3555-3557`) sets `error.value` only.
- The only firehose events: the web local-file poll's `reportError` at `severity: 'warning'` (`syncService.ts:228-234`, FSA provider only, `localProvider.ts:270-272` is the sole poller), `ResumePodSetup`'s `resumeSetup.autoLoadFetchFailed` at `'error'` (`:267-272`), `useJoinFlow`'s `FILE_READ_FAILED` (`:452-457`, `:513-518`), and `rebindPodFile`'s **critical** page (`syncStore.ts:3861-3871`, the only path that pages Slack). Triage from CloudWatch alone would see "network" refresh failures and "could not find pod" resume failures, not a version mismatch.

### F4 — The user is told the wrong thing (WRONG MESSAGE) — VERIFIED

`backgroundSyncFromFile` shows `'Could not refresh data from cloud'` with kind `'network'` (`syncStore.ts:2715-2717`), toasted by `BackgroundSyncBar.vue:38-40`, while the stale cache stays on screen and polling continues (`:2731-2733`). `ResumePodSetup` shows `resumeSetup.couldNotFindPod` (`:273`) for a pod that exists. `LoadPodView`/`JoinPodView` show the raw English `Unsupported file version: unknown` via the `lastError → error` mirror (`syncStore.ts:467-476`; `LoadPodView.vue:421-422`, `:601-602`, `:866-867`; `JoinPodView.vue:196-197`).

### F5 — Sub-paths that fail silently (outcome e) — VERIFIED

- `syncStore.requestPermission` (`syncStore.ts:626-631`): grant succeeds, load fails, nothing is surfaced.

## Q3 — The IndexedDB cache

**No rehydrate or reconcile path compares the cached envelope's version with the remote's, and nothing on a read path wipes the cache.** VERIFIED:

- The envelope cache is written only through `persistEnvelopeSafely` from `setFamilyKey`/`setEnvelope` (`syncService.ts:550-606`) and `createNewFile` (`syncStore.ts:1897`), always from a typed `BeanpodFileV4` that came out of `parseBeanpodV4` or `createBeanpodV4`. Remote TEXT never enters the cache.
- The reader `loadCachedEnvelope` (`cache.ts:352-363`) is a lenient `JSON.parse(entry.payload) as BeanpodFileV4`, but it can only ever return what this build wrote (a v4).
- The only read-path cache wipe is `applyAndProject.ts:493-505` inside `initAndLoadCache`, triggered by `cache.loadCachedDoc` throwing `CorruptPayloadError` on the **cached base** (`cache.ts:299`); no remote bytes are involved. `docClient.clearCache` has one production caller, `database.ts:70 deleteFamilyDatabase`, whose callers are sign-out (`authStore.ts:2355-2357`), Settings clear-data (`SettingsPage.vue:695`) and `deleteLocalFamily` (`familyContext.ts:149-151`), all user-driven.
- The worker's `mergeRemoteEnvelope` (`applyAndProject.ts:617-694`) and `verifyEnvelope` (`:699-703`) throw upward on a bad payload and never clear anything; `docClient.surface` (`docClient.ts:822-826`) keeps `CorruptPayloadError` quiet but takes no action.
- Re-download loop: none on Drive. `load()` learns the revision before the read (`syncService.ts:1429-1431`), so after the gate fails `compareMarkers` reports `'unchanged'` (`remoteBaseline.ts:224-226`) and both `reloadIfFileChanged` (`syncStore.ts:2792`) and `doSave` skip the read. This is also what arms F2.

Credentials (outcome c): the only read-path key clears are `tryDecryptWithCachedKey` (`syncStore.ts:2509`) and `LoadPodView.tryAutoDecrypt` (`:184`), both gated on a parsed V4 `pendingEncryptedFile`, which a v5 pod never populates; `revokeUnattendedReopen` (`authStore.ts:2233`) is raised only by a roster rejection computed from a DECRYPTED doc (`familyStore.ts:365-389`), which a v5 pod cannot alter (INFERRED from those lines); `healStaleWrappedKey` (`authStore.ts:367-395`) re-wraps rather than deletes; the single `delete wrappedKeys[...]` (`syncStore.ts:2185`) is a password-change mutation. No wrong-password loop (outcome d): every wrong-password prompt is downstream of a parsed V4 envelope.

## Q4 — Lenient-parse hazard

Only one lenient consumer of pod TEXT exists, and it is F1: `isStubBeanpod` (`connectStorage.ts:245-251`). The complete list of places that obtain pod text (grep `\.read\(\)|\.text\(\)`, non-test): `connectStorage.ts:233`, `syncService.ts:1189`, `:1447`, `:1535`, `:1586`, `:1626`, `syncStore.ts:1518`, `:3548`, `:3796`, and `useSharedDocumentIngest.ts:598-600` (the share-target ingest reading a shared `.txt`; no `.beanpod` routing exists under `src/services/share/`, whose adapters only build `File` objects for that ingest: `androidShareAdapter.ts:34`, `iosOpenInAdapter.ts:104`, `iosShareAdapter.ts:80`). Every other `JSON.parse` in `src` is unrelated state (settings, OAuth state, baseline rows at `remoteBaseline.ts:138-170`, snapshots). The only `as BeanpodFileV4` casts are the worker's RPC boundary (`applyAndProject.ts:868/875/883`, already typed on main) and the cache reader above. The invite/join surfaces (`inviteService.ts`, `JoinPodView.vue`, `useJoinFlow.ts`) contain no parse of their own; `tryInviteTokenDecrypt` reads `inviteKeys` off the parsed pending envelope (`useJoinFlow.ts:532-536`). `driveService` readers outside the providers are photo blobs (`photoStore.ts:574`) and a save helper. `web/` and `scripts/` contain prose only; `scripts/promo-video/seed.ts:5` writes an in-memory doc.

## Q5 — Residual

On the deployed build a `version: "5.0"` pod can **never reach an Automerge merge**: all five `docClient.mergeRemoteEnvelope` call sites (`syncService.ts:1202`; `syncStore.ts:847`, `:866`, `:1010`, `:1038`, `:1238`, `:2028`) take an envelope produced by `parseBeanpodV4` (`fileSync.ts:73-75` throws on any version but `'4.0'`) or gated by `detectFileVersion`, and the pending-envelope consumers can only hold a parsed V4. It also never triggers the corrupt-payload cache wipe or a credential clear. But it **can trigger a destructive write, twice over**: (1) the Drive create-path collision resolver classifies the v5 file as an empty orphan and, with no confirmation, adopts it as the target for a new pod written with a new family key (F1; unguarded on a fresh create, guarded on the resume screen only while the family registry is reachable); and (2) every warm-cache stale device overwrites the v5 pod with its cached v4 envelope on its next save, because the version gate leaves the baseline equal to the v5 revision and the save path skips the read (F2, P2/P3). The "cannot parse, therefore cannot corrupt" premise holds for merge and fails for overwrite; a version bump on its own does not make a stale build safe, it changes which code path destroys the file.

## Cross-references for the other audits

- P2/P3: F2 is the precise sequence; note the baseline-equal skip at `syncService.ts:1178` happens before the swallowed throw at `:1268-1272`, so a fix to the swallow alone would not stop the overwrite.
- P5/P6: any design that leaves a non-`'4.0'` file on Drive must first change `isStubBeanpod` (`connectStorage.ts:245-251`) on the NEW build and accept that DEPLOYED builds will keep treating the file as an orphan stub until they update; a version bump therefore needs the fleet drained BEFORE the first compacted write, not after, or the stub predicate needs a shape the old build reads as "populated" (e.g. keep `version: '4.0'` and refuse later, which trades F1 for the decrypt-time question P6 owns).
