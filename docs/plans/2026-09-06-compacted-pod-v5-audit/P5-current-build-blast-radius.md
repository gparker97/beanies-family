## Summary of the minimal change set

The literal `'4.0'` is load-bearing in exactly **three production places** and one type: the writer for a brand-new file (`createBeanpodV4`, `src/services/sync/fileSync.ts:40`), the validator (`parseBeanpodV4`, `fileSync.ts:73-75`), the detector (`detectFileVersion`, `fileSync.ts:97-105`), and the literal type `BeanpodFileV4.version: '4.0'` (`src/types/syncFileV4.ts:56`). One consumer compares the detector's result against the literal (`connectStorage.ts:250`); the three file-picker readers compare it too (`syncService.ts:2067`, `:2119`, `:2159`). The re-save path spreads the incoming envelope (`reEncryptEnvelope`, `fileSync.ts:219`; `preserveLocalKeyDicts`, `envelopeMerge.ts:73-74`; `withoutPayload`, `envelopeMerge.ts:41`), so **a v5 envelope read from a file is written back as v5 with no code change on the ordinary save, poll, rename, key-add and cache paths** — with one critical exception (Trap 1). The minimal correct change is therefore: (1) widen the type to a `BeanpodVersion = '4.0' | '5.0'` union; (2) make `parseBeanpodV4`/`detectFileVersion` accept both and throw a typed, non-latching, non-corruption error for anything else; (3) fix the two `!== '4.0'` comparisons and three `=== '4.0'` comparisons to use "is a known version"; (4) stamp `'5.0'` on the write path **derived from the document's lineage**, not carried on the envelope by spread — because the `kept-local` terminus adopts the remote's envelope (including its version) and then publishes the local compacted document under it (Trap 1). Nothing in the worker, the lineage guard, the join flow, the recovery kit, passkey unlock, trusted auto-open, or the IndexedDB envelope cache reads `envelope.version` at all, so none of those need a change once the parser accepts v5. Renaming `BeanpodFileV4` is scope creep and should not happen.

## Traps (most severe first)

### Trap 1 — `kept-local` republishes the compacted document under the REMOTE's version (silent downgrade, defeats the whole design)

VERIFIED. `preserveLocalKeyDicts` spreads `...incoming` (`src/services/sync/envelopeMerge.ts:73-74`); it merges only the key dicts and takes every other field, including `version`, from the fetched envelope. On the `kept-local` terminus — the worker decided OUR document is the newer lineage and left it installed — the code deliberately adopts the remote's envelope anyway to pick up its key dicts, then arms a publish of the LOCAL document:

- `src/services/sync/syncService.ts:1623-1633` — `adoptRemoteEnvelopeKeys()` is `setEnvelope(preserveLocalKeyDicts(remoteEnvelope, currentEnvelope))`, called at `:1633` in the `kept-local` branch of `fetchAndMergeRemote`; `doSave` then writes `reEncryptEnvelope(currentEnvelope, payload)` at `:1802`, where `payload` is the local (compacted) document.
- `src/stores/syncStore.ts:1015-1039` — `keepLocalDocumentAndAdoptEnvelopeKeys` does `replaceEnvelope(remoteEnvelope)` (`:1027`), whose body is `withoutPayload(preserveLocalKeyDicts(incoming, envelope.value))` (`:226`), then `triggerDebouncedSave()` (`:1038`). Called from `loadFromFile` (`:1293`), `hydrateFromEnvelope` (`:1081`), and `replaceDocWithCacheRecovery` (`:967`, surfaced as `KEPT_LOCAL` at `:1319`).

So whenever the remote file is on an OLDER lineage than this device's document, this device adopts `version: '4.0'` from that file and republishes its compacted document as `4.0`. That state is not exotic; it is the documented self-repair for a failed compaction publish (`src/composables/usePodCompaction.ts:389-394`: "the next open reads `ours-newer`, the policy says `publish-local`, and it republishes itself"), and it is also what every current-build peer does after a family restores the 4.0 safety copy (Q7), and what happens if a pre-guard device ever gets an old-lineage write through. In every one of those cases the republished pod is compacted and labelled `4.0`, and the deployed build will parse and merge it. `podLineage.ts:176` confirms the policy: `'ours-newer': { clean: 'publish-local', dirty: 'publish-local', ... }`.

**Consequence:** if `'5.0'` is implemented as "stamp the envelope once at compaction and let the spread carry it", the protection lasts exactly until the first `kept-local`. The version must describe the PAYLOAD, and the payload's lineage lives in the document (ADR-036, `docs/adr/036-pod-lineage-lives-in-the-document.md`). The sole writer of `podLineage` is `compactDoc` (`src/services/automerge/worker/applyAndProject.ts:1226`, the only `podLineage:` assignment in `worker/`, `sync/`, `stores/` — VERIFIED by grep). So "document has a `podLineage`" ⇔ "document is compacted" ⇔ "must be written as 5.0". Fix options, in order of preference:

1. **Document-derived (recommended).** `exportEncryptedPayload` (`applyAndProject.ts:1039-1044`) already returns `{ payload, heads }`; return `lineage: docLineage(doc)` (or a boolean `compacted`) alongside. `reEncryptEnvelope` (`fileSync.ts:214-221`) takes a third argument and stamps `version` from it. Two call sites: `doSave` (`syncService.ts:1801-1802`) and `buildExportEnvelope` (`syncStore.ts:2831-2834`). This also answers Q4 with zero changes in `usePodCompaction` and honours its "NO ENVELOPE STAMP" design note (`usePodCompaction.ts:381-386`). Rollback (Q7) is then correct for free: after a `user-file` adopt the document is on the old lineage and the next save derives `4.0`.
2. **Envelope-carried with a local-wins rule for `version` in `preserveLocalKeyDicts`.** Smaller diff, but wrong on the adopt/rebase branches (a device rebasing onto a compacted remote would keep its own `4.0`), so it needs `version: max(...)`, which is then wrong for the rollback case. Not recommended.

### Trap 2 — `connectStorage`'s stub probe classes a v5 pod as an empty placeholder and makes it the CREATE target (destructive)

VERIFIED. `isStubBeanpod` returns `detectFileVersion(text) !== '4.0'` (`src/services/sync/connectStorage.ts:245-251`; "Anything that isn't a real V4 envelope is treated as a non-pod stub"). `resolveExistingBeanpod` (`:224-242`) returns `{ kind: 'adopt-stub' }` for it, and `useDriveCollisionRecovery.resolveDriveCollision` (`src/composables/useDriveCollisionRecovery.ts:59-64`) calls `adoptDriveStub` (`connectStorage.ts:259-269`), which installs a provider on that fileId "so the in-flight create writes the real pod INTO it" (`:261-262`). The trigger is a same-name collision on the owner's own account during create (`connectStorage.ts:172-181`, default name `my-family.beanpod` at `:159`). If `detectFileVersion` is widened but this comparison is missed — or if `detectFileVersion` keeps returning `'4.0' | null` and returns `null` for `5.0` — a compacted family's real pod is overwritten with a fresh empty family. This must become "is a KNOWN version" (or `detectFileVersion(text) === null`), and the test at `src/services/sync/__tests__/connectStorage.test.ts:211-212` must gain a `5.0` case that expects `adopt-existing`.

### Trap 3 — the three file-picker readers reject a v5 pod with a misleading message and hand back `rawText`

VERIFIED. `openAndLoadFile` (`syncService.ts:2065-2076`), `openAndLoadFileFallback` (`:2117-2125`) and `loadDroppedFile` (`:2157-2168`) all do `const version = detectFileVersion(text); if (version === '4.0') { parseBeanpodV4 ... }` else `lastError: 'Unsupported file version: ${version ?? Because `detectFileVersion` returns `null` for anything but `'4.0'` (`fileSync.ts:100-101`), a `5.0` (or `6.0`) file reads as "unknown". `rawText` is declared "for V3 fallback detection" (`syncService.ts:71`) but has NO consumer in `src/` (VERIFIED by grep: the only hits are the three `return` sites and the type) — so it is DEAD and cannot feed a legacy migrator. ### Trap 4 — a version HIGHER than understood currently surfaces as raw English, or as "your data may be damaged" on the boot overlay

- `syncStore.loadFromGoogleDrive` `:4435` — `catch` at `:4458-4468` sets `error.value = e.message` and returns `reason: 'error'`; `useJoinFlow` records `FILE_READ_FAILED` (`src/composables/useJoinFlow.ts:530`, `:591`), `LoadPodView.vue:1003-1010` and `OpenFromDrivePage.vue:83` show `syncStore.error` raw.

The important negative result: **no path classifies a parse failure as corruption-that-wipes-the-cache or as wrong-key.** The cache self-heal is in the worker's `initAndLoadCache` (`applyAndProject.ts:531-560`, `clearCache` at `:557`) and fires on a `CorruptPayloadError` raised while loading the CACHED document; the cached envelope is never run through `parseBeanpodV4` (`cache.ts:432-440` is a bare `JSON.parse` cast), so a version string can never reach that branch. `keyMayBeWrong` is `step === 'decrypt'` only (`types/sync.ts:290-292`).

## Q4 — The compaction write

## Q6 — The "newer than I understand" path

Where it should live: **in `parseBeanpodV4` itself**, as a typed throw, because it is the single validator that every reader in Q5 funnels through (rows 1, 2, 7, 15, 17, 18, 19 directly; rows 3-5 and 13 after their `detectFileVersion` comparison is fixed to "known set"). Putting the classification in the callers means six catch sites (Trap 4) that already disagree.

Which existing pattern:

- `PayloadLoadError` / `RemoteBlocker` (`src/types/sync.ts:207-323`) is the right family. The interface was designed so "a new blocker answers the two members and is picked up by every site at once" (`:240-246`), `isRemoteBlocker` is duck-typed (`:247-251`), `PayloadLoadStep` already includes `'parse'` defined precisely as "the JSON or the version was rejected ... a pod written by a NEWER app version" (`:172-180`), `latches` is already `false` for `parse` (`:320-322`), `keyMayBeWrong` is already `false` for `parse` (`:290-292`), `deviceCannotOpen` is `false` (`:310-312`), `noteRemoteUnreadable` already reports `parse` at `warning` (`syncService.ts:127-143`), and `reportPayloadFailure` would report it at `critical` only via `surfacePayloadFatal` on the boot overlay (`payloadFailureSurface.ts:59-64` do not exclude `parse`) — acceptable, or add `err.step === 'parse'` to the early-return there.
