**Conclusion for Q1: (a) is the only candidate that fails before any destructive dispatch on the deployed build, and it is the only one whose failure mode the deployed build explicitly anticipates. Nothing better exists, because there is no earlier point than the version literal to fail at.** The one thing (a) cannot do — protect a stale device that opens from its own cache and later SAVES — is not fixable by any envelope-side mechanism, since the stale device never reads the envelope before writing (P2/P3 traces this).

One design decision the plan must make explicit (it is not in the README): **is the version a property of the DOCUMENT (stamped → `'5.0'`) or of the WRITER (a new build writes `'5.0'` always)?** OPINION: it must be the document. The writer rule would break every stale device in every family at deploy time, before any compaction, including the safety copy and manual exports of never-compacted pods; it turns "families that compact accept a stale-device cost" into "every family pays it on day one". The document rule confines the cost to the operation that needs it, keeps the safety copy at `'4.0'` (a full-history, unstamped document that a stale device can legitimately read — with one caveat in §6.5), and makes "two compactions → still 5.0" true by construction (§6.1).

## Findings, most severe first

### F1 — CRITICAL (current build; must be in the plan). On `kept-local` the current build adopts the REMOTE envelope's `version` and republishes the compacted document under it

VERIFIED. `preserveLocalKeyDicts` is `{ ...incoming, <key dicts merged> }` (`src/services/sync/envelopeMerge.ts:68-100`), so every field that is not a key dict — including `version` — comes from the FETCHED envelope. Both `kept-local` termini adopt it deliberately (to pick up remote-only keys) and then arm a publish of the LOCAL document:

- `src/services/sync/syncService.ts:1617-1655` — `adoptRemoteEnvelopeKeys()` = `setEnvelope(preserveLocalKeyDicts(remoteEnvelope, currentEnvelope))` at `:1624-1632`, called in the `kept-local` branch at `:1633`, then `triggerDebouncedSave()` at `:1654`.
- `src/stores/syncStore.ts:1015-1039` — `keepLocalDocumentAndAdoptEnvelopeKeys` does `replaceEnvelope(remoteEnvelope)` (`:1027`; body `withoutPayload(preserveLocalKeyDicts(incoming, envelope.value))` at `:222-229`) then `triggerDebouncedSave()` (`:1038`).
- `reEncryptEnvelope` is `{ ...envelope, encryptedPayload, writerVersion }` (`src/services/sync/fileSync.ts:214-221`): the published file carries whatever `version` the in-memory envelope holds.

Sequence: a stale device edits and saves → the pod is a `4.0` file on the old lineage (P2). A current device polls → worker says `ours-newer` → `publish-local` → `kept-local` (`applyAndProject.ts:847-857`) → main adopts the `4.0` envelope → republishes the COMPACTED document as **`version: '4.0'`** → the stale device parses it, CRDT-merges across lineages, destroys the compaction, and carries the lineage id forward so every guarded device reads the corruption as `same`. **The protection lasts exactly one round trip.** P5 (Trap 1) reached the same conclusion independently.

The fix is structural and it is the same principle as ADR-036: the version is a fact about the PAYLOAD, and the payload's lineage lives in the document. `exportEncryptedPayload` must return the document's lineage (or a `compacted` boolean) beside `payload`/`heads`, and `reEncryptEnvelope` must take it and stamp `version` from it, at both writers (`doSave`, `buildExportEnvelope`). A `version` field carried on the envelope by spread is the envelope-lineage bug again, one field over. (OPINION: a "local-wins for `version`" rule inside `preserveLocalKeyDicts` is the wrong fix — it is right on `kept-local` and wrong on every adopt/rebase branch.)

### F2 — HIGH (deployed build; cannot be fixed, must be named and mitigated). The create-flow stub probe classifies a v5 pod as an EMPTY PLACEHOLDER and writes a new family into it

VERIFIED at `c3a6be98`. `isStubBeanpod` returns `detectFileVersion(text) !== '4.0'` — _"Anything that isn't a real V4 envelope is treated as a non-pod stub"_ (`src/services/sync/connectStorage.ts:246-251`). `resolveExistingBeanpod` (`:224-242`) returns `adopt-stub` for it; `useDriveCollisionRecovery.resolveDriveCollision` (`:53-64`) calls `adoptDriveStub` **with no confirm** (the confirm at `:71-78` is only for `adopt-existing`); `adoptDriveStub` installs a provider on that fileId _"so the in-flight create writes the real pod INTO it"_ (`:259-269`); `CreatePodView.vue:292-295` then treats `adopted-stub` as success and proceeds to `createNewFile`, whose `provider.write(envelopeJson)` (`syncStore.ts:1866`) overwrites the family's compacted pod with a brand-new empty family. `ResumePodSetup.vue:735` has the same arm.

Trigger: the OWNER's Google account (`ownedByCurrentAccount`, `:228`), on a stale build, going through "create a new family" with a family name that collides in the app folder (`googleDriveProvider.ts:525-540` — an exact-name match in `getOrCreateAppFolder`). The default base name is **`my-family`** (`connectStorage.ts:159`), so a family whose pod carries the default name is exposed to a confused owner who reacts to "sync stopped" on an old tablet by "starting over". Today, with a `4.0` pod, that same sequence yields `adopt-existing` → a confirm → the pod is OPENED, never overwritten. **The version bump converts a safe path into a destructive one on the deployed build**, in this one narrow flow.

Blast radius when it fires: the pod's fileId now holds a `4.0` envelope with a NEW `familyId`. Current-build peers do not merge it: `loadAndParseV4` (`syncService.ts:1494-1501`, deployed; INFERRED unchanged) and `loadFromFile` refuse on familyId mismatch with _"Sync file belongs to a different family"_ and `isConfigured: false`. So the fleet STOPS, loudly; it is not corrupted. Recovery is the safety copy (Settings → Load another family data file) or a Drive revision (Drive keeps prior revisions of a file updated in place — INFERRED, Drive behaviour, not code).

Mitigation available to the plan: (i) the current build's `isStubBeanpod` must treat any KNOWN version as populated (P5 Trap 2 — a fix that only protects devices that have updated); (ii) the confirm copy and the Settings notice should say plainly that a device on an old version must be UPDATED, not set up again; (iii) the compaction gate could refuse when the pod's file name is the default `my-family.beanpod` AND a recently-active member's `appVersion` predates the guard — OPINION, cheap and targeted, but probably not worth a refusal code; a sentence in the notice is enough.

### F3 — HIGH (current build; a design gap the plan must close). Restoring the `4.0` safety copy does not survive the fleet

VERIFIED gap, INFERRED fix. Device A restores the pre-compaction file through Settings (`SettingsPage.vue:540-548` → `decryptPendingFile(password, {userChoseThisFile:true})`), the worker adopts under `user-file` (`ours-newer × user-file = adopt`, `podLineage.ts:176`), and A's document is now on the old lineage (`podLineage: null`). Every other current-build peer B still holds `{id, seq:1}`. On B's next poll: `compareLineage(remote=null, local={id,1})` → `'ours-newer'` (`podLineage.ts:148`) → `publish-local` (`:176`) → worker returns `kept-local` (`applyAndProject.ts:847-857`) → main arms a publish (`syncService.ts:1654` / `syncStore.ts:1038`). B republishes the COMPACTED pod over the restore within one poll interval; A then reads `adopt-remote` and takes the compacted pod back. **The rollback route the confirm dialog promises (`compaction.safetyCopyNote`) is undone by the fleet automatically.** The plan's R2 (`2026-09-06-pod-compaction-tier3.md:367-467`) covers writing, naming, verifying and hiding the copy; it says nothing about how peers respond to a restore. ADR-036 §"user-file" addresses only the RESTORING device.

This is not created by the version bump, but the version bump makes it worse in a specific way: with F1 fixed, B republishes as `5.0`; with F1 unfixed, B republishes as `4.0` and the stale devices rejoin the merge.

Fix: **a restore is a lineage event.** The `user-file` adopt of a document whose lineage is not the highest this device has seen must stamp the adopted document with a NEW id and `seq = (highest seen) + 1` — the same stamp `compactDoc` writes (`applyAndProject.ts:1226`) without the `toJS/from` rebuild. Peers then read `adopt-remote` and adopt (clean) or rebase (dirty), which is exactly the propagation the guard was built for. The restored file is written as `5.0` (it is stamped), so stale devices stay refused — the same posture as after the compaction. When the restoring device has no prior document (fresh device), it does not know the fleet's `seq`; it must pull the live pod first to learn it, or accept that peers will read `conflict` and block (a banner, not a loss). OPINION: a `stampLineage` worker op beside `compactDoc`, called from the `user-file` adopt path, is the smallest correct shape. A one-line test: "restore on A, poll on B, assert B adopts rather than republishes".

That query, not a code change, is the fleet-drain gauge for §7.

### F5 — MEDIUM (deployed; partially mitigated). The `4.0` safety copy is a file a stale build CAN open, sitting beside the pod with a similar name

VERIFIED: the deployed picker lists every `.beanpod` Drive-wide (`syncStore.ts:3876-3891` `searchBeanpodFilesGlobal`) with no safety-copy filter — `isSafetyCopyName` exists only in the current build (`driveService.ts:752`, `syncStore.ts:4696`). A stale-device user who reacts to "sync stopped" by picking "<family> (before compacting).beanpod" opens it successfully, is bound to its fileId, and every later save rewrites the SAFETY COPY. Two consequences: the device is forked onto the backup (detected: `CANONICAL_MISMATCH` exists at `c3a6be98`, `syncStore.ts:3098`, rendered by `PodAccessBanner.vue`), and the backup is no longer the pre-compaction bytes (its label becomes slightly false, though it remains a valid old-lineage rollback point). The same trap exists for a stale-build JOINER whose direct load fails (#9) and who is dropped into the picker: the join can complete against the safety copy if the invite predates the compaction (a later invite's token is absent from the copy → `INVITE_TOKEN_INVALID`).

OPINION on the remedy: write the safety copy as **`5.0` as well** (it is written in the same operation as the compacted pod; "a family that has compacted is a 5.0 family from that moment"). Stale builds then cannot open it, current builds can, the rollback route is unchanged, and the picker on old builds shows a file that refuses cleanly. This costs nothing the family had: a stale device could never rescue itself from the copy anyway (its home is the pod).

### F6 — LOW (deployed). No read storm

INFERRED from VERIFIED lines: `load()` learns the remote marker BEFORE the download (`syncService.ts:1428-1431`), so after one failed parse the next poll's `remoteChanged()` (`:1183`, `syncStore.ts:2797`) answers "unchanged" until the pod actually changes. A stale device downloads the (small, compacted) pod once per remote write, not every 10 seconds.

### F7 — LOW. The `.beanchanges` sweep cannot touch the safety copy

VERIFIED in both builds: `isChunkName` requires the `changes/` prefix AND the `.beanchanges` suffix (`chunkNames.ts:15-19`, identical at `c3a6be98`). `"<name> (before compacting).beanpod"` matches neither.

### F8 — LOW. Two owners compacting concurrently: `conflict` is reachable and handled

VERIFIED policy: same `seq`, different `id` → `'conflict'` (`podLineage.ts:151-153`) → `block` for `clean`/`dirty`, `adopt` for `user-file` (`:177`). Drive writes carry no precondition (`googleDriveProvider.ts` has no `If-Match`/412 handling — VERIFIED by grep), so both publish and the last write wins on Drive; the device whose write landed FIRST reads the other's on its next poll and blocks with the banner, whose action (`useRemoteFileOverLocalDocument`, `syncStore.ts:3600-3640`) adopts the other compaction. The device that wrote last never sees a conflict (it learned its own revision). The two safety copies collide by name (`safetyCopyName` is deterministic, `constants/compaction.ts:33-38`) but hold the same bytes — both passed `isFullySynced` against the same remote before compacting — so the overwrite loses nothing. Both files are `5.0`. Acceptable.

### F9 — LOW. Two compactions in a row do NOT need `6.0`

The version answers "can this reader merge safely?"; the lineage `seq` answers "which history is newer?". Every reader that understands `5.0` honours the guard, and the guard already orders generations by `seq` (`podLineage.ts:149-150`); `compactDoc` increments it (`applyAndProject.ts:1226`). A `6.0` would be needed only if a `5.0`-capable build had a merge bug that a later build fixes — which is what `minReaderVersion` (§1(b)) is for.

## 6. What we had not thought of (and what we had, checked)

Cross-referenced to the findings; new items first.

1. **The version is adopted from the remote envelope on `kept-local` (F1).** The single most dangerous item in this audit: a naive "stamp `5.0` at compaction" lasts one round trip.
2. **The create-flow stub probe (F2).** The only place on the deployed build where a `5.0` file is treated WORSE than garbage: it is overwritten. Unfixable; document, and fix the current build's copy of the same probe.
3. **The rollback does not stick (F3).** A restore must be a lineage event, or the fleet reverts it. Not caused by the bump, but the bump is the moment to fix it, because it is the moment the safety copy becomes the family's only way back.
4. **Which files are `5.0`?** Must be decided explicitly: the compacted pod, and (OPINION) the safety copy and the manual export written in the same operation — "a family that has compacted is a 5.0 family from that moment". Never-compacted families stay `4.0`. The rule must be derived from the document at write time (F1), not from which code path wrote the file.
5. **`minReaderVersion` now, for next time (§1(b)).** Useless against the deployed build, essential so the NEXT bump is a graceful "update beanies to open this file" instead of a raw string.
6. **Two compactions in a row → still `5.0` (F9).** `seq` orders generations; `version` gates readers.
7. **A joiner invited AFTER compaction, on a deployed-build device.** Direct load by fileId fails with the raw version string classified as `FILE_READ_FAILED` (`useJoinFlow.ts:451-458`), severity critical (pages Slack), copy that blames the Google account (`join.error.fileRead`), recoveries `signInDifferentAccount` / `retry` / `tryAnotherDevice`. Safe; the "Continue on another device" button is the correct recovery. ADR-024's registry shows something sensible, not a raw stack, but the sentence is wrong for this cause. The picker fallback can hand the joiner the `4.0` safety copy if the invite predates the compaction (F5) — one more reason to write the copy as `5.0`. NOTE: an invite link opens `app.beanies.family/join`, i.e. the WEB build, which updates itself; a stale joiner is a native deep-link case.
8. **Recovery kit on an old build against a `5.0` pod.** The kit path needs a parsed envelope (`LoadPodView.vue:443-444` reads `pendingEncryptedFile?.envelope`; the QR deep link `#beanies-kit=` at `LoginPage.vue:316-319` only prefills the code) — so the Drive pick fails first with the raw string (#6). Dead end with a message; no key or cache is touched. On the new build the kit flow is unaffected (P5: nothing in kit/passkey reads `version`).
9. **The Android open-testing / TestFlight cohorts (F10).** Identical parse behaviour on every V4-era build since March; they differ only in how they update (P4).
10. **Restoring the `4.0` safety copy while others are on `5.0` (F3, F5).** Today: the restoring device adopts, every peer republishes the compaction over it within a poll, and the restore is gone; with F1 unfixed the republish is `4.0` and stale devices rejoin the merge. Can the code tell a legitimate rollback from an accidental revert? YES — `user-file` on the restoring device is exactly that signal (ADR-036: "produced ONLY where a human was shown what it discards"). The peers cannot tell, and must not have to: the restoring device turns its decision into a new lineage generation, and the peers' existing policy does the rest.
11. **Google Drive's own versioning and conflict copies.** INFERRED (Drive behaviour): every in-place update creates a revision, so the pre-compaction bytes survive as a Drive revision for a period — a support-level third rollback. Conflict copies ("(1)") arise only for LOCAL-file families under a desktop sync client (`notifyIfConflictFile`, `syncService.ts:208-214` deployed); a conflict copy of a `5.0` pod is `5.0` and refused by stale builds identically, and the current build treats it as a different file (`CANONICAL_MISMATCH`). Nothing new.
12. **The `.beanchanges` sweep (F7).** Cannot match the safety copy, either build.
13. **Two owners compacting concurrently (F8).** `conflict` reachable, handled by the banner on the device that wrote first; safety copies collide by name but are identical bytes.
14. **No read storm (F6).**
15. **`compaction.doneButBehind` is now wrong** and must be rewritten (§3), as is `compaction.confirmMessage` (§4).
16. **The stale device's messages are English-only and unfixable** ("Unsupported file version: unknown" is a raw string on the deployed build). Accept.

## Verdict

**Yes: bumping the envelope `version` to `'5.0'` is the right mechanism, and the overall approach — structural refusal on the deployed build, fleet self-heal on the current one, the soak gate demoted to an honest notice — is the best available.** What convinced me: the deployed reader checks the version literal before it reads any other field, before decrypt, before the worker, and before adopting the remote marker or key dicts (`fileSync.ts:73-74`, `syncService.ts:1192-1211`); every user-facing read site anticipates exactly this failure and returns a result rather than throwing; and the two destructive catches that exist on the deployed build (credential delete in `tryAutoDecrypt`, cache wipe in `initAndLoadCache`) are both downstream of a successful parse and cannot be reached. No alternative fails earlier, and every alternative that fails later (key change, payload framing, a new Drive file, a new familyId) fails INTO the code paths that treat the file as damaged or forked. **The approach is sound only with two conditions the current plan does not yet contain:** (F1) the version must be derived from the DOCUMENT at write time — today the `kept-local` terminus adopts the remote envelope's `version` and would republish the compacted pod as `4.0` on the very first stale-device overwrite, which defeats the design in one round trip (P5 concurs); and (F3) a restore of the safety copy must be published as a new lineage generation, or every current-build peer reverts the family's rollback within a poll. One deployed-build hazard is unfixable and must be named in the plan: the create-flow stub probe treats a `5.0` pod as an empty placeholder and overwrites it if the owner "starts over" on a stale device with a colliding name (F2) — the safety copy and Drive revisions are the recovery, and the current build's copy of that probe must be fixed so the hole closes as the fleet drains.
