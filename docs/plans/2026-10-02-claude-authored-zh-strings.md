# Plan: Claude-authored Chinese UI strings; retire the MyMemory pipeline end to end

> Date: 2026-10-02
> Related issues: Notion tracker #38 (no GitHub issue)
> Plan file: `docs/plans/2026-10-02-claude-authored-zh-strings.md`

> **No GitHub issue created.** This plan was approved for direct implementation.

## User Story

As a Chinese-speaking member of a beanies.family pod, I want every screen in natural, correct Simplified Chinese, so I can trust and use the app without hitting spammy, machine-garbled or half-English text.

## Context

Chinese UI text today comes from a pipeline that nobody chose on quality grounds:

- `scripts/updateTranslations.mjs` (536 lines) text-parses `uiStrings.ts`, hashes every English value, and asks **MyMemory** (a scraped translation-memory lookup, not a translator) for anything whose hash changed. It writes `public/translations/zh.json` (5,764 keys, 880 KB, each entry carrying `translation` + `hash` + `lastUpdated`).
- `.github/workflows/translation-sync.yml` runs that script nightly and **commits straight to `main`** as `chore(i18n): auto-update translations`. In the two weeks before this plan the bot pushed Traditional characters into the bundle twice (`c5e1891d`, `477c0ae5`). In June it shipped a gambling-spam link and a dictionary-definition dump (tracker #38's origin).
- At runtime `translationStore.loadTranslations('zh')` runs a five-phase load: fetch `zh.json`, drop any entry whose hash no longer matches the current English, backfill from a dedicated IndexedDB database (`beanies-translations`), then **call MyMemory live from the user's browser** for whatever is still missing (200 ms per key), then persist. That runtime call sends UI strings plus the user's IP to a third party and is the path that silently papers over a missing translation.
- `suspiciousTranslationReason()` exists only to catch MyMemory garbage. `features.translationApiUpgrade` / `VITE_MYMEMORY_EMAIL` exist only to raise MyMemory's quota.

The original #38 scope was to swap MyMemory for Qwen via Tinfoil inside the same pipeline. On 2026-10-02 greg asked why the pipeline should exist at all: Claude writes every string in `uiStrings.ts` already, knows the feature and the surrounding copy, and ends up hand-fixing the machine output anyway. The `beanie` value is the precedent: a hand-authored parallel "language" with no pipeline, enforced only by a unit test, and it has never been a problem.

Current state of the Chinese, from a scan of `zh.json`: 77 entries contain no Chinese at all (some legitimately brand terms, many not), 4 contain Traditional characters, brand terms are rendered inconsistently (`Nook` is "家庭控制面板" in `nav.nook` but "Nook" in `mobile.nook`; "Pod" is sometimes kept, sometimes "家庭"), and a random sample reads as stiff machine output ("添加到重复性" for "Add to recurring").

## Requirements

1. **Chinese is authored, not generated.** Every UI string has a Simplified Chinese value written by Claude in the same change that creates or edits the English, with the same care as the `beanie` value.
2. **Completeness is enforced at compile time.** A missing or extra Chinese key fails `npm run type-check` (and therefore CI), not a nightly job.
3. **Quality is enforced by unit test.** A Chinese value that drops a `{placeholder}` the English has, adds one it does not, breaks a `.one`/`.other` pair, contains Traditional-only characters, contains HTML or a URL the English does not, or is English passthrough outside the brand allowlist fails `uiStrings.test.ts`.
4. **No machine translation anywhere.** The script, the workflow, the runtime API fallback, the IndexedDB translation cache, the hash machinery, the quota feature flag and env var, and every doc that describes them are removed. The client makes **no network call** for translations beyond loading its own code-split chunk.
5. **Runtime behaviour is preserved or better.** Switching to Chinese stays non-blocking and cancellable (the 2026-04-30 language-switcher-freeze contract), the beanie overlay stays English-only, `t()` in Chinese resolves zh then English, the Chinese text stays out of the main bundle, and the PWA still works offline in Chinese.
6. **One-time sweep.** Every existing Chinese value is rewritten fresh by Claude (Opus) with app context and the brand glossary, Simplified only, then a separate review pass checks a sample for correctness and readability to a native speaker. The sweep changes Chinese values only.
7. **The authoring rule is written down** where the next session will see it: `CLAUDE.md`, the beanies-theme skill, `docs/TRANSLATION.md`, and a short ADR recording the decision.
8. **Help Center is truthful.** The "Language & Currency" article stops saying the app uses an automatic translation service.

## Important Notes & Caveats

- **Design decision: a sibling file, not inline.** The Notion row and the morning discussion assumed `zh` inline on each `STRING_DEFS` entry plus a build-time extract to `zh.json`. Drafting against the code showed a simpler shape: a sibling module `src/services/translation/zh.ts` exporting `ZH_STRINGS: Record<UIStringKey, string>`. TypeScript's `Record` plus object-literal excess-property checking makes a missing key **and** a stale key a compile error with no test and no generator; a dynamic `import('./zh')` in the store gives a lazily loaded, service-worker-precached chunk with no JSON file, no fetch, no hash, no extract script and no "is the generated file current" question. The cost is that a string edit touches two files instead of one; the compile error names the exact key, so it cannot be forgotten. This supersedes the row's "inline + extract" wording and is called out for greg at approval.
- **Brand terms stay English** per the approved glossary: `beanies.family`, `The Pod`, `The Treehouse`, `Little Bean`, `Parent Bean`, `Meet the Beans`, `Nook`, `The Beanie Lab`, `beanies AI`, `Discord Beanies`, `.beanpod`, product names (Google Drive, Dropbox, iCloud, PDF). "bean(s)" as a noun for the AI allowance ("magic beans", "one bean per page") is translated as 豆子 / 魔法豆 consistently; the sweep prompt carries the full glossary. A pure-English navigation label inside a Chinese UI is a deliberate brand choice greg can reverse later by editing the glossary and re-running the sweep on the affected keys.
- **Staleness is undetectable by design.** When English changes and Chinese does not, nothing fails. This is exactly the situation `beanie` is in today. The authoring rule ("en, beanie and zh in the same edit") is the control, same as for `beanie`.
- **Do not change `en` or `beanie` values anywhere in this work.** The sweep commit diffs `zh.ts` only. Any English copy problem found during the sweep is recorded in the report, not fixed in passing.
- **The runtime fallback removal changes one behaviour**: a key missing at runtime used to be filled by MyMemory a few hundred milliseconds later. After this change that case cannot occur (compile-time completeness), and if the chunk itself fails to load the app stays in English with the existing toast.
- **Older app builds on the update floor** load `public/translations/zh.json` by path. Deleting the file from the deployed site means an old build that has not yet precached it falls back to English (it then calls MyMemory, as it always could). Builds that already precached it keep working. This is acceptable: the floor forces an update on next open anyway. Record it, do not engineer around it.
- **The dedicated IndexedDB database `beanies-translations`** is a separate idb database, not a store in the main one. Removing the repository leaves orphaned databases on existing devices. Delete it once on the next load with `deleteDB('beanies-translations')` (the pattern already used for legacy databases in `database.ts`), wrapped so a failure is logged, never thrown.
- **`scripts/__tests__/updateTranslations.test.mjs`** is picked up by vitest's `scripts/**` include; it is deleted with the script.
- **Native app bundles** under `ios/App/App/public` and `android/app/src/main/assets/public` contain built assets that still mention MyMemory; they are build outputs regenerated on the next native build and are not edited by hand.
- **Chunk budget at boot, accepted.** The store's chunk recovery and `App.vue`'s init catch can both fire for the same stale precache at boot (`loadTranslations` runs before the auth/data dynamic imports), so one deploy gap may increment the counter twice and exhaust the budget of 3 in two reload cycles instead of three. Bounded and self-correcting (a healthy boot calls `resetChunkAttempts`). Likewise `chunkReloadInProgress` is `App.vue`-local, so a store-triggered `hardReload()` lets the boot spinner dismiss for the instant before `location.replace` lands. Both recorded, neither engineered around.
- **Prettier** will format `zh.ts`; write it in the same one-key-per-line style as `uiStrings.ts` so formatting is stable and diffs are per key.

## Approach

### 1. The Chinese module

Create `src/services/translation/zh.ts`:

```ts
import type { UIStringKey } from './uiStrings';

/**
 * Simplified Chinese UI strings, authored by hand (Claude) alongside the
 * English in uiStrings.ts. Keyed by UIStringKey so TypeScript fails the
 * build on a missing or stale key. Loaded lazily by translationStore.
 * Style and glossary: docs/TRANSLATION.md.
 */
export const ZH_STRINGS: Record<UIStringKey, string> = {
  'app.name': 'beanies.family',
  'app.tagline': '每一颗豆子都很重要',
  // ...
};
```

- `Record<UIStringKey, string>` fails type-check when a key is missing; the object-literal excess-property check fails it when a key no longer exists in `STRING_DEFS`. No generator, no hash, no test needed for completeness.
- Keys appear in `uiStrings.ts` order with the top-level `// Section` headers only; explanatory prose comments stay in `uiStrings.ts` (mirroring them would create a second copy that drifts). Side-by-side review works by key order.
- The file is imported **only** via `import('./zh')` in the store, so Vite emits it as its own chunk and the main bundle does not grow.

### 2. The store

Rewrite `src/stores/translationStore.ts` `loadTranslations` to a single phase while keeping the cancellation contract:

```ts
type Strings = Readonly<Record<UIStringKey, string>>;
const LOADERS: Record<Exclude<LanguageCode, 'en'>, () => Promise<Strings>> = {
  zh: async () => {
    // Destructure deliberately: a rotated chunk that resolves to null (the iOS
    // shape recorded in hardReload.ts) then throws "Cannot destructure ... null",
    // which isChunkLoadError matches; a property read would throw "Cannot read
    // properties of null", which it does not, and self-healing would be lost.
    const { ZH_STRINGS } = await import('@/services/translation/zh');
    return ZH_STRINGS;
  },
};

// shallowRef: a 5,764-key record must not be wrapped in a deep reactive proxy
// on every switch; null means "English, no table loaded".
const translations = shallowRef<Strings | null>(null);

async function loadTranslations(language: LanguageCode): Promise<void> {
  if (language === 'en') {
    /* unchanged: bump token, translations.value = null, set en */ return;
  }
  const myToken = ++activeLoadToken;
  const isStale = () => myToken !== activeLoadToken;
  try {
    isLoading.value = true;
    translations.value = await LOADERS[language](); // held directly, no Map rebuild
    if (isStale()) return;
    currentLanguage.value = language;
  } catch (err) {
    if (isStale()) return;
    if (tryRecoverChunkLoad(err)) return; // shared helper, see below
    handleCatastrophicLoadError(language, err); // reportError + toast, see Observability
    if (translations.value === null) currentLanguage.value = 'en';
  } finally {
    if (!isStale()) isLoading.value = false;
  }
}

function t(key: UIStringKey): string {
  if (currentLanguage.value === 'en') {
    /* unchanged beanie-overlay branch */
  }
  return translations.value?.[key] ?? UI_STRINGS[key]; // ?? not ||: the ZH suite forbids empty values
}
```

(The `await` placement above is illustrative; write it as two statements.)

- Remove: `tryTranslateOneKey`, the IndexedDB phases, `loadProgress` (rendered nowhere; only re-exported by `useTranslation.ts` and stubbed as `loadProgress: ref(1)` in five component tests, which may drop the dead key when touched), `translationFile`, `translationCount` (no consumer), `clearCache` (verified: every other `clearCache` hit is the Automerge worker cache), imports of `translationApi`, `translationFiles`, `translationCache`, `getAllKeys`, `getSourceText`, `getAllHashes`. Keep `error` only if the rewritten test reads it.
- Keep: `t()`, `setBeanieMode`, `setLanguageSync`, `activeLoadToken` staleness guard, `handleCatastrophicLoadError` with its `reportError({ surface: 'translation-load' })` and toast.
- Chunk-load recovery: the "attempts < 3 → increment → hardReload" dance already exists three times with two storage accessors (`src/router/index.ts` `onError` with a literal `3`, `src/main.ts`, `src/App.vue` with a local `MAX_ATTEMPTS = 3`). Do not add a fourth. Add to `src/utils/hardReload.ts` an exported `CHUNK_RELOAD_MAX_ATTEMPTS = 3` and `tryRecoverChunkLoad(err: unknown): boolean` (false unless `isChunkLoadError(err)` and attempts are under the max; otherwise `writeChunkAttempts(n + 1)`, `void hardReload()`, true). The store's catch is `if (tryRecoverChunkLoad(err)) return;`. In the same change replace `App.vue`'s local `MAX_ATTEMPTS`, the router's literal `3`, and `main.ts`'s `if (attempts >= 3)` in the `vite:preloadError` listener with the exported constant (three one-line edits; do not refactor their surrounding logic). When the budget is exhausted the failure falls through to `handleCatastrophicLoadError` with `error_code: 'chunk_load'`.
- `error` ref: removed outright. No consumer outside the store; the rewritten test asserts through the already-mocked `reportError`.
- `tr()` in `src/services/translation/tr.ts` (the pre-Pinia-safe entry point used by foundational modules) is unchanged and stays; the verify step confirms a pre-Pinia caller still gets its English fallback.
- `handleCatastrophicLoadError` changes its report context from `{ language }` to `{ error_code }`: `'language'` is not in `ALLOWED_CONTEXT_KEYS` (`src/utils/diagnosticContext.ts`) and is silently dropped by `redactContext` today; the language already travels in the message string. The rewritten store test stops asserting `context: { language: 'zh' }`.
- `t()` is unchanged. Adding a language later is one `LOADERS` entry, one `LanguageCode` member and one sibling module.

### 3. One-time cleanup of the orphaned IndexedDB database

`database.ts` has no "deleted on init" list; its private `deleteDB(name)` helper is called only from `deleteFamilyDatabase` on sign-out. So: export `deleteRetiredTranslationDatabase(): Promise<void>` from `database.ts`, reusing that private `deleteDB('beanies-translations')`. Call it fire-and-forget from `App.vue` **immediately after the public-page early return** (that boundary's comment says public pages skip IndexedDB entirely; the boot `loadTranslations` call sits before it, so "next to loadTranslations" would be the wrong side). Use the same `await import('@/services/indexeddb/database')` style `App.vue` already uses three times, not a new static import. Keep it minimal: guard `typeof indexedDB === 'undefined'`; no existence probe (`deleteDatabase` of a missing database is a cheap no-op, and probing via `indexedDB.databases()` would log forever on browsers that lack it); try/catch; on failure `console.warn` plus `logEvent({ level: 'info', surface: 'idb-legacy-cleanup', context: { action: 'failed', error_code } })`; **no event on success** (a per-boot "skipped"/"deleted" line on every device is noise with nothing to drain). Mark it `TEMPORARY: remove after 2026-12-01` so a future session can act on it without CloudWatch access. `deleteDB`'s resolve-on-blocked caveat is moot: nothing re-opens this database once the repository is gone.

### 5. Tests

`src/services/translation/uiStrings.test.ts` gains a `describe('ZH_STRINGS')`:

- every value is non-empty and not whitespace;
- the set of `{placeholder}` tokens in zh equals the set in en, per key;
- for every `*.one` key with a `*.other` sibling, both have zh;
- no value contains a character from `TRADITIONAL_ONLY` (the existing ~1,150-character detection-only set in `scripts/lib/traditionalChars.mjs`, already documented as false-positive-safe, moved to `src/services/translation/traditionalChars.ts`; do not curate a second list);
- placeholder check uses the `/\{[a-zA-Z0-9_]+\}/g` regex from the retired `zhBundleIntegrity` test (`fillTemplate` itself uses `replaceAll` per key, no regex);
- no value contains `<a`, `href`, `http` unless the en value does;
- English passthrough is value-based, not a per-key allowlist (a key list would grow forever): define one `ZH_BRAND_TERMS: readonly string[]` (the approved glossary: `beanies.family`, `The Pod`, `The Treehouse`, `Little Bean`, `Parent Bean`, `Meet the Beans`, `Nook`, `The Beanie Lab`, `beanies AI`, `Discord Beanies`, `.beanpod`, `Google Drive`, `Dropbox`, `iCloud`, `OneDrive`), brand and product names only. For a value with no CJK characters, strip every glossary term, `{placeholder}`, emoji, digits, uppercase tokens of 2 to 4 letters (`/\b[A-Z]{2,4}\b/`: currency codes plus the acronyms `eslint.config.js` already exempts such as OK, ID, AI, PWA, URL, PDF, PIN, QR), and punctuation; if any Latin letter remains, fail. Values that contain CJK are not examined (so "使用EpiPen" is fine). `ZH_BRAND_TERMS` in the test file is the single source; `docs/TRANSLATION.md` and the theme skill **reference** it rather than restating it (the lint rule's separate brand allowlist in `eslint.config.js` stays separate; cross-link, do not merge). This check is also the staleness floor: an English value pasted into `zh.ts` fails, so nobody needs to bring a hash scheme back for that;
- the "important-surface" discipline from the beanie test does not apply to zh (zh is a real translation, not an overlay).

`src/stores/__tests__/translationStore.test.ts` is rewritten for the one-phase load: cosmetic switch applies after the import resolves; stale load does not write; catastrophic failure (import rejects) toasts + `reportError` and falls back to English; stale catastrophic failures stay silent. Mock `@/services/translation/zh` with a tiny map. `src/composables/useTranslation.test.ts` drops its three mocks of deleted modules (`translationCacheRepository`, `translationApi`, `translationFiles`); a `vi.mock` of an unresolvable path fails the whole file.

### 6. The one-time sweep

Run after steps 1 to 5 compile with a placeholder `zh.ts` built mechanically from the current `zh.json`, filling keys that are missing or hash-stale in the JSON with the English value so type-check is green before the rewrite starts. **Sequencing:** steps 1 to 5 land as a commit with type-check and the existing suites green; the new `describe('ZH_STRINGS')` block lands in the same commit as the assembled sweep output, not before, because the placeholder file (77 non-Chinese entries, a handful of Traditional ones) would fail the English-passthrough and Traditional checks until the sweep replaces it.

1. **Batching.** Split the 5,764 keys into batches of about 250 contiguous keys (same namespace prefix where possible, ~23 batches). Each batch job receives: the key, `en`, `beanie` (as tone context only), the current zh (as "do not trust, may be wrong"), the glossary, the style rules, and a one-paragraph description of what the namespace is (`whoOwnsWhat.*` is the chores board, `magicBeans.*` is the AI allowance, and so on; the orchestrator writes these from `docs/` and the page components).
2. **Model.** Opus subagents, 4 to 6 in parallel, each writing its batch to `scratchpad/zh-batches/<n>.json` as `{ key: zh }`. They do not touch the repo.
3. **Style rules in the prompt.** Simplified Chinese only; natural app UI register (简洁、口语化但不随意); preserve every `{placeholder}` verbatim; keep `.one`/`.other` pairs both natural (Chinese has no plural, so both usually read the same); keep brand terms per glossary; keep emoji and arrows where en has them; never add punctuation the English lacks at the end of a label; full-width punctuation (，。：) in sentences, no space between CJK and a placeholder unless en has one around a number; measurements and currency codes unchanged; "bean" for the AI allowance is 豆子, "magic beans" is 魔法豆; family roles (Parent Bean, Little Bean) stay English per glossary.
4. **Assembly.** The orchestrator merges the batch files into `zh.ts` in `uiStrings.ts` key order, runs type-check and the new tests, and fixes any mechanical failure (a lost placeholder, a stray Traditional character) by re-asking that batch for the failing keys only.
5. **Review pass.** A separate Opus subagent (fresh context) reads a stratified sample: every key under the important-surface prefixes used by the beanie test (auth, PIN, recovery, sync, delete/leave confirms, errors), plus 300 random keys. It rates each as fine / awkward / wrong with a suggested fix, in Chinese-speaker terms. The orchestrator applies "wrong" and "awkward" fixes, re-runs the tests, and records the sample size and defect rate in the plan's Outcome.
6. **Report.** The Phase 8 report lists the defect rate, a dozen before/after examples, and the keys where the glossary produced a label greg may want to revisit (English nav labels inside a Chinese UI).

## Observability Coverage

- **Events**: `reportError({ surface: 'translation-load', severity: 'error', message: 'Translation load failed for zh', context: { error_code } })` for the one remaining failure, the dynamic chunk import rejecting after chunk-reload recovery is exhausted (offline before first precache, a corrupted cache). The language travels in the message (`'language'` is not an allowlisted context key and would be redacted). The user sees the existing toast (`error.translationLoadFailed`) and the app stays in English. A rotated-chunk failure (`isChunkLoadError`) is healed by `hardReload()` within the router's budget of 3 and is not reported, matching `main.ts`'s existing suppression of chunk-load errors. The one-time `beanies-translations` database deletion emits `logEvent({ level: 'info', surface: 'idb-legacy-cleanup', context: { action: 'failed', error_code } })` on failure only; success is silent by design (a per-boot event on every device would be noise), and the block carries a removal date.
- **Failure modes covered**: chunk import failure (the event above, triageable by `build_sha` + `error_code` + message); rotated chunk after deploy (self-heals; a `chunk_load` error_code in the report means the budget was exhausted); a missing translation key (impossible after this change: compile-time); a stale translation (undetectable by design, same as `beanie`, documented); English passthrough or Traditional characters (CI test, never reaches prod); orphaned IndexedDB cleanup failing (`action: 'failed'`; success is deliberately unlogged).
- **Success-path signal**: none added. The language switch is a local, sub-millisecond state change after the chunk resolves, and the chunk fetch is observable through the existing `load-perf` events if it ever matters. Adding a counter here would be noise.
- **Critical vs. telemetry**: nothing critical. A failed language load degrades to English and is firehose-only.
- **Privacy/store gate**: no new context key. The change **removes** a third-party network call (MyMemory) from the client; if any privacy page or store declaration names a translation service, that wording comes out in the same change (grep `privacy.astro`, `docs/runbooks/native-store-submission.md` for "translation" / "MyMemory").
